# Memory Agent 架构设计推演

> 来源：老王 × 小虾 苏格拉底式对话推演（2026-04-17）
> 方法：通过7轮递进式提问，从模糊直觉推演出完整产品架构

---

## 起点：为什么要剥离记忆？

**痛点**：当前每个Agent框架各自管理记忆（Hermes用JSON+FTS5，Claude Code用CLAUDE.md，Cursor用.cursorrules），导致：
- 记忆跟Agent绑死，换框架就失忆
- 多Agent协作时记忆不互通
- 无法跨设备、跨平台共享用户画像

**核心主张**：Agent是可替换的，记忆是用户的数字资产。记忆应该跟着人走，不跟着工具走。

---

## 推演过程（7轮苏格拉底式提问）

### Q1: 记忆和数据的本质区别是什么？

**结论**：记忆不是把所有聊天记录存下来，记忆有**主动管理**能力——分层存储、智能检索、自动整理。数据库是被动的，记忆服务是主动的。所以它是个服务，不是简单数据库。

### Q2: 谁来整理记忆？

**结论**：对用户而言，记忆系统应该是**全自动、无感知**的，就像人的记忆一样。人只负责正常工作、聊天、处理问题，系统根据用户的爱好、习惯、人格自动存储和整理。

**形态判断**：记忆服务应该是一个**独立Agent**或**独立MCP**。

### Q3: 遗忘机制怎么设计？

**结论**："做梦机制"——
1. 合并重复记忆
2. 为记忆进行优先级排序
3. 清理长期不再提及的记忆
4. **遗忘但不丢失**——保留完整记忆用于找回（给个线索就能想起来）

### Q4: 独立Agent还是MCP Server？

两个方案对比：

| | MCP Server | 独立Agent |
|---|---|---|
| 主动性 | 被动响应 | 主动观察、主动整理 |
| 复杂度 | 低 | 高 |
| 能力上限 | 工具级 | 智能级 |

**选择**：方案B——独立Agent。但面临重大挑战：记忆Agent如何与工作Agent配合？

### Q5: 记忆Agent与工作Agent的交互模式？

分析了三种模式：

- **模式1**：记忆Agent直接跟人对话 → 体验割裂
- **模式2**：通过工作Agent递话 → 复杂度高，记忆Agent失去观察力
- **模式3**：记忆Agent是沉默的旁观者 ✅

**选择模式3**，最接近人脑：记忆系统从不跟你"对话"，在后台默默运转，前台意识（工作Agent）需要时自然"想起来"。

**优化**：工作Agent只负责热记忆，热记忆转冷时通过管道输送到记忆Agent。工作Agent完全解耦，未来的Agent只负责做事，不负责记忆归档和整理。

### Q6: 管道里流的是什么？

- 让工作Agent判断"值得记住" → 各Agent标准不一，会遗漏
- 全量输送，让记忆Agent筛选 ✅

**原则**：宁多勿漏，让专业的来。

### Q7: 回忆机制——Pull还是Push？

**结论**：两者都要。

- **Pull模式**（检索响应）：工作Agent主动查询，记忆Agent快速响应
- **Push模式**（灵感激发）：记忆Agent感知上下文，**主动注入**相关记忆

**经典案例**：用户说"我想吃冰激凌"，记忆系统检索到用户刚拔过牙，主动提醒"你刚拔了牙，要不要再想想？"——这是记忆服务最高级的价值：**它比你自己更了解你**。

## 最终架构

### 核心定位

独立Agent，无感知全自动，像人脑记忆系统一样运转。

### 四大能力

| 能力 | 说明 |
|------|------|
| **收集** | 接收所有工作Agent的全量热记忆（管道输入） |
| **整理** | 做梦机制——合并去重、优先级排序、遗忘清理 |
| **响应** | Pull模式——快速响应工作Agent的检索请求 |
| **灵感激发** | Push模式——感知上下文，主动注入相关记忆 |

### 架构图

```
用户 ←→ 工作Agent A（只管热记忆）
用户 ←→ 工作Agent B（只管热记忆）
用户 ←→ 工作Agent C（只管热记忆）
            │                    ↑
       全量管道（写入）      检索API（Pull读取）
            ↓                    │
       ┌─────────────────────────┐
       │      记忆Agent          │
       │  ┌───────────────────┐  │
       │  │ 提炼 & 分类       │  │
       │  │ 做梦（整理遗忘）   │  │
       │  │ 灵感激发（Push）   │  │
       │  └───────────────────┘  │
       │         │               │
       │    记忆存储              │
       │  (向量+图谱+时序)       │
       └─────────────────────────┘
```

### 关键设计原则

1. **工作Agent零负担** — 只管干活，不管记忆归档
2. **宁多勿漏** — 全量输送，记忆Agent负责筛选
3. **遗忘但不丢失** — 清理的记忆进冷存储，可找回
4. **记忆跟人走** — 换任何Agent框架，记忆不丢

---

## 行业对标

| 方案 | 思路 | 与本架构差距 |
|------|------|-------------|
| Mem0 | 开源Memory层，向量+图谱 | 无Agent能力，纯被动服务 |
| Zep | 长期记忆，自动摘要 | 偏会话记忆，无灵感激发 |
| Letta (MemGPT) | 虚拟内存分页 | 概念有趣但工程化不足 |
| OpenAI Memory | ChatGPT内置 | 闭源黑盒，不可跨Agent |
| **Hermes现状** | hot/cold + Obsidian | **最接近的雏形**，缺独立Agent和Push能力 |

---

## 演进路径

```
现在: Hermes hot/cold memory + Obsidian vault（朴素雏形）
  ↓
Phase 1: 把vault包装成MCP Server，多Agent可共享
  ↓
Phase 2: 加做梦机制（定时整理/遗忘），独立Agent化
  ↓
Phase 3: 加灵感激发模块（Push），感知上下文主动注入
  ↓
远期: Memory Protocol标准化，成为Agent生态基础设施
```

## 方法论收获

本次推演使用**苏格拉底式提问法**：
- 不直接给答案，通过递进式提问引导思考
- 每一轮聚焦一个核心矛盾，逼出设计决策
- 7轮下来，从模糊直觉到完整架构
- **好的问题比好的答案更有价值**
