# AI Agent 核心心智模型

## 核心概念

> [!note] 核心定义：AI Agent (智能体)
> 在大语言模型 (LLM) 语境下，AI Agent 是一个将 LLM 作为核心推理引擎（大脑），通过感知当前上下文，自主拆解任务、规划步骤，并调用外部工具执行以改变环境状态的自治系统。

相较于传统的静态 Prompt 问答，Agent 的核心特征在于**闭环的行动与反馈机制**。它能够根据环境返回的真实数据动态调整后续策略。

> [!tip] .NET 类比
> 把 Agent 想象成一个 **BackgroundService + 状态机**：
> - `BackgroundService` 提供持续运行的循环 (`ExecuteAsync`)
> - 每一轮循环是一次 `Perception → Reasoning → Action → Observation`
> - 状态机 (`State Machine`) 管理当前处于哪个阶段、是否需要工具调用、是否完成任务
> - 工具调用就是 `IServiceProvider.GetRequiredService<T>()` 的动态解析

## 主流心智框架解析

目前工业界与学术界主流的智能体推理框架主要分为以下几种。它们在复杂度与适用场景上有着显著差异。

### 1. ReAct (Reasoning and Acting)

ReAct 是由普林斯顿大学与 Google 团队提出的一种交错执行推理与动作的范式。
它强制要求模型在执行任何外部动作（Action）前，必须先输出一段内在的思考过程（Thought），然后观察（Observation）动作结果。这种 `Thought -> Action -> Observation` 的状态机流转极大地提高了动作的准确性。

**ReAct 的状态机流转**：
```
┌──────────┐    ┌──────────┐    ┌──────────────┐
│ Thought   │───▶│  Action   │───▶│ Observation   │
│ (思考推理) │    │ (执行动作) │    │ (观察结果)     │
└──────────┘    └──────────┘    └──────┬───────┘
      ▲                                │
      │         任务未完成              │
      └────────────────────────────────┘
                    │
                    ▼ 任务完成
              ┌──────────┐
              │  Answer   │
              └──────────┘
```

> [!tip] 最佳实践
> 当任务属于线性依赖且工具调用逻辑较为直接时（如查天气、查库存），优先使用 ReAct 框架。它在延迟与效果之间取得了极佳的平衡。

**2025-2026 年 ReAct 的演进**：
- **ReAct 已成为事实标准**：OpenAI Agents SDK、LangGraph、Claude 的 tool_use 模式本质上都是 ReAct 的工程实现
- **与 Extended Thinking 融合**：Claude 3.5 和 o3 等推理模型将 ReAct 的 Thought 阶段替换为更强大的 Chain-of-Thought 推理，Thought 不再是简单的一句话，而是深度多步思考
- **隐式 ReAct**：新一代模型（GPT-4o、Claude 3.5 Sonnet）在 Function Calling 时已内化了 ReAct 模式，无需显式 prompt engineering 即可自动执行 Think-Act-Observe 循环

### 2. ToT (Tree of Thoughts)

ToT 将推理过程建模为一棵搜索树。每一步决策都是树上的一个节点，LLM 需要生成多个候选分支，并使用启发式评估机制（Heuristic Evaluator）对分支打分，通过广度优先搜索 (BFS) 或深度优先搜索 (DFS) 寻找全局最优解。

```
                    [问题]
                   /  |  \
                 /    |    \
            [方案A] [方案B] [方案C]    ← 第一步扩展
            /  \      |      \
         [A1] [A2]  [B1]    [C1]      ← 第二步扩展
          ↓    ↓     ↓       ↓
         3分  7分   8分     2分        ← 启发式评估
                     ↓
                  [最优解]              ← 选择得分最高的路径
```

> [!tip] SQL Server 类比
> ToT 类似于 SQL Server **查询优化器的搜索空间探索**：优化器会枚举多种 JOIN 顺序、索引选择方案，对每个方案做代价估算（Cardinality Estimation），最终选择估算代价最低的执行计划。ToT 做的是同样的事——枚举多种推理路径，评估每条路径的质量。

### 3. Reflexion (反思机制)

Reflexion 引入了长时记忆与自我反思闭环。其架构由 Actor（执行者）、Evaluator（评估者）和 Self-Reflection（反思模块）组成。当任务失败时，反思模块会总结失败原因并存入上下文记忆中，指导下一次重试。

```
     ┌─────────┐
     │  Actor   │──── 执行任务 ────▶ 结果
     └────┬────┘                      │
          │                           ▼
          │                     ┌──────────┐
          │                     │Evaluator │ 成功? ──▶ 结束
          │                     └────┬─────┘
          │                          │ 失败
          │                          ▼
          │                   ┌──────────────┐
          │                   │Self-Reflection│
          │                   │ 总结失败原因    │
          │                   └──────┬───────┘
          │                          │
          │                          ▼
          │                   ┌──────────────┐
          └──── 读取经验 ◀────│ Memory (记忆) │
                              └──────────────┘
```

> [!warning] 性能陷阱
> Reflexion 与 ToT 均会产生巨大的 Token 消耗。在工程落地时，需严密监控 API 成本并设置合理的最大重试次数 (Max Retries)。

### 4. LATS (Language Agent Tree Search) — 2025 年新增

LATS 结合了 ToT 的树搜索和 Reflexion 的反思机制，并引入了 **Monte Carlo Tree Search (MCTS)** 策略：

1. **Selection**：基于 UCB1 算法选择最有前景的节点
2. **Expansion**：LLM 生成新的候选行动
3. **Evaluation**：评估行动结果
4. **Backpropagation**：将评估结果回传更新所有祖先节点的统计信息

LATS 特别适合需要探索与利用平衡（Exploration-Exploitation Trade-off）的复杂任务，如多步骤代码生成和数学推理。

### 5. Plan-and-Execute（规划-执行分离）

2025 年在工程实践中广泛采用的模式，将任务拆分为两个阶段：

```
Planner (规划者 LLM)                Executor (执行者 LLM/Agent)
┌──────────────────────┐            ┌──────────────────────┐
│ 输入：用户目标         │            │ 输入：单个步骤        │
│ 输出：步骤列表         │            │ 输出：步骤执行结果     │
│                       │            │                       │
│ Step 1: 查询用户信息   │──────────▶│ 调用 get_user API     │
│ Step 2: 查询订单历史   │──────────▶│ 调用 query_orders API │
│ Step 3: 生成报告       │──────────▶│ 格式化输出            │
└──────────────────────┘            └──────────────────────┘
         ▲                                    │
         └── Re-plan (动态调整计划) ◀──────────┘
```

> [!tip] C# 类比
> 这就是 **CQRS (Command Query Responsibility Segregation)** 模式在 Agent 世界的翻版：Planner 是 Query 侧（只读分析），Executor 是 Command 侧（执行变更），两者职责分离让系统更可控。

## 流派横向对比

| 框架范式 | 推理拓扑结构 | Token 消耗 | 核心优势 | 典型适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **ReAct** | 线性序列 (Linear) | 中等 | 延迟低，可解释性好 | 信息检索、基础 [[3.1-函数调用底层机制]] |
| **ToT** | 树状分支 (Tree) | 极高 | 全局寻优能力极强 | 复杂数学证明、多步骤创意写作 |
| **Reflexion** | 环形反馈 (Loop) | 偏高 | 具备纠错能力与经验进化 | 自动化代码修复、长期对弈环境 |
| **LATS** | 树 + MCTS (Tree+Loop) | 极高 | 搜索效率优于 ToT | 竞赛级编程、复杂数学推理 |
| **Plan-and-Execute** | 两阶段分离 | 中等 | 可控性强，易于调试 | 企业级业务流程自动化 |

## 2025-2026 年认知架构新进展

### Anthropic 的 Agent 设计哲学

Anthropic 在 2025 年 3 月发布的《Building Effective Agents》研究报告中提出了重要的设计原则：

1. **优先使用简单方案**：不要一上来就搭建复杂 Agent 框架，先试试单次 LLM 调用 + 好的 prompt
2. **Workflows vs Agents**：
   - **Workflow**：预定义的 LLM 调用流程，编排逻辑在代码中（确定性）
   - **Agent**：LLM 自主决定执行路径（自主性）
3. **增量提升复杂度**：simple prompt → few-shot → RAG → tool use → workflow → agent
4. **Agent 循环的本质**：就是 `while not done: action = llm(context); result = execute(action); context += result`

### OpenAI 的 Agent 架构观

OpenAI 在 2025 年发布 Agents SDK 时，将 Agent 架构简化为三个核心原语：

1. **Agent**：一个配置了特定指令和工具的 LLM 实例
2. **Handoff**：Agent 之间的任务移交机制
3. **Guardrails**：输入/输出的安全护栏

这种"少即是多"的设计与 Anthropic 不谋而合——避免过度框架化。

### Google 的 Agent 白皮书

Google DeepMind 在 2025 年初发布的 Agent 白皮书将认知架构分为三层：

```
┌──────────────────────────┐
│    Orchestration Layer    │  ← Agent 循环控制
│  (ReAct / Plan-Execute)  │
├──────────────────────────┤
│     Model Layer          │  ← LLM 推理能力
│  (Gemini 2.5 Pro)        │
├──────────────────────────┤
│     Tool Layer           │  ← 外部能力扩展
│  (MCP / Function Call)   │
└──────────────────────────┘
```

## 工程落地要点

### Agent 可靠性模式

在生产环境中，Agent 的不确定性是最大挑战。关键稳定性模式：

| 模式 | 说明 | C# 类比 |
| :--- | :--- | :--- |
| **Max Iterations** | 限制最大循环次数，防止无限循环 | `CancellationToken` 超时 |
| **Fallback** | Agent 失败时降级到确定性逻辑 | `try-catch` + fallback handler |
| **Checkpoint** | 长任务在每步保存状态，支持断点恢复 | `IDistributedCache` 持久化 |
| **Observation Validation** | 验证工具返回结果的格式和合理性 | `ModelState.IsValid` 校验 |
| **Budget Control** | 限制 Token/API 调用总预算 | `SemaphoreSlim` 限流 |

> [!warning] 生产环境红线
> 不设置 Max Iterations 的 Agent 等于写了个 `while(true)` 不带 break——迟早会烧穿你的 API 额度。建议设置 max_iterations=10 作为安全阀，同时配合 token budget 做双重保护。

## 主流 Agent 框架（2025-2026）

### LangGraph v0.2+

LangChain 团队出品，有状态循环 Agent 图。核心思想：把 Agent 建模为**有向图**——节点是函数或子 Agent，边是条件路由，状态在节点间流转。

```python
from langgraph.graph import StateGraph

graph = StateGraph(AgentState)
graph.add_node("planner", plan_step)
graph.add_node("executor", execute_step)
graph.add_node("reviewer", review_step)
graph.add_conditional_edges("reviewer", should_continue,
    {"continue": "executor", "end": END})
```

> [!tip] .NET 类比
> 这就像用 Durable Functions 编排工作流，每个 Activity Function 是一个节点。

### OpenAI Agents SDK（2025.3）

替代之前实验性的 Swarm 项目。三个核心抽象：

- **Agent**：带指令和工具的 LLM 配置（类似一个配置好的 Controller）
- **Handoffs**：Agent 之间的任务交接（类似请求转发/路由）
- **Guardrails**：输入输出校验（类似 FluentValidation）

同期发布的 Responses API 支持内置工具：`web_search`、`file_search`、`computer_use`。

### CrewAI v0.100+

20k+ GitHub Stars。特色是**角色化多 Agent**——你定义 Agent 的角色(Role)、目标(Goal)、背景(Backstory)，它们像一个团队协作完成任务。

```python
researcher = Agent(
    role="高级研究员",
    goal="找到关于AI Agent的最新技术趋势",
    backstory="你是一个有10年经验的AI研究员...",
    tools=[search_tool, wiki_tool]
)
```

> [!tip] .NET 类比
> 每个 Agent 像一个微服务，有自己的职责边界，通过消息通信协作。

### AutoGen v0.5

微软出品，核心是 AgentChat API，支持异步多 Agent 对话。特色：Agent 之间可以像群聊一样交流，支持人类参与 (Human-in-the-Loop)。

### Claude 生态

- **Claude computer_use**：GUI-Agent，能操作鼠标键盘控制桌面应用
- **Claude Code**：CLI Agent，2025 年初发布，直接在终端中进行代码开发

## 从 Augmented LLM 到 Agent 的渐进路径

Anthropic 的建议（也是实践中验证有效的）：**不要一上来就搞复杂 Agent，从增强型 LLM 开始。**

```
Level 0: 纯 LLM 对话（ChatBot）
    ↓ 加检索
Level 1: RAG 增强（LLM + 知识库检索）
    ↓ 加工具
Level 2: Tool-Augmented LLM（LLM + 工具调用）
    ↓ 加循环
Level 3: ReAct Agent（LLM + 工具 + 思考循环）
    ↓ 加规划
Level 4: Plan-and-Execute Agent（规划 + 执行 + 反思）
    ↓ 加协作
Level 5: Multi-Agent 系统（多 Agent 协作/竞争）
```

> [!tip] .NET 类比
> 这和 .NET 开发一样——不要一开始就上微服务，先单体跑通，再按需拆分。

## 附录：.NET 开发者 Agent 概念速查

| .NET 概念 | Agent 对应概念 | 职责 |
|---|---|---|
| CLR（公共语言运行时） | LLM（大语言模型） | 核心推理引擎，负责"思考" |
| SQL Server / MemoryCache | Memory（记忆系统） | 长期持久化 / 短期上下文缓存 |
| DI 注册的接口(IService) | Tools（工具集） | 外部能力的标准化接入点 |
| ASP.NET 管道中间件 | Workflow（工作流） | 控制请求处理的流转顺序 |
| AppDomain / 进程隔离 | Sandbox（沙箱） | 隔离执行不受信任的代码 |

**LLM = CLR**：CLR 负责把 IL 编译成机器码并执行。LLM 负责把自然语言"编译"成推理步骤并执行。关键区别：CLR 是确定性的，LLM 是概率性的——这是 Agent 工程中大量"防御性编程"的根源。

**Memory = SQL Server + MemoryCache**：
- 短期记忆 = `MemoryCache` / Session State（上下文窗口，受 token 上限约束）
- 长期记忆 = SQL Server / 向量数据库（通过 RAG 按需加载，类似 EF Core 查询）

**Tools = DI 接口**：LLM 只看到工具的"接口声明"（名称、描述、参数 Schema），不关心背后实现——就像 Controller 通过构造函数注入拿到接口。工具声明的质量直接决定 Agent 表现，把它当 API 文档来写。

**Agent 防御性编程速查**：

| 风险 | 防护手段 | .NET 类比 |
|---|---|---|
| LLM 输出格式错误 | 结构化输出(JSON Mode) + 重试 | 强类型 + try-catch |
| 工具调用参数错误 | JSON Schema 验证 + 参数约束 | FluentValidation |
| 无限循环 | max_iterations 限制 | CancellationToken + Timeout |
| Token 爆炸 | 上下文窗口管理 + 摘要压缩 | 内存池 + GC |
| 幻觉/错误推理 | RAG 事实锚定 + 人工审核 | 集成测试 + Code Review |
| 成本失控 | 小模型 routing + 大模型推理 | 缓存策略 + 读写分离 |
