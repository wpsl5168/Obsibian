# 工作流编排模式

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。聚焦 AI Agent 工作流的编排模式、主流框架对比与工程实践。

## 核心概念

**工作流编排（Workflow Orchestration）** 是指将多个 LLM 调用、工具调用、条件判断等步骤按照一定的逻辑拓扑组织起来，形成可执行、可观测、可恢复的自动化流程。

> [!tip] .NET 类比
> 工作流编排就像 .NET 中的 **Durable Functions / Durable Task Framework**：
> - 每个 Activity 对应一次 LLM 调用或工具调用
> - Orchestrator Function 定义步骤之间的流转逻辑（串行、并行、条件分支）
> - 框架自动处理持久化、重试、超时
> - 即使进程崩溃也能从 checkpoint 恢复——这正是 Agent 工作流最需要的能力

### Workflow vs Agent：关键区别

| 维度 | Workflow（工作流） | Agent（智能体） |
| :--- | :--- | :--- |
| 流程控制 | 代码预定义（确定性） | LLM 动态决定（自主性） |
| 可预测性 | 高，路径可枚举 | 低，行为不确定 |
| 调试难度 | 低，步骤可追踪 | 高，推理过程不透明 |
| 适用场景 | 业务流程明确的场景 | 开放式、探索性任务 |
| 典型代表 | Chain、Router、Parallel | ReAct Agent、Plan-and-Execute |

Anthropic 在 2025 年的研究报告中明确建议：**能用 Workflow 解决的就不要用 Agent**。Agent 的自主性带来的灵活性也意味着不可预测性。

## 五大基础编排模式

### 1. Chain（链式）

最简单的模式：步骤 A → 步骤 B → 步骤 C，每步的输出是下一步的输入。

```
┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐
│ 输入  │───▶│ LLM① │───▶│ LLM② │───▶│ 输出  │
│      │    │ 提取  │    │ 分析  │    │      │
└──────┘    └──────┘    └──────┘    └──────┘
```

**适用场景**：文档处理流水线（提取 → 分类 → 摘要 → 翻译）

> [!tip] C# 类比
> 这就是 **Middleware Pipeline**（`app.Use().Use().Use()`）：每个中间件处理请求后传给下一个，最终返回结果。

### 2. Router（路由分发）

根据输入特征，将任务分发到不同的处理分支：

```
                    ┌──────────┐
                    │ 分类 LLM  │
                    │ (Router)  │
                    └────┬─────┘
                   ╱     │      ╲
                 ╱       │        ╲
         ┌──────┐  ┌──────┐  ┌──────┐
         │技术问题│  │商务问题│  │投诉处理│
         │专家LLM│  │专家LLM│  │专家LLM│
         └──────┘  └──────┘  └──────┘
```

**适用场景**：客服系统（按问题类型路由到不同技能组）

> [!tip] C# 类比
> 这就是 **Strategy Pattern + Factory**：`IServiceProvider` 根据运行时类型解析出具体的 `IHandler` 实现。

### 3. Parallel（并行扇出-扇入）

将任务拆分为多个独立子任务并行执行，最后汇总：

```
                ┌──────┐
                │ 拆分  │
                └──┬───┘
              ╱    │    ╲
            ╱      │      ╲
    ┌──────┐  ┌──────┐  ┌──────┐
    │子任务①│  │子任务②│  │子任务③│   ← 并行执行
    └──┬───┘  └──┬───┘  └──┬───┘
       ╲       │       ╱
         ╲     │     ╱
          ┌──────┐
          │ 汇总  │
          └──────┘
```

**适用场景**：多维度分析（同时做情感分析、关键词提取、分类）

> [!tip] C# 类比
> `Task.WhenAll(task1, task2, task3)` + 结果聚合。注意每个子任务的 LLM 调用是独立的，不共享上下文。

### 4. Orchestrator-Workers（指挥官-工人）

一个 Orchestrator LLM 动态拆解任务并分配给 Worker LLM 执行：

```
         ┌──────────────────┐
         │  Orchestrator     │
         │  (指挥官 LLM)     │◀──── 汇报结果
         │  动态任务分配      │
         └────────┬─────────┘
              ╱   │   ╲
            ╱     │     ╲
    ┌────────┐┌────────┐┌────────┐
    │Worker ①││Worker ②││Worker ③│
    │搜索信息 ││写代码   ││做测试   │
    └────────┘└────────┘└────────┘
```

与 Parallel 的区别：Orchestrator 可以**动态决定**需要几个 Worker、每个做什么，而不是预定义的并行分支。

**适用场景**：复杂的多步骤代码生成、研究报告撰写

### 5. Evaluator-Optimizer（评估-优化循环）

一个 LLM 生成结果，另一个 LLM 评估质量，不达标则迭代优化：

```
┌──────────┐         ┌──────────┐
│ Generator │────────▶│ Evaluator │
│ (生成器)   │         │ (评估器)   │
└──────────┘         └─────┬────┘
      ▲                    │
      │     不合格 + 改进建议 │
      └────────────────────┘
              │
              ▼ 合格
         ┌──────┐
         │ 输出  │
         └──────┘
```

**适用场景**：代码生成（生成 → 测试 → 修复 → 测试...直到通过）、内容创作优化

## 多 Agent 协作模式（Multi-Agent）

### Handoff 模式（任务移交）

OpenAI Agents SDK 推广的模式——Agent 之间通过 **Handoff** 进行任务移交：

```python
from agents import Agent, handoff

triage_agent = Agent(
    name="Triage Agent",
    instructions="根据用户问题分类，移交给合适的专家",
    handoffs=[
        handoff(target=tech_agent, description="技术问题"),
        handoff(target=billing_agent, description="账单问题"),
        handoff(target=human_agent, description="需要人工介入"),
    ]
)
```

Handoff 的本质是**控制权转移**：当前 Agent 将会话上下文完整传递给目标 Agent，自己退出循环。

> [!tip] C# 类比
> Handoff 就像 ASP.NET 的 **`context.Response.Redirect()`** 或更精确地说，是 **Chain of Responsibility Pattern**：每个 Handler 要么自己处理，要么 `next.Handle(request)` 传给下一个。

### Supervisor 模式（主管协调）

一个 Supervisor Agent 统筹多个 Worker Agent：

```
                 ┌──────────────┐
                 │  Supervisor   │
                 │  管理状态      │
                 │  分配任务      │
                 │  汇总结果      │
                 └──────┬───────┘
                    ╱   │   ╲
                  ╱     │     ╲
         ┌────────┐┌────────┐┌────────┐
         │Research ││Writer  ││Reviewer│
         │Agent    ││Agent   ││Agent   │
         └────────┘└────────┘└────────┘
```

与 Orchestrator-Workers 的区别：Supervisor 维护**全局状态**（如共享的文档草稿），Worker 在共享状态上操作。

### Swarm 模式（群体智能）

受 OpenAI 2024 年实验性项目 Swarm 启发，多个对等 Agent 自组织协作，无中央控制：

- 每个 Agent 有自己的角色和工具集
- Agent 通过共享 context 或消息总线通信
- 无单一故障点，但行为更难预测

> [!warning] 工程建议
> Swarm 模式在学术研究中有趣，但在生产环境中**慎用**——去中心化意味着去可控性。绝大多数企业场景用 Supervisor 或 Handoff 模式就够了。

## 主流编排框架对比（2026 年 4 月）

### LangGraph

**LangChain 团队**推出的 Agent 编排框架，核心抽象是**有向图（Graph）**：

- **State**：图的全局状态，所有节点共享
- **Node**：每个节点是一个处理函数（LLM 调用/工具调用/逻辑判断）
- **Edge**：节点之间的流转条件（可以是确定性的或 LLM 驱动的条件边）

```python
from langgraph.graph import StateGraph, END

graph = StateGraph(AgentState)
graph.add_node("research", research_node)
graph.add_node("write", write_node)  
graph.add_node("review", review_node)

graph.add_edge("research", "write")
graph.add_conditional_edges("review", quality_check, {
    "pass": END,
    "fail": "write"  # 回到写作节点修改
})
```

**优势**：灵活的图结构、内置持久化（checkpointing）、支持 human-in-the-loop
**劣势**：学习曲线陡峭、调试困难（图状态难以追踪）

### OpenAI Agents SDK

2025 年 3 月发布，Python-first 的轻量 Agent 框架：

```python
from agents import Agent, Runner, tool

@tool
def get_weather(city: str) -> str:
    """获取指定城市的天气"""
    return f"{city}: 晴, 25°C"

agent = Agent(
    name="Assistant",
    instructions="你是一个乐于助人的助手",
    tools=[get_weather],
    model="gpt-4o"
)

result = Runner.run_sync(agent, "北京今天天气怎么样？")
```

**核心特性**：
- `@tool` 装饰器自动从 Python type hints 生成 JSON Schema
- 内置 Handoff（Agent 间移交）
- 内置 Guardrails（输入/输出护栏）
- 支持 Tracing（可对接 LangSmith、Logfire 等可观测性平台）

**优势**：极简 API、官方维护、与 OpenAI API 深度集成
**劣势**：强绑定 OpenAI 生态（虽然支持其他 Provider 但体验不一）

### CrewAI

面向**多 Agent 协作**的框架，强调角色扮演和任务委派：

```python
from crewai import Agent, Task, Crew

researcher = Agent(
    role="Research Analyst",
    goal="收集并分析最新市场数据",
    tools=[search_tool, scrape_tool]
)

writer = Agent(
    role="Content Writer",
    goal="基于研究结果撰写报告",
    tools=[write_tool]
)

crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, write_task],
    process="sequential"  # 或 "hierarchical"
)
```

**优势**：多 Agent 协作体验好、角色定义直观
**劣势**：底层可控性不如 LangGraph

### AutoGen (Microsoft)

微软的多 Agent 对话框架，2025 年推出 **AutoGen v0.4** 大版本重构：

- 基于 Actor 模型重写（异步消息传递）
- 支持分布式部署
- 引入 Team（Agent 组）概念
- 内置多种对话模式（RoundRobin、Selector、Swarm）

### 框架选型指南

| 场景 | 推荐框架 | 理由 |
| :--- | :--- | :--- |
| 简单的单 Agent + 工具调用 | OpenAI Agents SDK | 最简单直接 |
| 复杂状态机、需要 human-in-the-loop | LangGraph | 图结构灵活、内置 checkpoint |
| 多角色协作（如研究 + 写作 + 审核） | CrewAI 或 AutoGen | 角色定义和协作机制完善 |
| 企业级、需要分布式部署 | AutoGen v0.4 | Actor 模型，可扩展 |
| 与 Anthropic Claude 深度集成 | 直接用 Claude API + tool_use | Anthropic 建议避免过度框架化 |

> [!tip] .NET 工程师指南
> 如果你是 .NET 技术栈，**Semantic Kernel (Microsoft)** 是最自然的选择。它在 2025 年已发展为成熟的 Agent 框架，支持：
> - `KernelFunction` 定义工具（类似 `[HttpGet]` 的声明式风格）
> - `ChatCompletionAgent` / `OpenAIAssistantAgent` 等多种 Agent 类型
> - Agent Group Chat（多 Agent 协作）
> - 与 Azure AI Services 深度集成

## 可观测性与调试

Agent 工作流的可观测性是工程落地的**关键痛点**。主流方案：

| 工具 | 类型 | 特点 |
| :--- | :--- | :--- |
| **LangSmith** | SaaS | LangChain 生态，Trace 可视化 |
| **Arize Phoenix** | 开源 | LLM Observability，支持 RAG 评估 |
| **Logfire (Pydantic)** | SaaS + 开源 | OpenTelemetry 原生，OpenAI Agents SDK 官方推荐 |
| **Braintrust** | SaaS | Eval + Tracing 一体化 |
| **Langfuse** | 开源 | 社区驱动，自部署友好 |

> [!tip] 核心指标
> 必须监控的四个指标：
> 1. **Token 消耗**：每次 Agent 循环的 input/output tokens
> 2. **延迟分布**：端到端延迟及每步延迟
> 3. **工具调用成功率**：工具调用失败/异常的比例
> 4. **循环次数**：Agent 执行了几轮才完成任务

## LangGraph 深度实操

### 状态管理

LangGraph 的 State 是一个 TypedDict，所有节点共享和修改同一个状态对象。

```python
from typing import TypedDict, Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]  # 消息列表，自动追加
    plan: str                                 # 当前计划
    iteration: int                            # 迭代次数
    final_answer: str                         # 最终答案
```

> [!tip] C# 类比
> 这就是 Durable Functions 中 Orchestrator 传递给每个 Activity 的上下文对象：
> ```csharp
> [FunctionName("AgentOrchestrator")]
> public async Task<AgentState> Run(
>     [OrchestrationTrigger] IDurableOrchestrationContext context)
> {
>     var state = context.GetInput<AgentState>();
>     state = await context.CallActivityAsync<AgentState>("Plan", state);
>     state = await context.CallActivityAsync<AgentState>("Execute", state);
>     return state;
> }
> ```

### 条件路由与循环

LangGraph 原生支持循环——这是它相比简单 DAG 框架的核心优势。

```python
def should_continue(state: AgentState) -> str:
    if state["iteration"] >= 3:
        return "end"              # 达到最大迭代，强制结束
    if state["quality_score"] > 0.8:
        return "end"              # 质量达标，正常结束
    return "retry"                # 继续迭代

graph.add_conditional_edges("evaluator", should_continue, {
    "retry": "generator",         # 循环回去重新生成
    "end": "output"               # 输出最终结果
})
```

> [!tip] C# 类比
> `do-while` 循环加退出条件，和 Durable Functions 的 `ContinueAsNew` 模式一样。

### Subgraph 嵌套

复杂 Workflow 可以拆分为多个子图，像 .NET 中的子工作流。

```python
# 子图：代码审查流程
review_subgraph = StateGraph(ReviewState)
review_subgraph.add_node("security_check", security_check)
review_subgraph.add_node("style_check", style_check)

# 主图中引用子图
main_graph = StateGraph(MainState)
main_graph.add_node("develop", develop_code)
main_graph.add_node("review", review_subgraph.compile())  # 嵌入子图
main_graph.add_node("deploy", deploy)
```

### Human-in-the-Loop 实操

```python
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()
app = graph.compile(checkpointer=checkpointer, interrupt_before=["deploy"])

# 执行到 deploy 节点前会暂停，等待人工确认
# 人工确认后，从 checkpoint 恢复继续执行
```

> [!tip] C# 类比
> WF 的 Bookmark 机制——工作流执行到某个点暂停，等待外部事件触发后继续。和 Durable Functions 的 `WaitForExternalEvent` 完全对应。

### Time Travel（时间旅行）

LangGraph 的 Checkpointer 支持回到任意历史状态重新执行。调试神器。

```python
# 查看所有 checkpoint
for state in app.get_state_history(config):
    print(state.values, state.config)

# 从某个历史 checkpoint 重新执行
app.update_state(old_config, new_values)
result = app.invoke(None, old_config)
```

> [!tip] C# 类比
> 数据库的 Point-in-Time Recovery，或者 Git 的 `git checkout <commit-hash>`。

## 多 Agent 通信模式

当 Workflow 中有多个 Agent 时，它们如何通信？

| 通信模式 | 机制 | 适用场景 | 复杂度 | .NET 类比 |
|---|---|---|---|---|
| 共享状态 | 所有 Agent 读写同一个 State | 2-3 个紧耦合 Agent | 低 | `ConcurrentDictionary` |
| 消息传递 | Agent 通过消息通信 | 松耦合、需要审计日志 | 中 | RabbitMQ / Azure Service Bus |
| 层级委托 | 上级分配、下级上报 | 复杂任务分解 | 高 | Hangfire 父子 Job / Saga |

LangGraph 默认采用共享状态（Blackboard）模式。AutoGen v0.5 的 AgentChat API 是消息传递模式。CrewAI 和 OpenAI Agents SDK 的 Handoffs 支持层级委托。

## 工程最佳实践

### 不要过度抽象

> "不要一上来就搞多 Agent 编排，先看一个 augmented LLM 能不能解决问题。" —— Anthropic

这和 .NET 界"不要过早微服务化"的建议一模一样。先单体，有明确需求再拆分。

### 工具描述当 API 文档写

```json
// ❌ 糟糕的工具描述
{ "name": "search", "description": "搜索" }

// ✅ 好的工具描述
{
  "name": "search_codebase",
  "description": "在代码仓库中搜索文件内容。支持正则表达式。返回匹配的文件路径和行号。最多返回50条结果。",
  "inputSchema": {
    "properties": {
      "pattern": { "type": "string", "description": "搜索模式，支持正则表达式" },
      "file_glob": { "type": "string", "description": "文件过滤，如 '*.py'", "default": "*" },
      "max_results": { "type": "integer", "default": 50, "enum": [10, 20, 50, 100] }
    }
  }
}
```

参数尽量用 `enum` 约束——减少 LLM "自由发挥"出错的概率。

### 错误处理三板斧

```python
# 1. max_iterations 防无限循环
MAX_ITERATIONS = 5

# 2. 超时控制
result = await asyncio.wait_for(agent.run(task), timeout=120)

# 3. 异常兜底——不要直接抛异常终止，给 LLM 机会自我修正
try:
    result = await tool.execute(args)
except Exception as e:
    result = f"工具执行失败: {e}. 请尝试其他方法。"
```

> [!tip] C# 类比
> `CancellationToken` + `try-catch` + Polly 重试。

### 成本控制策略

| 策略 | 实现 | 节省比例 |
|---|---|---|
| 路由用小模型 | GPT-4o-mini 做分类，Opus 做推理 | 50-70% |
| 缓存常见查询 | 语义相似度匹配历史结果 | 30-50% |
| 限制上下文长度 | 摘要压缩历史消息 | 20-40% |
| 早停机制 | 置信度达标就停止迭代 | 视场景而定 |

### 渐进式路径

```
Step 1: 单 LLM + 工具调用（不需要 Workflow 框架）
    ↓
Step 2: Prompt Chaining（2-3 步顺序流水线）
    ↓
Step 3: Routing（输入分类 + 专业化处理）
    ↓
Step 4: ReAct 循环（LangGraph 单 Agent + 循环）
    ↓
Step 5: Orchestrator-Workers（多 Agent 协作）
    ↓
Step 6: 完整系统（Human-in-the-Loop + 持久化 + 监控）
```

每一步都要确认当前步骤真的不够用了，再往下走。过早复杂化是 Agent 开发的第一大坑。
