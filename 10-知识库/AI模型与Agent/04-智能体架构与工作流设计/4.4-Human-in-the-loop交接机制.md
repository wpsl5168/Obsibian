# Human-in-the-loop 交接机制

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。聚焦 AI Agent 与人类协作的交接模式、审批工作流与安全护栏设计。

## 核心概念

**Human-in-the-loop (HITL)** 是指在 AI Agent 的自主执行循环中，在关键决策点引入人类审核、确认或介入的机制。它是 Agent 从实验环境走向生产环境的**必要安全网**。

> [!tip] .NET 类比
> HITL 就像 **ASP.NET Core 的 Authorization Middleware**：
> - 不是所有请求都需要授权（简单查询 Agent 自主完成）
> - 但涉及敏感操作时（修改数据、发送邮件、执行支付），必须经过授权（人类审批）
> - Middleware Pipeline 的位置很关键——在执行 Action 之前插入审批节点
> - 就像 `[Authorize(Policy = "Admin")]` 标注在 Controller 方法上，Agent 的审批标注在敏感工具上

### 为什么 HITL 是必需的

| 风险场景 | 说明 | 后果 |
| :--- | :--- | :--- |
| **不可逆操作** | 删除数据、发送邮件、执行支付 | 无法回滚的破坏性操作 |
| **高成本决策** | 大额采购、合同签署 | 经济损失 |
| **信息不确定** | Agent 基于不完整信息做判断 | 错误决策 |
| **合规要求** | 金融、医疗等受监管行业 | 法律风险 |
| **边界场景** | Agent 遇到训练数据未覆盖的情况 | 幻觉或错误输出 |

## HITL 的四种模式

### 模式 1：Tool-level Approval（工具级审批）

在 Agent 调用特定工具前，暂停执行等待人类确认。

```
Agent 推理 → 决定调用 delete_record()
    ↓
🔴 暂停！该工具标记为需要审批
    ↓
通知人类：
  "Agent 请求删除记录 #12345，理由：用户要求删除过期数据"
    ↓
人类选择：[批准] [拒绝] [修改参数后批准]
    ↓
Agent 继续执行或调整策略
```

> [!tip] MCP Tool Annotations 的应用
> 这正是 [[3.2-Model_Context_Protocol规范解析|MCP]] 的 Tool Annotations 设计目的：
> ```json
> {
>   "name": "delete_user_data",
>   "annotations": {
>     "destructiveHint": true,   // ← Host 看到此标记自动触发审批
>     "readOnlyHint": false,
>     "idempotentHint": false
>   }
> }
> ```

**工程实现**（LangGraph 示例）：

```python
from langgraph.graph import StateGraph
from langgraph.checkpoint.memory import MemorySaver

def should_approve(state):
    """判断是否需要人类审批"""
    last_action = state["pending_action"]
    if last_action["tool"] in SENSITIVE_TOOLS:
        return "human_review"
    return "execute"

graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("execute", execute_tool_node)
graph.add_node("human_review", human_review_node)  # 中断点

graph.add_conditional_edges("agent", should_approve, {
    "human_review": "human_review",
    "execute": "execute"
})

# 编译时启用 checkpointing
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["human_review"]  # 在此节点前暂停
)
```

当执行到 `human_review` 节点时，LangGraph 会自动保存完整状态并暂停。人类审批后，调用 `app.update_state()` 恢复执行。

### 模式 2：Output Review（输出审核）

Agent 生成最终输出后，交给人类审核再发送给用户：

```
用户提问 → Agent 推理 → 生成回答草稿
    ↓
🔶 审核队列
    ↓
人类审核员：
  [直接发送] [编辑后发送] [驳回重新生成] [人工接管]
```

**适用场景**：
- 对外客服回复（品牌风险控制）
- 医疗/法律咨询（合规要求）
- 高价值客户的服务（VIP 体验保障）

### 模式 3：Escalation（升级介入）

Agent 检测到自己无法处理的情况时，**主动**将任务升级给人类：

```python
# Agent 的 System Prompt 中明确定义升级规则
SYSTEM_PROMPT = """
你是客服 Agent。以下情况必须升级给人工客服：
1. 用户明确要求"转人工"
2. 连续 3 轮无法解决用户问题
3. 涉及退款金额 > 500 元
4. 用户情绪检测为愤怒/激动
5. 你不确定答案的正确性（置信度 < 0.7）

升级时调用 escalate_to_human 工具，必须附带：
- 问题摘要
- 已尝试的解决方案
- 建议的处理方向
"""
```

**Handoff 与 Escalation 的区别**：

| 维度 | Handoff（同级移交） | Escalation（向上升级） |
| :--- | :--- | :--- |
| 方向 | Agent → Agent | Agent → Human |
| 触发 | 任务类型不匹配 | 能力不足或风险过高 |
| 上下文 | 完整传递 | 传递 + 摘要 |
| 回流 | 通常不回流 | 人类可能将部分任务交回 Agent |

### 模式 4：Collaborative Editing（协同编辑）

人类和 Agent 在同一个工作产物上协作，交替修改：

```
Agent 生成初稿 → 人类修改第 2 段 → Agent 根据修改调整其余部分
    → 人类确认 → Agent 执行最终格式化 → 发布
```

**适用场景**：长文档撰写、代码 Review（如 GitHub Copilot Workspace）、设计稿迭代

## Guardrails（安全护栏）

Guardrails 是 HITL 的自动化补充——不需要人类每次手动审核，而是用**规则或 AI 模型**自动拦截不合规的行为。

### 输入护栏（Input Guardrails）

在用户输入到达 Agent 之前进行过滤：

```
用户输入 → [Input Guardrail] → Agent
              │
              ├── Prompt Injection 检测
              ├── 敏感信息脱敏（PII Masking）
              ├── 话题合规性检查
              └── 意图分类（是否在 Agent 能力范围内）
```

**Prompt Injection 防护**（2025-2026 年的重点安全课题）：

```python
# OpenAI Agents SDK 的 Guardrail 实现
from agents import Agent, InputGuardrail, GuardrailFunctionOutput

async def injection_detector(ctx, agent, input):
    """检测 Prompt Injection 攻击"""
    result = await Runner.run(
        injection_classifier_agent,  # 专门的分类 Agent
        input,
        context=ctx
    )
    return GuardrailFunctionOutput(
        output_info=result,
        tripwire_triggered=result.is_injection  # 触发则中断
    )

agent = Agent(
    name="Customer Support",
    input_guardrails=[
        InputGuardrail(guardrail_function=injection_detector)
    ]
)
```

### 输出护栏（Output Guardrails）

在 Agent 输出到达用户之前进行过滤：

```
Agent 输出 → [Output Guardrail] → 用户
                │
                ├── 幻觉检测（Factuality Check）
                ├── 有害内容过滤
                ├── PII 泄漏检测
                ├── 品牌合规检查
                └── 格式校验
```

### 工具调用护栏（Tool Guardrails）

在工具执行前后进行安全检查：

| 检查点 | 检查内容 | 示例 |
| :--- | :--- | :--- |
| **Pre-execution** | 参数合法性、权限检查 | SQL 注入检测、文件路径越权 |
| **Rate Limiting** | 调用频率限制 | 同一工具每分钟最多调用 10 次 |
| **Post-execution** | 结果合理性、敏感数据脱敏 | 返回结果中的身份证号脱敏 |
| **Cost Control** | Token/API 消耗控制 | 单次任务总 token < 100K |

> [!tip] C# 实现思路
> 用 **Decorator Pattern** 或 **Action Filter** 包裹每个工具调用：
> ```csharp
> public class GuardedToolExecutor : IToolExecutor
> {
>     private readonly IToolExecutor _inner;
>     private readonly IEnumerable<IToolGuardrail> _guardrails;
>     
>     public async Task<ToolResult> ExecuteAsync(ToolCall call)
>     {
>         // Pre-execution guardrails
>         foreach (var guard in _guardrails)
>             await guard.ValidateInputAsync(call);
>         
>         var result = await _inner.ExecuteAsync(call);
>         
>         // Post-execution guardrails
>         foreach (var guard in _guardrails)
>             result = await guard.ValidateOutputAsync(result);
>         
>         return result;
>     }
> }
> ```

## 审批工作流设计

### 异步审批架构

生产环境中，人类审批是异步的——Agent 不能阻塞等待：

```
┌──────────┐     ┌──────────────┐     ┌──────────────┐
│  Agent    │────▶│ Approval Queue│────▶│  审批 UI      │
│ (暂停)    │     │ (Redis/MQ)    │     │  (Web/Mobile) │
└──────────┘     └──────────────┘     └──────┬───────┘
      ▲                                       │
      │              审批结果                   │
      └───────────── (Webhook/Event) ─────────┘
```

**关键设计决策**：

| 决策点 | 选项 | 建议 |
| :--- | :--- | :--- |
| 审批超时 | 自动批准 / 自动拒绝 / 升级 | 安全敏感场景选自动拒绝 |
| 审批粒度 | 每次工具调用 / 每批次 / 每任务 | 按风险分级 |
| 审批者选择 | 固定人员 / 值班表 / 技能路由 | 大型团队用技能路由 |
| 上下文呈现 | 原始数据 / AI 摘要 / 可视化 | 提供足够但不过多的上下文 |

### 风险分级矩阵

| 风险等级 | 审批要求 | 工具示例 |
| :--- | :--- | :--- |
| 🟢 **低** | 无需审批，自动执行 | 查询天气、搜索文档 |
| 🟡 **中** | Agent 执行后异步通知 | 发送内部消息、创建工单 |
| 🟠 **高** | 执行前需要人类审批 | 修改数据库记录、调用外部 API |
| 🔴 **极高** | 双人审批 + 操作日志 | 删除数据、执行支付、发送外部邮件 |

> [!tip] 工具标注驱动
> 将风险等级编码到 MCP Tool Annotations 或工具元数据中，审批系统自动根据标注执行对应策略——无需硬编码每个工具的审批规则。

## 2025-2026 年行业实践

### OpenAI Agents SDK 的 Guardrails 实现

OpenAI 在 Agents SDK 中将 Guardrails 作为一等公民：
- `InputGuardrail`：在 Agent 处理前检查输入
- `OutputGuardrail`：在输出给用户前检查输出
- Guardrail 与 Agent 推理**并行执行**，不增加额外延迟
- 触发 tripwire 时自动抛出异常，中断 Agent 循环

### LangGraph 的 Interrupt 机制

LangGraph 提供了最灵活的 HITL 实现：
- `interrupt_before` / `interrupt_after`：在指定节点前/后中断
- 中断时自动保存完整图状态（checkpointing）
- 人类可以通过 `Command` 对象修改状态、跳转节点、甚至回退到之前的 checkpoint
- 2025 年新增 `Command(resume=value)` 模式，简化了审批结果的回传

### Anthropic 的安全设计理念

Anthropic 在 Agent 安全方面强调**纵深防御**：
1. **模型层**：Constitutional AI、RLHF 训练模型拒绝有害请求
2. **Prompt 层**：System prompt 中明确定义行为边界
3. **工具层**：Tool Annotations 标记风险级别
4. **应用层**：Host 实现审批、限流、日志
5. **人类层**：HITL 作为最后防线

### 微软 Semantic Kernel 的 Approval Filter

```csharp
// Semantic Kernel 的函数调用过滤器（C# 原生实现）
public class ApprovalFilter : IAutoFunctionInvocationFilter
{
    public async Task OnAutoFunctionInvocationAsync(
        AutoFunctionInvocationContext context,
        Func<AutoFunctionInvocationContext, Task> next)
    {
        var functionName = context.Function.Name;
        
        if (RequiresApproval(functionName))
        {
            var approved = await RequestHumanApproval(
                functionName, 
                context.Arguments);
            
            if (!approved)
            {
                context.Result = new FunctionResult(
                    context.Function, 
                    "操作被管理员拒绝");
                return;  // 不执行工具，直接返回拒绝信息
            }
        }
        
        await next(context);  // 执行工具
    }
}
```

## 设计最佳实践

1. **渐进式自动化**：先全人工 → 人机协作 → Agent 主导 + 人类监督 → 全自动化（仅低风险场景）
2. **审批疲劳防御**：审批请求太多会导致人类"橡皮图章"式盲批。用风险分级减少不必要的审批
3. **上下文充分呈现**：审批界面要展示 Agent 的推理过程、调用参数、风险评估，不要让审批者"盲审"
4. **审批 SLA**：定义每个风险等级的审批时效要求，超时自动升级
5. **审计日志**：所有 Agent 操作（无论是否经过审批）都要留痕，满足合规审计需求

> [!warning] 关键红线
> **永远不要**让 Agent 直接执行涉及资金的操作（支付、转账）而不经过人类确认。即使 Agent 的准确率是 99.9%，0.1% 的错误在金融场景中也是不可接受的。
