# LangGraph 深度实操

> 📚 上级页面：[[4.2-工作流编排模式]]

## LangGraph 深度实操

### 状态管理

LangGraph 的 State 是一个 TypedDict，所有节点共享和修改同一个状态对象。

```python
from typing import TypedDict, Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]  # 消息列表，自动追加
    plan: str                                 # 当前计划
    iteration: int                            # 迭代次数
    final_answer: str                         # 最终答案
```

> [!tip] C# 类比
> 这就是 Durable Functions 中 Orchestrator 传递给每个 Activity 的上下文对象：
> ```csharp
> [FunctionName("AgentOrchestrator")]
> public async Task<AgentState> Run(
>     [OrchestrationTrigger] IDurableOrchestrationContext context)
> {
>     var state = context.GetInput<AgentState>();
>     state = await context.CallActivityAsync<AgentState>("Plan", state);
>     state = await context.CallActivityAsync<AgentState>("Execute", state);
>     return state;
> }
> ```

### 条件路由与循环

LangGraph 原生支持循环——这是它相比简单 DAG 框架的核心优势。

```python
def should_continue(state: AgentState) -> str:
    if state["iteration"] >= 3:
        return "end"              # 达到最大迭代，强制结束
    if state["quality_score"] > 0.8:
        return "end"              # 质量达标，正常结束
    return "retry"                # 继续迭代

graph.add_conditional_edges("evaluator", should_continue, {
    "retry": "generator",         # 循环回去重新生成
    "end": "output"               # 输出最终结果
})
```

> [!tip] C# 类比
> `do-while` 循环加退出条件，和 Durable Functions 的 `ContinueAsNew` 模式一样。

### Subgraph 嵌套

复杂 Workflow 可以拆分为多个子图，像 .NET 中的子工作流。

```python
# 子图：代码审查流程
review_subgraph = StateGraph(ReviewState)
review_subgraph.add_node("security_check", security_check)
review_subgraph.add_node("style_check", style_check)

# 主图中引用子图
main_graph = StateGraph(MainState)
main_graph.add_node("develop", develop_code)
main_graph.add_node("review", review_subgraph.compile())  # 嵌入子图
main_graph.add_node("deploy", deploy)
```

### Human-in-the-Loop 实操

```python
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()
app = graph.compile(checkpointer=checkpointer, interrupt_before=["deploy"])

# 执行到 deploy 节点前会暂停，等待人工确认
# 人工确认后，从 checkpoint 恢复继续执行
```

> [!tip] C# 类比
> WF 的 Bookmark 机制——工作流执行到某个点暂停，等待外部事件触发后继续。和 Durable Functions 的 `WaitForExternalEvent` 完全对应。

### Time Travel(时间旅行)

LangGraph 的 Checkpointer 支持回到任意历史状态重新执行。调试神器。

```python
# 查看所有 checkpoint
for state in app.get_state_history(config):
    print(state.values, state.config)

# 从某个历史 checkpoint 重新执行
app.update_state(old_config, new_values)
result = app.invoke(None, old_config)
```

> [!tip] C# 类比
> 数据库的 Point-in-Time Recovery,或者 Git 的 `git checkout <commit-hash>`。

## 生产级 HITL 模式深度解析

### Streaming + Breakpoint 组合拳

生产环境中,HITL 不能是"执行完等结果"的黑盒,必须实时可见+可干预:

```python
from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import StateGraph

# 1. 配置 interrupt_before — 在关键节点前暂停
checkpointer = MemorySaver()
app = graph.compile(
    checkpointer=checkpointer,
    interrupt_before=["deploy", "delete_data"]  # 高危操作前强制暂停
)

# 2. Streaming 实时追踪执行
config = {"configurable": {"thread_id": "prod-job-123"}}
for chunk in app.stream(initial_state, config, stream_mode="values"):
    print(f"[STATE UPDATE] {chunk}")
    # 实时将状态推送到监控系统/日志

# 3. 执行到 interrupt 点时,检查状态并决策
current_state = app.get_state(config)
print(f"[PAUSED] Waiting at: {current_state.next}")
print(f"Current plan: {current_state.values['plan']}")

# 人工审批后,决定是继续、修改还是终止
if user_approved:
    # 可选:修改状态再继续
    app.update_state(config, {"approved_by": "user@example.com"})
    result = app.invoke(None, config)  # 从断点继续
else:
    # 拒绝:不再继续,记录日志
    app.update_state(config, {"status": "rejected", "reason": user_reason})
```

**关键实现细节**:
- `interrupt_before` 在进入节点**前**暂停(state 已更新但节点未执行)
- `interrupt_after` 在节点执行**后**暂停(适合"执行完让人检查结果"的场景)
- `stream_mode="values"` 返回完整 state,`stream_mode="updates"` 只返回本轮更新的字段

### Interrupt 的三种响应模式

LangChain 官方文档(2026)定义了标准 HITL 响应类型:

| 响应类型 | 用途 | 实现 |
|---------|------|------|
| `approve` | 批准原计划,继续执行 | `app.invoke(None, config)` |
| `edit` | 修改 state 后继续 | `app.update_state(config, new_values)` + `invoke` |
| `reject` | 拒绝并终止 | `update_state` 写入拒绝原因,不再 `invoke` |
| `respond` | 直接回答(用于"问用户"类工具) | `update_state` 写入用户答案,继续执行 |

```python
# 实战例子:Code Review Agent
# 场景:代码审查 Agent 发现"删除 1000+ 行代码"的 PR,暂停等人工确认

def review_node(state: AgentState):
    diff = state["pr_diff"]
    lines_deleted = diff.count("\n-")
    
    if lines_deleted > 1000:
        # 触发 interrupt,将高危信息暴露给人类
        return Command(
            update={"warning": f"High risk: {lines_deleted} lines deleted"},
            interrupt={"reason": "Large deletion detected", "diff_summary": diff[:500]}
        )
    return {"review_status": "auto_approved"}

# 人工介入:
state = app.get_state(config)
if state.values["warning"]:
    # 人类看了 diff 后决定
    if human_says_ok:
        app.update_state(config, {"review_status": "human_approved"})
        app.invoke(None, config)  # 继续
    else:
        app.update_state(config, {"review_status": "rejected", "reason": "Unsafe change"})
```

### Time Travel 实战:调试与分支探索

```python
# 场景:Agent 执行到第 8 步时出错,需要回到第 5 步改参数重试

# 1. 列出历史 checkpoint
history = list(app.get_state_history(config))
for i, snapshot in enumerate(history):
    print(f"[{i}] Step: {snapshot.next}, Iteration: {snapshot.values.get('iteration')}")

# 输出示例:
# [0] Step: ('output',), Iteration: 8  ← 当前(失败)
# [1] Step: ('evaluator',), Iteration: 7
# [2] Step: ('generator',), Iteration: 6
# [3] Step: ('planner',), Iteration: 5  ← 目标

# 2. 跳回第 5 步的 checkpoint
target_config = history[3].config
print(f"Rewinding to: {history[3].values}")

# 3. 修改 state 后重新执行
app.update_state(target_config, {"temperature": 0.3, "iteration": 5})
new_result = app.invoke(None, target_config)  # 从第 5 步重新跑,走出新分支
```

**生产级 Time Travel 用途**:
- **A/B 测试**:同一输入,在某个 checkpoint 分叉出两条路径(不同 prompt/模型),对比结果
- **故障恢复**:线上 Agent 执行到一半崩溃,从最近的 checkpoint 恢复继续(类似 Durable Functions 的 replay)
- **用户反悔**:用户说"上一步选错了",直接 rewind 回去重选

### 生产环境 Checkpoint 持久化

`MemorySaver` 只在内存,进程重启就丢。生产必须持久化:

```python
from langgraph.checkpoint.postgres import PostgresSaver

# PostgreSQL checkpointer — 数据库存 state 历史
DB_URI = "postgresql://user:pass@localhost/checkpoints"
checkpointer = PostgresSaver.from_conn_string(DB_URI)

app = graph.compile(checkpointer=checkpointer)

# 每次执行都自动存 checkpoint,跨进程/跨机器都能恢复
config = {"configurable": {"thread_id": "order-processing-456"}}
app.invoke(input_data, config)

# 另一台机器/另一个进程也能恢复
app2 = graph.compile(checkpointer=PostgresSaver.from_conn_string(DB_URI))
state = app2.get_state(config)  # 拿到完整历史
```

**企业级 Checkpoint 方案对比**:

| Backend | 适用场景 | 优势 | 劣势 |
|---------|---------|------|------|
| `MemorySaver` | 开发/测试 | 零配置 | 进程重启丢失 |
| `PostgresSaver` | 中小规模生产 | SQL 事务保证,易查询 | 单点,需维护 DB |
| `RedisSaver` | 高并发短生命周期 | 快,支持 TTL | 数据可能丢(非 AOF 配置) |
| S3/Blob Storage | 长期归档审计 | 无限容量,合规友好 | 查询慢,需自建索引 |

## Subgraph 嵌套与状态共享陷阱

### 父子 State 映射的两种模式

```python
# 模式 1: 直接嵌入 — 父子 State 字段完全一致
parent_graph = StateGraph(UnifiedState)
parent_graph.add_node("sub", subgraph.compile())  # 无缝共享

# 模式 2: 适配器模式 — 父子 State 不兼容,需显式映射
def subgraph_adapter(parent_state: ParentState) -> ChildState:
    return ChildState(
        query=parent_state["user_input"],
        max_results=3
    )

def result_merger(child_state: ChildState) -> dict:
    return {"search_results": child_state["results"]}

parent_graph.add_node(
    "search",
    subgraph.compile() | subgraph_adapter  # 输入映射
)
parent_graph.add_edge("search", result_merger)  # 输出映射
```

### Subgraph Checkpoint 独立性问题

**陷阱**:父图和子图都有 checkpointer 时,子图的 state 会被父图覆盖。

```python
# ❌ 错误示范 — 子图 checkpoint 会被父图"覆盖"
subgraph = StateGraph(SubState)
subgraph_app = subgraph.compile(checkpointer=MemorySaver())  # 子图有自己的 checkpoint

parent = StateGraph(ParentState)
parent.add_node("sub", subgraph_app)
parent_app = parent.compile(checkpointer=MemorySaver())  # 父图也有 checkpoint

# 父图执行时,子图的 checkpoint 不会独立保存!

# ✅ 正确做法 — 只在父图配置 checkpointer
parent_app = parent.compile(checkpointer=PostgresSaver(...))
# 子图不配置 checkpointer,依赖父图的统一持久化
```

**设计原则**:
- 嵌套 Workflow 只在**最外层**配置 checkpointer
- 子图作为"纯函数"节点,不应有独立的持久化状态
- 如果子图确实需要独立生命周期,应拆成独立服务(通过 API/消息队列通信)

## 实战决策树

```
需要工作流编排?
├─ 否 → 单 LLM + Function Calling 足矣
└─ 是 → 需要循环/条件分支?
    ├─ 否 → Prompt Chaining(LCEL/纯函数)
    └─ 是 → 需要人工介入?
        ├─ 否 → LangGraph 单图 + 条件边
        └─ 是 → 需要跨会话恢复?
            ├─ 否 → MemorySaver + interrupt
            └─ 是 → PostgresSaver + HITL 完整方案
```
