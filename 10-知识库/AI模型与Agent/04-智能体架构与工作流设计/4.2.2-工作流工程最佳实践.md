## 可观测性与调试

Agent 工作流的可观测性是工程落地的**关键痛点**。2026年LangChain调研显示,超过60%的生产事故与状态管理和可观测性不足有关。

### 可观测性平台对比(2026版)

| 工具 | 类型 | 核心优势 | 适用场景 | 价格模型 |
|------|------|---------|---------|---------|
| **LangSmith** | SaaS | LangChain原生集成,UI最成熟 | LangChain/LangGraph项目 | 免费5K traces/月,Plus $39/席 |
| **Langfuse** | 开源+云 | 社区驱动,自部署友好,PostgreSQL后端 | 金融/医疗等数据敏感场景 | 开源免费,云版按trace计费 |
| **Arize Phoenix** | 开源 | RAG评估+嵌入分析,支持离线分析 | 需要深度RAG调试的团队 | 开源免费 |
| **Braintrust** | SaaS | Eval+Tracing一体化,支持生产trace自动生成评估 | 重视持续评估的团队 | 按trace+eval计费 |
| **Logfire (Pydantic)** | SaaS+OSS | OpenTelemetry原生,结构化日志,OpenAI官方推荐 | 已有OTel基础设施的企业 | 免费tier,企业按量 |

> [!tip] 核心指标 — 四个必监控维度
> 1. **Token经济学**:每次Agent循环的input/output tokens,按模型分类的成本归因
> 2. **延迟分布**:端到端P50/P95/P99延迟,每步延迟(LLM调用 vs 工具执行 vs 状态序列化)
> 3. **工具调用健康度**:成功率、失败类型分布(超时/4xx/5xx/解析错误)、重试次数
> 4. **循环收敛性**:Agent执行轮数分布,是否有"无限循环"异常,平均几轮收敛

### OpenTelemetry GenAI标准(2026统一规范)

2026年OpenTelemetry正式发布GenAI语义约定,成为Agent可观测性的事实标准:

```python
from opentelemetry import trace
from opentelemetry.semconv.gen_ai import GenAIAttributes

tracer = trace.get_tracer(__name__)

with tracer.start_as_current_span("agent.run") as span:
    span.set_attribute(GenAIAttributes.SYSTEM, "langgraph")
    span.set_attribute(GenAIAttributes.OPERATION_NAME, "react_loop")
    span.set_attribute(GenAIAttributes.REQUEST_MODEL, "gpt-4.1-turbo")
    span.set_attribute(GenAIAttributes.REQUEST_TEMPERATURE, 0.7)
    
    # 嵌套span记录工具调用
    with tracer.start_as_current_span("tool.search") as tool_span:
        tool_span.set_attribute(GenAIAttributes.TOOL_NAME, "web_search")
        tool_span.set_attribute("tool.input", query)
        result = search(query)
        tool_span.set_attribute("tool.output", result)
```

**关键优势**:
- 跨框架统一:LangChain/LlamaIndex/Semantic Kernel的trace可以在同一平台查看
- 原生支持MCP:通过MCP协议的工具调用自动打上标准span
- 与传统APM集成:可以和HTTP/数据库span在同一火焰图里

## 多 Agent 通信模式

当 Workflow 中有多个 Agent 时,它们如何通信?这是生产系统最容易踩坑的地方。

### 三种通信拓扑

| 通信模式 | 机制 | 适用场景 | 复杂度 | .NET 类比 | 典型框架 |
|---|---|---|---|---|---|
| **共享状态**(Blackboard) | 所有Agent读写同一个State | 2-3个紧耦合Agent | 低 | `ConcurrentDictionary` | LangGraph |
| **消息传递**(Message Bus) | Agent通过消息通信 | 松耦合、需审计日志 | 中 | RabbitMQ / Service Bus | AutoGen v0.5 |
| **层级委托**(Handoff) | 上级分配、下级上报 | 复杂任务分解 | 高 | Hangfire父子Job / Saga | CrewAI / AutoGen v0.4 |

**LangGraph默认采用共享状态(Blackboard)模式**:所有节点读写同一个`AgentState`,天然适合"流水线"场景(A的输出是B的输入)。

**AutoGen v0.5的AgentChat API**是消息传递模式:每个Agent有独立的消息队列,通过发布/订阅通信,天然支持异步和并发。

**CrewAI和OpenAI Agents SDK的Handoffs**支持层级委托:Manager分配任务给Worker,Worker完成后上报,Manager决定下一步。

### 实战案例:LangGraph多Agent协作(共享状态)

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class MultiAgentState(TypedDict):
    messages: Annotated[list, add_messages]
    research_result: str
    code: str
    review_comments: str

# Agent 1: Research Agent
def research_agent(state: MultiAgentState):
    query = state["messages"][-1].content
    result = web_search(query)
    return {"research_result": result}

# Agent 2: Coder Agent(读取research_result)
def coder_agent(state: MultiAgentState):
    spec = state["research_result"]
    code = generate_code(spec)
    return {"code": code}

# Agent 3: Reviewer Agent(读取code)
def reviewer_agent(state: MultiAgentState):
    code = state["code"]
    comments = review(code)
    if "LGTM" in comments:
        return {"review_comments": comments}
    else:
        # 退回给coder重写
        return Command(goto="coder_agent", update={"review_comments": comments})

# 编排
graph = StateGraph(MultiAgentState)
graph.add_node("research", research_agent)
graph.add_node("coder", coder_agent)
graph.add_node("reviewer", reviewer_agent)

graph.add_edge(START, "research")
graph.add_edge("research", "coder")
graph.add_edge("coder", "reviewer")
graph.add_conditional_edges("reviewer", lambda s: "coder" if "LGTM" not in s["review_comments"] else END)

app = graph.compile()
```

**优势**:简单直接,一个State对象串起整条链。  
**劣势**:Agent间紧耦合,State字段多了容易混乱(谁写了什么?谁读了什么?)。

### 实战案例:AutoGen Handoff(层级委托)

```python
from autogen_agentchat.agents import AssistantAgent
from autogen_agentchat.teams import Handoffs

# 定义专家Agent
sql_expert = AssistantAgent(
    name="sql_expert",
    model_client=openai_client,
    system_message="你是SQL专家,只处理数据库查询任务",
    handoffs=[Handoffs(target="manager")]  # 完成后交还给manager
)

python_expert = AssistantAgent(
    name="python_expert",
    model_client=openai_client,
    system_message="你是Python专家,只处理代码生成任务",
    handoffs=[Handoffs(target="manager")]
)

# Manager Agent
manager = AssistantAgent(
    name="manager",
    model_client=openai_client,
    system_message="你是项目经理,根据用户需求委派任务给专家",
    handoffs=[
        Handoffs(target="sql_expert"),
        Handoffs(target="python_expert")
    ]
)

# 运行
team = SelectorGroupChat([manager, sql_expert, python_expert], model_client=openai_client)
result = await team.run(task="生成一个Python脚本,从PostgreSQL读数据并可视化")
```

**Handoff机制**:
1. Manager收到任务,调用特殊工具`transfer_to_sql_expert()`(LLM自动识别需要哪个专家)
2. SQL Expert执行完,调用`transfer_to_manager()`交回控制权
3. Manager再决定是否需要下一个专家

**优势**:专家Agent独立开发和测试,Manager可以动态路由。  
**劣势**:需要LLM准确识别"何时handoff",prompt工程成本高。

### Azure Architecture Center的五种编排模式(2026版)

| 模式 | 描述 | 适用场景 |
|------|------|---------|
| **Sequential**(顺序) | A→B→C线性执行 | 简单流水线,无分支 |
| **Concurrent**(并发) | A/B/C同时跑,聚合结果 | 多角度分析同一输入 |
| **Group Chat**(群聊) | 所有Agent在同一对话里讨论 | 需要"辩论/投票"的决策场景 |
| **Handoff**(委托) | Manager动态分配 | 任务类型多样,需要专家路由 |
| **Magentic**(磁吸) | Agent先做计划,再调工具执行 | 需要"思考→行动"分离的复杂任务 |

**选择建议**:
- 2-3步无分支 → Sequential(用LangGraph或纯函数链)
- 多个独立子任务 → Concurrent(LangGraph的`Send` API或asyncio.gather)
- 需要多Agent"辩论" → Group Chat(AutoGen GroupChat或CrewAI)
- 任务类型动态 → Handoff(AutoGen v0.4或OpenAI Swarm)
- 复杂规划+工具执行 → Magentic(LangGraph + ReAct)

## 工程最佳实践

### 不要过度抽象

> "不要一上来就搞多 Agent 编排，先看一个 augmented LLM 能不能解决问题。" —— Anthropic

这和 .NET 界"不要过早微服务化"的建议一模一样。先单体，有明确需求再拆分。

### 工具描述当 API 文档写

```json
// ❌ 糟糕的工具描述
{ "name": "search", "description": "搜索" }

// ✅ 好的工具描述
{
  "name": "search_codebase",
  "description": "在代码仓库中搜索文件内容。支持正则表达式。返回匹配的文件路径和行号。最多返回50条结果。",
  "inputSchema": {
    "properties": {
      "pattern": { "type": "string", "description": "搜索模式，支持正则表达式" },
      "file_glob": { "type": "string", "description": "文件过滤，如 '*.py'", "default": "*" },
      "max_results": { "type": "integer", "default": 50, "enum": [10, 20, 50, 100] }
    }
  }
}
```

参数尽量用 `enum` 约束——减少 LLM "自由发挥"出错的概率。

### 错误处理三板斧

```python
# 1. max_iterations 防无限循环
MAX_ITERATIONS = 5

# 2. 超时控制
result = await asyncio.wait_for(agent.run(task), timeout=120)

# 3. 异常兜底——不要直接抛异常终止，给 LLM 机会自我修正
try:
    result = await tool.execute(args)
except Exception as e:
    result = f"工具执行失败: {e}. 请尝试其他方法。"
```

> [!tip] C# 类比
> `CancellationToken` + `try-catch` + Polly 重试。

### 成本控制策略

| 策略 | 实现 | 节省比例 |
|---|---|---|
| 路由用小模型 | GPT-4o-mini 做分类，Opus 做推理 | 50-70% |
| 缓存常见查询 | 语义相似度匹配历史结果 | 30-50% |
| 限制上下文长度 | 摘要压缩历史消息 | 20-40% |
| 早停机制 | 置信度达标就停止迭代 | 视场景而定 |

### 渐进式路径

```
Step 1: 单 LLM + 工具调用（不需要 Workflow 框架）
    ↓
Step 2: Prompt Chaining（2-3 步顺序流水线）
    ↓
Step 3: Routing（输入分类 + 专业化处理）
    ↓
Step 4: ReAct 循环（LangGraph 单 Agent + 循环）
    ↓
Step 5: Orchestrator-Workers（多 Agent 协作）
    ↓
Step 6: 完整系统（Human-in-the-Loop + 持久化 + 监控）
```

每一步都要确认当前步骤真的不够用了,再往下走。过早复杂化是 Agent 开发的第一大坑。
