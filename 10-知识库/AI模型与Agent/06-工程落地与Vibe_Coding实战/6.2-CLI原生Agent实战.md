# 6.2 CLI原生Agent实战

> 当 IDE 插件还在做"自动补全"的时候，CLI Agent 已经在做"自主编程"了。
> 本篇深入拆解三大 CLI 原生 Agent——Aider、Claude Code、OpenAI Codex CLI——的架构差异、编辑策略与实战工作流。

## 一、为什么是 CLI？

在 [[10-知识库/AI模型与Agent/06-工程落地与Vibe_Coding实战/6.1-终端IDE形态深度对比.md]] 中我们提到 Vibe Coding 的核心是"意图驱动"。但 VS Code 插件（Copilot / Cursor）本质上是 **IDE-first**，Agent 能力受限于编辑器沙箱。CLI Agent 走了另一条路：

- **零 UI 开销**：一个终端窗口 = 整个工作台
- **原生 Shell 集成**：可以直接跑 `dotnet test`、`sqlcmd`、`git diff`
- **管道组合**：Unix 哲学，`aider --message "重构这个类" | tee log.txt`
- **SSH 友好**：远程服务器上直接 pair programming，无需 Remote Desktop

如果你是 .NET 老兵，可以这样理解：IDE 插件像 SSMS 的图形化查询设计器，而 CLI Agent 像 `sqlcmd` + 存储过程——更底层、更可控、更适合自动化。

## 二、Aider：社区王者

### 2.1 核心数据

| 指标 | 数值 |
|------|------|
| 总安装量 | **5.7M+** |
| 周 Token 消耗 | **15B tokens/week** |
| 自写代码率 | **88%**（即 88% 的代码由 LLM 生成，人类只做审核） |
| 支持语言 | **100+ 种**（包括 C#、F#、SQL、XAML 等 .NET 生态全覆盖） |
| 支持模型 | Claude 3.7 Sonnet、DeepSeek R1、GPT-4o、Gemini 等 |

### 2.2 repo-map 架构：SQL Server 执行计划的类比

Aider 最核心的创新是 **repo-map**——在每次对话前，先对整个仓库做一次"索引扫描"，生成一棵 AST（抽象语法树）级别的代码地图。

这就像 SQL Server 的**执行计划（Execution Plan）**：
- SQL Server 在执行查询前，先分析表结构、索引、统计信息，生成最优执行路径
- Aider 在编辑代码前，先分析文件结构、类/函数签名、依赖关系，生成最优的上下文窗口

```
repo-map 工作流：

1. 扫描 → 构建 tree-sitter AST
2. 提取 → 类名、方法签名、import 关系
3. 排序 → PageRank 算法按"相关性"排序
4. 裁剪 → 只把最相关的签名塞入 context window
5. 发送 → LLM 看到的是"精简版全局视图"
```

**优势**：即使仓库有 10 万行代码，context window 里可能只有 2000 行签名摘要，但 LLM 已经"看到了全局"。这是 Aider 能在大型 .NET 解决方案（几十个 csproj）上工作的关键。

### 2.3 编辑格式三选一

Aider 支持三种编辑格式，适配不同模型的能力：

| 格式 | 原理 | 适用场景 | .NET 类比 |
|------|------|----------|-----------|
| **diff** | 搜索/替换块 | Claude 系列，精准度高 | `git diff` 补丁 |
| **whole** | 输出完整文件 | 小文件、弱模型 | `File.WriteAllText()` |
| **udiff** | 统一差异格式 | GPT-4o，兼顾精准和效率 | `patch -p1 < fix.udiff` |

实战建议：
- C# 大文件（500+ 行）：用 `diff` 格式，避免 whole 模式下 token 爆炸
- 新建文件：自动切 `whole` 格式
- 混合使用 `--edit-format` 参数手动指定

### 2.4 Git 深度集成

Aider 每次编辑自动创建 git commit，commit message 由 LLM 生成。这意味着：

```bash
# 每一步都可回滚
git log --oneline
# a1b2c3d aider: 重构 UserService.cs，提取 IUserRepository 接口
# d4e5f6g aider: 添加单元测试 UserServiceTests.cs
# h7i8j9k aider: 修复 NullReferenceException in GetUserById

# 不满意？一键回退
git revert HEAD
```

这在 .NET 企业项目里极其重要——每个 AI 改动都有 **audit trail**。

### 2.5 实战：用 Aider 重构一个 .NET 8 Web API

```bash
# 安装
pip install aider-chat

# 进入项目目录
cd ~/src/MyWebApi

# 启动（指定模型）
aider --model claude-3.7-sonnet

# 对话式编程
> 把 UserController 里的业务逻辑提取到 UserService，注入 IUserRepository
> 同时生成对应的 xUnit 测试
> 确保所有现有测试仍然通过

# Aider 会：
# 1. 读取 repo-map，理解项目结构
# 2. 修改 UserController.cs
# 3. 创建 UserService.cs + IUserRepository.cs
# 4. 创建 UserServiceTests.cs
# 5. 运行 dotnet test 验证
# 6. 自动 git commit
```

## 三、Claude Code：Anthropic 官方 CLI Agent

### 3.1 定位与设计理念

Claude Code 是 Anthropic 在 2025 年推出的 CLI Agent，核心理念是 **agentic coding**——不只是"帮你写代码"，而是"像一个初级开发者一样自主工作"。

关键特性：
- **Extended Thinking**：在复杂任务时，Claude 会先进行长链推理（类似 Chain-of-Thought），然后再开始编码
- **原生 MCP 支持**：通过 [[10-知识库/AI模型与Agent/03-工具调用与上下文协议/3.2-Model_Context_Protocol规范解析.md]] 连接外部工具（数据库、API、文件系统）
- **Full-context 架构**：不做 repo-map 裁剪，而是把尽可能多的代码直接塞入 200K context window

### 3.2 Full-context vs repo-map

| 维度 | Aider (repo-map) | Claude Code (full-context) |
|------|-------------------|---------------------------|
| 上下文策略 | AST 摘要 + 按需加载 | 尽量全量加载 |
| Token 消耗 | 低（签名级别） | 高（完整代码） |
| 适合项目规模 | 大型 monorepo | 中小型项目（< 100K 行） |
| 精准度 | 依赖 repo-map 质量 | 直接看源码，理解更深 |
| .NET 类比 | 覆盖索引（Covering Index） | 全表扫描（Table Scan） |

Full-context 的哲学很简单：**给模型看越多代码，它就理解得越好**。200K context window 能装大约 15 万行代码，对中型 .NET 项目已经足够。

### 3.3 Extended Thinking 的工程价值

当你给 Claude Code 一个复杂任务（比如"把这个 WCF 服务迁移到 gRPC"），它不会立刻开始写代码，而是：

1. **分析阶段**（Extended Thinking）：梳理依赖、识别风险、制定迁移计划
2. **执行阶段**：按计划逐步修改代码
3. **验证阶段**：运行测试、检查编译

这类似于资深 DBA 在做数据库迁移前，先写一份详细的迁移方案，而不是直接 `ALTER TABLE`。

### 3.4 MCP 集成实战

Claude Code 可以通过 MCP 协议连接你的 SQL Server：

```json
// .claude/mcp.json
{
  "servers": {
    "sqlserver": {
      "command": "mcp-server-mssql",
      "args": ["--connection-string", "Server=localhost;Database=MyApp;Trusted_Connection=true"]
    }
  }
}
```

然后你可以说："查看 Users 表结构，给 UserRepository 生成 CRUD 方法"，Claude Code 会 **先查询数据库元数据，再生成代码**。详见 [[10-知识库/AI模型与Agent/03-工具调用与上下文协议/3.2-Model_Context_Protocol规范解析.md]]。

### 3.5 底层架构揭秘（Tengu Architecture）

2026 年 3 月源码泄露揭示了 Claude Code 代号为 **"Tengu"（天狗）** 的底层架构：

**技术栈**：运行时采用 **Bun**（确保 CLI 交互无延迟），UI 引擎用 **React + Ink**（终端中的组件化开发，支持动态进度条和实时刷新）。

**四层架构模型**：

| 层级 | 职责 |
|---|---|
| 协议层 (Protocol) | 标准化数据交换（深度集成 MCP） |
| 调度层 (Coordinator) | 任务编排中心，拆解任务并启动 Sub-agents 并行协作 |
| 工具层 (Tooling) | 40+ 核心工具，具备严密的权限过滤机制 |
| 持久层 (Persistence) | 通过 `CLAUDE.md` 与 `MEMORY.md` 构建长期记忆 |

**创新设计点**：

1. **原子级影子工作区 (Snapshot System)**：修改代码前自动生成文件快照，比 Git 更轻量的"一键撤销"，防止 AI 破坏源码
2. **自动语义压缩 (Auto-compaction)**：监控上下文窗口，自动触发轻量级模型对历史输出进行摘要提取，解决 Token 爆炸问题
3. **XML 驱动的结构化通信**：底层全面采用 XML 标签（`<thought>`、`<call>`），利用 Claude 模型对 XML 的高识别力，大幅提升指令准确率
4. **KAIROS 异步长程任务模式**：支持后台执行耗时操作，不阻塞主交互循环

## 四、OpenAI Codex CLI：沙箱执行的安全哲学

### 4.1 核心特点

Codex CLI 是 OpenAI 在 2025 年推出的开源 CLI Agent，最大特色是 **沙箱执行**：

- 所有代码修改在隔离环境中运行
- 支持 GPT-4o / o3 / o4-mini 模型
- **多模态输入**：可以截图贴入终端，让它"看着 UI 写代码" [待验证]
- 完全开源（Apache 2.0）

### 4.2 沙箱架构

```
┌─────────────────────────────────┐
│         Codex CLI 主进程         │
│  ┌────────────────────────────┐ │
│  │     Sandbox Container      │ │
│  │  - 网络隔离（默认）         │ │
│  │  - 文件系统快照             │ │
│  │  - 执行 → 检查 → 提交      │ │
│  └────────────────────────────┘ │
│         ↕ 审批门控              │
│  ┌────────────────────────────┐ │
│  │     Host 文件系统           │ │
│  └────────────────────────────┘ │
└─────────────────────────────────┘
```

三种运行模式：
- **suggest**（默认）：只建议，不执行
- **auto-edit**：自动编辑文件，但命令需审批
- **full-auto**：完全自主（需显式开启，配合沙箱使用）

这像 SQL Server 的**事务隔离级别**：suggest = READ UNCOMMITTED（只看不改），auto-edit = READ COMMITTED（改了但要确认），full-auto = SERIALIZABLE（完全托管）。

### 4.3 与 Aider / Claude Code 的差异

Codex CLI 不做 repo-map，也不做 full-context 堆料。它更像一个 **task runner**：
1. 接收任务描述
2. 在沙箱中执行一系列 shell 命令 + 代码编辑
3. 把结果呈现给用户审批

优势在安全性和可审计性，劣势在对大型代码库的全局理解较弱。

## 五、三剑客对比总览

| 维度 | Aider | Claude Code | Codex CLI |
|------|-------|-------------|-----------|
| **架构** | repo-map (AST) | full-context (200K) | sandbox (隔离执行) |
| **编辑格式** | diff / whole / udiff | streaming diff | patch-based |
| **Git 集成** | 自动 commit | 自动 commit | 手动 commit |
| **模型支持** | 多模型路由 | 仅 Claude 系列 | 仅 OpenAI 系列 |
| **MCP 支持** | 无原生支持 | 原生支持 | 无原生支持 [待验证] |
| **开源** | 是 (Apache 2.0) | 否 | 是 (Apache 2.0) |
| **安全模型** | 信任用户 | 信任用户 | 沙箱隔离 |
| **适合场景** | 大型 monorepo | 中型项目 + 工具链 | 安全敏感环境 |
| **.NET 类比** | 执行计划 + 索引 | 全表扫描 | 事务沙箱 |

## 六、实战工作流建议

### 6.1 日常开发（中小项目）

```bash
# Claude Code 最省心
claude "添加一个 HealthCheck endpoint，检查数据库连接和 Redis 可用性"
```

### 6.2 大型遗留代码重构

```bash
# Aider 的 repo-map 在大型项目上优势明显
aider --model claude-3.7-sonnet --map-tokens 4096
> 把所有 Repository 类从直接 SQL 迁移到 Entity Framework Core
> 一次只改一个 Repository，改完跑测试
```

### 6.3 CI/CD 自动化修复

```bash
# Codex CLI 的沙箱特性适合 CI 环境
codex --mode full-auto "修复这个 failing test" --sandbox
```

### 6.4 模型路由策略

Aider 独有的模型路由能力值得一提：

```yaml
# .aider.model.settings.yml
- name: "编辑模式"
  main-model: claude-3.7-sonnet   # 负责代码编辑
  editor-model: deepseek-r1       # 负责 diff 生成（便宜）
  
- name: "审查模式"  
  main-model: gpt-4o              # 负责 code review
```

这类似于 SQL Server 的**读写分离**：写操作用强模型，读操作用便宜模型。

## 七、选型决策树

```
你的项目有多大？
├── < 5万行 → Claude Code（全量上下文，理解最深）
├── 5-50万行 → Aider（repo-map 必须，否则 context 爆炸）
└── 任意规模但安全要求高 → Codex CLI（沙箱隔离）

你需要 MCP 工具链吗？
├── 是 → Claude Code（原生支持）
└── 否 → Aider 或 Codex CLI

你的团队用什么模型？
├── Claude → Claude Code 或 Aider
├── GPT → Codex CLI 或 Aider
├── 混合 → Aider（多模型路由）
└── 开源模型 → Aider（支持 DeepSeek R1 等）
```
