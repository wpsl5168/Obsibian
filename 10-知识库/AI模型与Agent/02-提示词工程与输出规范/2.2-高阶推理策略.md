# 高阶推理策略

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。

## 核心概念

高阶推理策略就是让 LLM "想清楚再说话"的各种套路。如果说基础 Prompt 是 `Console.WriteLine("答案")`，**高阶推理就是在输出前先跑一遍 `Debug.Assert()` + 单元测试 + 代码审查**。

2025-2026 年推理能力已经成为 LLM 竞争的核心赛道：
- OpenAI 的 **o1 / o3 / o4-mini** 系列——原生推理模型，内置 Chain of Thought
- Google 的 **Gemini 2.5 Pro / Flash**——"Thinking" 模式，支持可配置的思考预算
- Anthropic 的 **Claude 3.5/4 系列**——Extended Thinking 模式，思考 token 可达 128K
- DeepSeek 的 **DeepSeek-R1**——开源推理模型标杆

## 关键机制与原理解析

### 1. Chain of Thought（CoT，思维链）

最经典的推理策略。核心思路：**让模型把中间推理步骤写出来，而不是直接蹦答案**。

```csharp
// 类比：就像 SQL Server 的 Execution Plan
// 不只要查询结果，还要看查询计划——知道它是怎么"想"的

// 差的 prompt（直接要答案）
"这个 LINQ 查询的时间复杂度是多少？"
// → 模型直接猜：O(n)（可能猜错）

// 好的 prompt（CoT）
"分析这个 LINQ 查询的时间复杂度。请分步骤思考：
1. 先识别每个 LINQ 操作符的底层实现
2. 分析每个操作符的时间复杂度
3. 组合计算总体复杂度
4. 给出最终答案"
// → 模型逐步推理，准确率大幅提升
```

**CoT 的三种用法**：
- **Zero-shot CoT**：直接加 "Let's think step by step"（简单但有效）
- **Few-shot CoT**：给出带推理过程的示例，让模型模仿
- **Auto-CoT**：让模型自己决定何时、如何展开推理

### 2. 原生推理模型（Reasoning Models, 2025-2026 重点）

这是 2025 年最大的范式转变——**推理不再靠提示词"骗"出来，而是模型训练时就内化了**。

#### OpenAI o 系列

```json
// o3 / o4-mini 使用方式
{
  "model": "o3",
  "reasoning": {
    "effort": "high"  // low / medium / high
  },
  "messages": [
    {"role": "developer", "content": "你是 .NET 性能优化专家"},
    {"role": "user", "content": "分析这段代码为什么在高并发下 GC 压力大"}
  ]
}
```

关键特点：
- **`reasoning.effort`**：控制"思考深度"——`low` 快而浅，`high` 慢而深。类比 SQL Server 的 `OPTIMIZE FOR` hint
- **不需要手写 CoT**：模型自动在内部展开推理链（你看不到中间过程）
- **Streaming 支持**：o3/o4-mini 支持 `reasoning.summary` 参数，可以在流式输出中获取推理摘要
- **o4-mini**：2025年4月发布，成本仅为 o3 的约 1/3，在 STEM 任务上接近 o3 水平

#### Claude Extended Thinking

```python
# Claude 的扩展思考模式
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=16000,
    thinking={
        "type": "enabled",
        "budget_tokens": 10000  # 分配给"思考"的 token 预算
    },
    messages=[{"role": "user", "content": "设计一个高并发消息队列的 C# 实现方案"}]
)

# 响应中包含思考过程（可见！）
for block in response.content:
    if block.type == "thinking":
        print(f"思考过程: {block.thinking}")  # 能看到推理链
    elif block.type == "text":
        print(f"最终回答: {block.text}")
```

**Claude vs OpenAI 推理的关键区别**：
- Claude 的思考过程**对开发者可见**（透明）；OpenAI o 系列的推理过程**不可见**（黑箱，仅有摘要）
- Claude 的思考预算由开发者显式控制；OpenAI 用 `effort` 粗粒度调节
- Claude 支持 thinking + tool_use 联合使用（边想边用工具）

#### Gemini 2.5 Thinking Mode

```python
# Gemini 2.5 Pro/Flash 的思考模式
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="重构这段 C# 代码以提升可测试性",
    config={
        "thinking_config": {
            "thinking_budget": 8192  # 思考 token 预算
            # 设为 0 关闭思考，设为 -1 则由模型自行决定
        }
    }
)
# Gemini 的思考过程也对开发者可见
for part in response.candidates[0].content.parts:
    if part.thought:
        print(f"思考: {part.text}")
```

### 3. Tree of Thoughts（ToT，思维树）

CoT 是单链推理，ToT 是**分叉探索**——类比 `git branch` 的思路：

```
                    问题
                   /    \
              思路A      思路B
             /    \        \
          A1      A2       B1
          ✓       ✗        ✓
        深入A1            深入B1
          |                 |
        最终答案A         最终答案B
              → 选择更优的
```

```csharp
// C# 类比：就像 Parallel.ForEach + 竞争选优
var solutions = await Task.WhenAll(
    ThinkPath_A(problem),  // 分支A
    ThinkPath_B(problem),  // 分支B
    ThinkPath_C(problem)   // 分支C
);
var bestSolution = solutions.OrderByDescending(s => s.Score).First();
```

**实际用法**：目前没有模型原生支持 ToT，通常通过多次 API 调用 + 外部评分函数实现。适合高价值决策场景（架构设计、方案选型）。

### 4. Self-Consistency（自洽性验证）

同一问题让模型回答多次，取多数一致的结果——**投票机制**：

```csharp
// 类比：分布式系统的 Quorum 投票
var results = new List<string>();
for (int i = 0; i < 5; i++)
{
    results.Add(await AskLLM(question, temperature: 0.7));
}
// 多数投票——类似 Raft 共识算法
var finalAnswer = results
    .GroupBy(r => r)
    .OrderByDescending(g => g.Count())
    .First().Key;
```

成本高但准确率能提升 5-15%。适合数学推理、逻辑判断等有明确正确答案的场景。

### 5. Reflection（反思/自我纠错）

让模型审视自己的回答并修正——**Code Review 的 AI 版本**：

```markdown
第一轮：回答问题
第二轮：审视自己的回答——
  "请检查你上面的回答：
   1. 有没有事实错误？
   2. 逻辑是否自洽？
   3. 有没有遗漏重要方面？
   4. 代码示例是否能编译通过？
   如果发现问题，给出修正版。"
```

Anthropic 和 OpenAI 的官方文档都推荐在 Agent 工作流中内置 Reflection 环节。

### 6. Reasoning Effort 调优策略（2025-2026 新课题）

原生推理模型引入了"推理成本"的概念——想得越多越贵。**关键问题：什么时候该深度推理，什么时候该快速回答？**

```
场景分级策略（类比 SQL Server 的查询优化器 Hint）：

高 effort（High）：
  - 复杂架构设计决策
  - 多步数学/逻辑推理
  - 安全关键代码审查
  - 涉及多个系统交互的方案

中 effort（Medium）：
  - 一般代码编写
  - 技术方案比较
  - Bug 分析

低 effort（Low）：
  - 简单问答
  - 格式转换
  - 文档翻译
```

**成本对比**（以 OpenAI 为例）：
| 模型 | 输入成本 | 输出成本 | 适用场景 |
|------|---------|---------|---------|
| gpt-4.1 | $2/M | $8/M | 常规任务，不需要推理 |
| o4-mini (low) | $1.1/M | $4.4/M | 轻量推理，性价比之王 |
| o4-mini (high) | $1.1/M | $4.4/M | 中等推理（token消耗更多） |
| o3 (high) | $10/M | $40/M | 重度推理，顶级难题 |

> [!tip] 实战经验
> **先用 o4-mini medium 试水，不行再升 o3 high**——跟数据库调优一个道理：先跑 `STATISTICS IO`，确认是慢查询了再加索引，别上来就 `FORCESEEK`。

### 7. 工具辅助推理（Tool-Augmented Reasoning）

2025-2026 年推理模型开始支持"边想边用工具"：

```
用户：计算我们 SQL Server 数据库中 Orders 表最近30天的P99延迟

推理模型内部过程：
  思考：需要先查看表结构... → 调用 SQL 工具
  思考：需要查看索引情况... → 调用 SQL 工具  
  思考：根据查询计划分析... → 继续推理
  思考：P99 需要用 PERCENTILE_CONT... → 生成最终 SQL
  
输出：[最终分析结果 + 优化建议]
```

Claude 的 Extended Thinking 和 Gemini 2.5 都已支持 Thinking + Tool Use 的交替执行。OpenAI o3 也在 2025 年 4 月加入了对函数调用的完整支持。

### 8. DeepSeek-R1 与开源推理模型生态

2025 年 1 月 DeepSeek 发布 R1，是开源推理模型的里程碑事件：

```
DeepSeek-R1 核心特点：
- 完全开源（MIT 协议），671B MoE 架构
- 推理能力在数学/代码任务上接近 o1 正式版水平
- 训练方法论：GRPO（Group Relative Policy Optimization）—— 
  不依赖人工标注的推理链，通过 RL 自动学习推理策略
- 蒸馏版本：R1-Distill-Qwen-32B / R1-Distill-Llama-70B 等
  可在消费级 GPU 上运行
```

```csharp
// R1 的训练范式类比
// 传统 CoT 训练：人工写好"标准解题过程"，让模型背诵（Supervised Fine-Tuning）
// ← 类比：给实习生一本"操作手册"，照做就行
//
// R1 的 GRPO 训练：只给答案对不对的反馈，让模型自己摸索推理路径
// ← 类比：不给操作手册，只告诉实习生"结果对了奖金翻倍"，自己想办法
//
// 结果：R1 自己"发明"了 CoT、自我纠错、回溯等推理策略
```

**开源推理模型格局（2025-2026）**：
| 模型 | 参数量 | 推理特色 | 适合场景 |
|------|--------|---------|---------|
| DeepSeek-R1 | 671B (MoE) | 完整推理链可见，数学/代码强 | 自部署，隐私敏感场景 |
| R1-Distill-Qwen-32B | 32B | R1 的精华蒸馏版，性价比极高 | 单卡 A100 部署 |
| QwQ-32B | 32B | 阿里的推理模型，中文推理能力突出 | 中文场景首选 |
| Llama-3.3-70B | 70B | Meta 出品，通用推理 | 多语言通用 |

### 9. Reasoning 的"附加税"与何时不该推理

原生推理模型的隐性成本经常被低估：

```
推理模型的"隐形账单"：

o3 (high effort) 处理一个简单问题：
  - 输入 tokens：200（你的问题）
  - 思考 tokens：3000（模型内部推理，不可见但收费！）
  - 输出 tokens：100（最终回答）
  - 实际计费：200 × $10/M + 3000 × $40/M + 100 × $40/M = $0.126
  
同样问题用 gpt-4.1：
  - 输入 tokens：200
  - 输出 tokens：100
  - 实际计费：200 × $2/M + 100 × $8/M = $0.0012
  
差距：100x+ ！！
```

```csharp
// 类比 SQL Server：
// 推理模型 = 每个查询都强制走 OPTION(RECOMPILE) + 全表扫描
// 普通模型 = 走缓存执行计划 + 索引查找
// 
// 不是说 RECOMPILE 不好，而是只有复杂查询才需要
// 简单 SELECT TOP 1 就别 RECOMPILE 了
```

**实用判断原则**：
1. **能用 gpt-4.1-mini 解决的，别上推理模型**——杀鸡别用牛刀
2. **推理模型不擅长的事**：创意写作、简单翻译、格式转换、闲聊
3. **推理模型真正该用的场景**：多步骤数学证明、复杂代码 debug、涉及多条件约束的逻辑推理、需要自我纠错的关键决策
4. **混合路由策略**：用轻量模型做意图分类，决定是否需要推理模型——类似 SQL Server 的 Query Store 监控，只优化慢查询

## 推理策略选型决策树

```
你的任务需要推理吗？
├── 不需要 → 用 GPT-4.1 / Claude Sonnet / Gemini Flash（快且便宜）
└── 需要 →
    ├── 预算充足？
    │   ├── 是 → o3 high / Claude Extended Thinking（效果最佳）
    │   └── 否 → o4-mini medium / Gemini 2.5 Flash Thinking（性价比）
    ├── 需要透明推理链？
    │   ├── 是 → Claude Extended Thinking / Gemini Thinking（可见思考过程）
    │   └── 否 → OpenAI o 系列（黑箱但效果好）
    └── 多步骤复杂任务？
        ├── 是 → Agent + Reflection + Tool Use
        └── 否 → 单次推理调用即可
```
