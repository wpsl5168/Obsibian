# 结构化输出 — 各大模型厂商能力对比

> 📚 上级页面：[[2.3-结构化数据输出]]

### 1. 各大模型的结构化输出能力（2025-2026）

#### OpenAI Structured Outputs（最成熟）

OpenAI 在 2024 年 8 月推出 Structured Outputs，到 2025-2026 年已经是最成熟的方案：

```json
// API 请求示例
{
  "model": "gpt-4.1",
  "messages": [
    {"role": "user", "content": "分析这段 C# 代码的性能问题"}
  ],
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "code_analysis",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {
          "issues": {
            "type": "array",
            "items": {
              "type": "object",
              "properties": {
                "severity": {"type": "string", "enum": ["critical", "warning", "info"]},
                "line_number": {"type": "integer"},
                "description": {"type": "string"},
                "suggestion": {"type": "string"}
              },
              "required": ["severity", "line_number", "description", "suggestion"],
              "additionalProperties": false
            }
          },
          "overall_score": {"type": "integer", "description": "1-10 分"},
          "summary": {"type": "string"}
        },
        "required": ["issues", "overall_score", "summary"],
        "additionalProperties": false
      }
    }
  }
}
```

关键特性：
- **`strict: true`**：开启严格模式后，输出 **100% 符合 JSON Schema**——不是"尽量"，是"保证"
- 底层使用 **Constrained Decoding（约束解码）** 技术，在 token 生成阶段就屏蔽不合法的 token
- 支持 `gpt-4.1`、`gpt-4.1-mini`、`gpt-4.1-nano`、`o3`、`o4-mini` 等全系列模型
- 首次请求某 Schema 时有额外延迟（Schema 编译），后续请求无额外开销

> [!tip] .NET 开发者提示
> `strict: true` 要求 Schema 中所有属性都列入 `required`，且必须设置 `additionalProperties: false`。这跟 C# 的 `record` 类型理念一致——字段全部必填，不允许动态属性。

#### Claude 的结构化输出方案

Anthropic 的 Claude 采用不同的技术路线：

**a) Tool Use（函数调用）方式——推荐**
```python
# Claude 推荐用 Tool Use 来实现结构化输出
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=1024,
    tools=[{
        "name": "code_analysis",
        "description": "输出代码分析结果",
        "input_schema": {
            "type": "object",
            "properties": {
                "issues": {
                    "type": "array",
                    "items": {
                        "type": "object",
                        "properties": {
                            "severity": {"type": "string", "enum": ["critical", "warning", "info"]},
                            "description": {"type": "string"},
                            "suggestion": {"type": "string"}
                        },
                        "required": ["severity", "description", "suggestion"]
                    }
                },
                "overall_score": {"type": "integer"}
            },
            "required": ["issues", "overall_score"]
        }
    }],
    tool_choice={"type": "tool", "name": "code_analysis"},  # 强制使用该工具
    messages=[{"role": "user", "content": "分析这段 C# 代码..."}]
)
# tool_choice 强制模型调用指定工具，输出严格符合 input_schema
```

**b) Prefill + JSON 方式**
```python
# 用 assistant prefill 引导 JSON 输出
messages = [
    {"role": "user", "content": "分析代码，以 JSON 格式输出"},
    {"role": "assistant", "content": "{"}  # 预填充 JSON 开头
]
# 模型会接着 { 继续生成合法 JSON
```

**Claude vs OpenAI 结构化输出对比**：

| 特性 | OpenAI Structured Outputs | Claude Tool Use |
|------|--------------------------|-----------------| | 保证合规率 | 100%（strict 模式） | ~99%+（极少数边界 case） |
| 底层技术 | Constrained Decoding | 训练时强化 + Schema 验证 |
| Schema 定义 | JSON Schema 标准 | JSON Schema（通过 Tool） |
| 嵌套复杂度 | 最多 5 层嵌套深度 + 100 个属性总数 | 无明确层级限制 |
| 首次延迟 | 有（Schema 编译） | 无 |

> [!info] OpenAI 嵌套深度限制详解（2026.01 文档）
> 官方文档规定："A schema may have up to 100 object properties total, with up to 5 levels of nesting"。这里的"5 层嵌套"指的是 JSON Schema **定义层级**，而非**数据路径深度**。例如 `.properties.items.properties.value.anyOf.properties` 这样的路径深度可以超过 5，但 Schema 定义的 `object` → `object` → `object` 嵌套不能超过 5 层。实际使用中，复杂嵌套 Schema 会触发不明确的 "invalid JSON schema" 错误，需逐步简化验证边界。

#### Gemini 的结构化输出

Google Gemini 从 1.5 Pro 开始支持，2.5 系列进一步强化：

```python
import google.generativeai as genai
from pydantic import BaseModel

# 方式一：直接传 JSON Schema
model = genai.GenerativeModel(
    "gemini-2.5-pro",
    generation_config={
        "response_mime_type": "application/json",
        "response_schema": {
            "type": "object",
            "properties": {
                "issues": {"type": "array", "items": {"type": "object"}},
                "score": {"type": "integer"}
            }
        }
    }
)

# 方式二：用 Python Enum/TypedDict 定义（更 Pythonic）
from enum import Enum
class Severity(Enum):
    CRITICAL = "critical"
    WARNING = "warning"
    INFO = "info"
```

Gemini 的特色是支持 `response_mime_type` 设为 `text/x.enum`，让模型只能输出预定义的枚举值——适合分类任务。

**Gemini 结构化输出关键特性（2026.02）**：

- **原生 JSON 模式**：通过 `response_mime_type: "application/json"` + `response_schema` 强制输出符合 Schema 的 JSON
- **Schema 强制执行**：不依赖 Constrained Decoding，而是通过训练时的强化学习让模型学会符合 Schema
- **合规率**：实际测试接近 100%（2026.02 Google 官方博客实测数据），但无 OpenAI 那样的数学保证
- **枚举约束**：`text/x.enum` MIME 类型可强制模型只输出预定义值列表中的一个，适合分类场景
- **Pydantic/TypedDict 支持**：Python SDK 原生支持用 Pydantic 模型或 TypedDict 定义 Schema，自动转为 JSON Schema

#### xAI Grok 的结构化输出（2026.04 新增）

xAI 的 Grok 2.5 系列在 2026 年 4 月加入结构化输出支持：

```python
# Grok API 示例（兼容 OpenAI SDK）
from openai import OpenAI

client = OpenAI(
    api_key="xai-...",
    base_url="https://api.x.ai/v1"
)

response = client.chat.completions.create(
    model="grok-2.5",
    messages=[{"role": "user", "content": "分析这段代码"}],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "code_analysis",
            "strict": True,  # Grok 也支持 strict 模式
            "schema": {
                # ... 同 OpenAI 格式
            }
        }
    }
)
```

**Grok 特点**：
- API 完全兼容 OpenAI SDK（可直接替换 `base_url`）
- 支持 `strict: True` 模式，底层也使用约束解码
- 嵌套深度限制：同 OpenAI（5 层 + 100 属性）
- 独特优势：实时数据访问（X 平台数据），适合需要结合最新信息的结构化提取

#### 各厂商结构化输出能力总览（2026.07）

| 厂商 | 方法 | 合规保证 | Schema 限制 | 流式支持 | 成本影响 |
|------|------|----------|-------------|----------|----------|
| **OpenAI** | `response_format` + `strict: true` | 100%（数学保证） | 5 层 / 100 属性 | ✅ | Schema Token 计入系统提示（~50-2000 Token） |
| **Anthropic** | Tool Use 强制调用 | ~99%+ | 无明确限制 | ✅ | Schema 计入 Tool 定义 |
| **Google** | `response_schema` | ~99%+（实测） | 无明确限制 | ✅ | Schema 计入配置（不额外收费） |
| **xAI** | `response_format`（OpenAI 兼容） | 100%（strict 模式） | 5 层 / 100 属性 | ✅ | 同 OpenAI |
| **DeepSeek** | JSON Mode（提示词引导） | ~95% | 无 | ✅ | 无额外成本，但需提示词优化 |

> [!tip] 成本优化建议
> - **Schema Token 成本**：OpenAI/xAI 的 Schema 会计入系统提示 Token。简单 Schema（3 字段）~50 Token，复杂嵌套 Schema 可达 2000 Token。每次请求都重传。
> - **输出 Token 膨胀**：结构化输出比自然语言多 40-300% Token。例如 `{"sentiment": "positive"}` 比 `"正面"` 多 ~40% Token。
> - **最省方案**：Gemini（Schema 不计费）+ 简化 Schema（只保留必需字段）。

### 2. 工程实战最佳实践

#### 错误处理模式

```python
from openai import OpenAI
import json
from pydantic import BaseModel, ValidationError

class CodeIssue(BaseModel):
    severity: str
    line_number: int
    description: str

def call_with_structured_output(prompt: str, max_retries=3):
    """带重试的结构化输出调用"""
    for attempt in range(max_retries):
        try:
            response = client.chat.completions.create(
                model="gpt-4.1",
                messages=[{"role": "user", "content": prompt}],
                response_format={
                    "type": "json_schema",
                    "json_schema": {
                        "name": "code_analysis",
                        "strict": True,
                        "schema": CodeIssue.model_json_schema()
                    }
                }
            )
            
            # OpenAI strict 模式下这步理论上不会失败，但保险起见仍验证
            data = json.loads(response.choices[0].message.content)
            return CodeIssue(**data)
            
        except ValidationError as e:
            # Pydantic 验证失败（几乎不应该发生）
            if attempt == max_retries - 1:
                raise
            continue
        except json.JSONDecodeError:
            # JSON 解析失败（strict 模式下不应该发生）
            if attempt == max_retries - 1:
                raise ValueError("模型返回非法 JSON，即使在 strict 模式下")
            continue
    
    raise RuntimeError("结构化输出调用失败")
```

#### Schema 设计原则

**✅ 推荐做法**：

```json
{
  "type": "object",
  "properties": {
    "status": {
      "type": "string",
      "enum": ["success", "warning", "error"],
      "description": "任务执行状态"
    },
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "id": {"type": "integer"},
          "name": {"type": "string", "minLength": 1, "maxLength": 100}
        },
        "required": ["id", "name"],
        "additionalProperties": false
      },
      "minItems": 1,
      "maxItems": 50
    }
  },
  "required": ["status", "items"],
  "additionalProperties": false
}
```

**关键设计要点**：
1. **必填字段**：所有重要字段列入 `required`（OpenAI strict 模式强制要求）
2. **禁止额外属性**：`additionalProperties: false` 防止模型自由发挥
3. **枚举值**：用 `enum` 限定分类字段（比提示词描述更可靠）
4. **边界约束**：`minLength/maxLength`、`minItems/maxItems` 防止极端输出
5. **描述字段**：`description` 帮助模型理解字段语义（计入 Schema Token）

**❌ 反模式**：

```json
{
  "type": "object",
  "properties": {
    "result": {"type": "string"},  // ❌ 太宽泛，没有约束
    "metadata": {"type": "object"}  // ❌ 嵌套对象没有定义属性
  }
  // ❌ 没有 required 和 additionalProperties: false
}
```

#### 复杂嵌套 Schema 拆分策略

当业务需要超过 5 层嵌套时（OpenAI/xAI 限制），使用**扁平化 + 引用 ID** 模式：

**❌ 超深嵌套（触发限制）**：
```json
{
  "company": {
    "departments": [{
      "teams": [{
        "members": [{
          "tasks": [{
            "subtasks": [...]  // 第 6 层，违规
          }]
        }]
      }]
    }]
  }
}
```

**✅ 扁平化重构**：
```json
{
  "companies": [{"id": 1, "name": "Acme"}],
  "departments": [{"id": 10, "company_id": 1, "name": "Engineering"}],
  "teams": [{"id": 100, "department_id": 10, "name": "Backend"}],
  "members": [{"id": 1000, "team_id": 100, "name": "Alice"}],
  "tasks": [{"id": 10000, "member_id": 1000, "title": "Fix bug"}]
}
```

这种关系型设计模式（类比 SQL 表结构）可以表达任意深度的层级关系，且永远不超过 2 层嵌套。

### 3. 性能与成本对比（2026.07 实测）

#### Token 消耗对比

| 任务 | 自然语言输出 | 结构化输出 | Token 膨胀率 |
|------|--------------|------------|--------------|
| 情感分类（单条） | `"正面"` (2 Token) | `{"sentiment": "positive"}` (7 Token) | +250% |
| 代码审查（5 问题） | ~150 Token | ~420 Token（完整 JSON） | +180% |
| 数据提取（发票） | ~80 Token | ~240 Token（结构化字段） | +200% |

**结论**：结构化输出的 Token 成本通常是自然语言的 **2-3 倍**，但换来的是**零解析成本 + 零错误率**。

#### 延迟对比（单次请求，gpt-4.1）

| Schema 复杂度 | 首次请求延迟 | 后续请求延迟 |
|---------------|--------------|--------------|
| 简单（3 字段） | +120ms（编译） | +0ms |
| 中等（15 字段，2 层嵌套） | +350ms | +0ms |
| 复杂（50 字段，5 层嵌套） | +800ms | +0ms |

**优化建议**：
- 高频 Schema 在应用启动时"预热"（发一次空请求触发编译）
- 同一 Schema 复用，避免动态生成不同的 Schema

### 4. 选型决策树

```
需要 100% 合规保证？
├─ 是 → OpenAI/xAI strict 模式（金融、医疗、法律场景）
└─ 否
   ├─ 需要超深嵌套（>5 层）？
   │  ├─ 是 → Claude Tool Use 或 Gemini（无嵌套限制）
   │  └─ 否
   │     ├─ 成本敏感？
   │     │  ├─ 是 → Gemini（Schema 不计费）
   │     │  └─ 否 → OpenAI（生态最成熟，工具链最全）
   │     └─ 需要实时数据（X 平台）？
   │        └─ 是 → xAI Grok
   └─ 边缘设备/离线场景？
      └─ 开源模型 + Outlines/Guidance 库（本地约束解码）
```
