# 推理模型工程化进阶

> 📚 上级页面：[[2.2-高阶推理策略]]

推理模型不是“更会写 CoT 的聊天模型”，而是允许在最终回答前消耗额外 inference compute 的模型。工程重点不在诱导它输出思维链，而在 **任务路由、计算预算、状态延续、工具循环、评测与降级**。

## 1. 训练与推理：不要混为一谈

现代推理能力通常由预训练、监督微调、可验证奖励/偏好优化共同形成。GRPO、PPO、DPO、Process Reward Model 都是训练侧方法，API 使用方不能通过几个 prompt 参数“开启 GRPO”。生产系统真正能控制的是 test-time compute：模型、effort/budget、上下文、工具、超时和重试。

| 层级 | 可控制项 | 不应假设 |
|---|---|---|
| 训练侧 | 数据、奖励、采样、验证器 | 只靠最终答案奖励就必然学会可靠推理 |
| 模型 API | reasoning effort、thinking mode、输出上限 | effort 是严格 token 上限 |
| 编排侧 | 路由、并行验证、工具循环、状态续接 | 模型自报 confidence 可直接当概率 |
| 业务侧 | SLO、错误成本、人工复核、审计 | 更长思考必然单调提升质量 |

**关键边界**：隐藏/摘要化 thinking 不是审计证据。审计应记录输入、外部证据、工具调用、最终结论和策略版本，不依赖内部思维链。

## 2. 2026 API 控制面

| 供应商形态 | 深度控制 | 多轮/工具状态 | 工程注意点 |
|---|---|---|---|
| OpenAI Responses | `reasoning.effort` | 优先 `previous_response_id` 或回传完整 response items | 复杂 tool loop 不宜退回无状态 Chat Completions |
| Anthropic adaptive thinking | `thinking: adaptive` + `output_config.effort` | 保留 API 要求的 thinking/tool blocks | 新模型优先 adaptive；旧 manual budget 迁移时会影响 cache |
| Anthropic manual thinking | `budget_tokens`，最低 1,024 | interleaved thinking 受模型与 API 限制 | budget 是目标，不是严格消耗；通常须小于 `max_tokens` |
| 普通低延迟模型 | 无显式推理预算 | 常规消息历史 | 适合明确、可模板化、低风险任务 |

不要把供应商参数抽象成一个虚假的统一 `thinking_steps`。统一层应暴露业务语义，例如 `fast / balanced / deep`，然后按 provider 映射，并保留 capability probe。

## 3. 决策树：什么时候升级推理

```text
请求进入
├─ 仅格式转换、抽取、翻译、模板填充？ → 普通模型 + 结构化输出
├─ 有确定性算法/SQL/规则可解？ → 先用代码，不用 LLM 猜
├─ 多约束、信息冲突、跨文档归纳？ → balanced reasoning
├─ 高错误成本（资金/权限/数据删除/合规）？
│  ├─ 有外部验证器 → deep reasoning + verifier
│  └─ 无验证器 → deep reasoning + 人工审批
└─ 工具链超过 3 步或会动态改计划？ → reasoning planner + 低成本 executor
```

路由依据必须来自可观测信号：任务类型、约束数量、工具数量、历史失败、风险等级。不要让模型仅凭一句“这很难”自行无限升级预算。

## 4. 生产示例一：OpenAI Responses 的状态化工具循环

下面的骨架强调三件事：显式 effort、保存 response id、对超时和未完成状态做分流。工具 schema 与执行器略去，但状态续接方式保留。

```python
from __future__ import annotations
import os
from openai import OpenAI, APITimeoutError, APIConnectionError

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"], timeout=45.0)

def plan_change(request: str, previous_response_id: str | None = None):
    kwargs = {
        "model": os.getenv("REASONING_MODEL", "gpt-5.6"),
        "input": request,
        "reasoning": {"effort": "medium"},
        "store": True,
        "max_output_tokens": 4000,
    }
    if previous_response_id:
        kwargs["previous_response_id"] = previous_response_id

    try:
        response = client.responses.create(**kwargs)
    except (APITimeoutError, APIConnectionError) as exc:
        raise RuntimeError("reasoning upstream unavailable") from exc

    if response.status != "completed":
        reason = getattr(response.incomplete_details, "reason", "unknown")
        raise RuntimeError(f"incomplete response: {reason}")

    return {
        "response_id": response.id,
        "text": response.output_text,
        "usage": response.usage,
    }
```

在真实 agent loop 中，工具结果应通过同一 response/conversation 链续接。OpenAI 官方说明：复杂 function calling 若丢掉相邻 reasoning items，模型可能重新推理，增加 token 且降低工具调用表现。

## 5. 生产示例二：Anthropic adaptive/manual 双栈

新模型优先 adaptive thinking；只有需要固定成本窗口、且模型仍支持 manual mode 时才使用 `budget_tokens`。

```python
from __future__ import annotations
import os
from anthropic import Anthropic, APIError

client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"], timeout=60.0)

def review_architecture(requirements: str, adaptive: bool = True):
    common = {
        "model": os.getenv("CLAUDE_MODEL", "claude-sonnet-4-6"),
        "max_tokens": 8000,
        "messages": [{"role": "user", "content": requirements}],
    }
    if adaptive:
        common["thinking"] = {"type": "adaptive"}
        common["output_config"] = {"effort": "high"}
    else:
        # 仅供仍支持 manual extended thinking 的模型；>=1024 且通常 < max_tokens
        common["thinking"] = {"type": "enabled", "budget_tokens": 4000}

    try:
        message = client.messages.create(**common)
    except APIError as exc:
        raise RuntimeError(f"Claude request failed: {exc.status_code}") from exc

    text = "\n".join(
        block.text for block in message.content if block.type == "text"
    )
    if not text:
        raise RuntimeError("no final text block")
    return text, message.usage
```

Manual mode 的 `budget_tokens` 是目标值，实际可提前结束；改变预算会使相关 prompt cache breakpoint 失效。需要工具间再思考时，必须同时核对模型、Messages API 和 interleaved-thinking 支持，不能只看请求是否返回 200。

## 6. Planner / Executor / Verifier 分层

把所有步骤都交给最贵的推理模型通常不是最优解。

```text
Planner（推理模型）
  输入：目标、约束、可用工具、风险等级
  输出：有依赖关系的计划 + 每步验收条件
        ↓
Executor（普通模型/确定性程序，可并行）
  输出：文件、查询结果、API 响应、测试日志
        ↓
Verifier（规则引擎/测试/第二模型）
  输出：通过、可重试错误、需重规划错误、需人工审批
```

实现时应限制：最大规划轮次、最大工具调用数、单工具超时、总成本、不可逆操作审批。Verifier 优先选择确定性机制，例如 JSON Schema、编译、单元测试、SQL 约束和 checksum；LLM-as-a-judge 只用于无法规则化的语义质量，并要用人工标注集校准。

## 7. 预算与 SLO：用数据调，不用“80/15/5”经验比例

对每个任务族建立 eval set，至少记录：

- `success_rate`：业务验收通过率，而非模型自评。
- `p50/p95_latency`：含工具调用，不只模型首 token。
- `input/output/reasoning tokens`：供应商提供什么就记什么。
- `cost_per_success`：总成本 / 成功任务数，比单次请求价格更有意义。
- `retry_rate`、`human_escalation_rate`、`unsafe_action_rate`。

离线调参流程：固定模型与 prompt，对 `low/medium/high` 做同一批样本；计算 Wilson 区间或 bootstrap 置信区间；只有准确率收益覆盖延迟/成本损失时才升级默认 effort。线上先灰度 5%—10%，设置成本和错误率熔断，不根据少量成功案例全量切换。

## 8. 常见错误与最便宜验证

| 症状 | 先查因素 | 最便宜验证 |
|---|---|---|
| 开高 effort 仍答错 | 缺证据、问题不可判定、工具结果错 | 给标准答案集做 20 条 A/B，而非继续加 prompt |
| tool loop 重复调用 | 状态未续接、结果缺 id、工具描述含糊 | 记录完整 item sequence，重放单个失败 case |
| 延迟突然升高 | effort、输出上限、缓存失效、工具慢 | 分离模型耗时与工具耗时，比较 cache hit |
| 成本暴涨 | 重试叠加、历史重复注入、无总预算 | 按 request id 聚合 token 与重试次数 |
| thinking 配置 200 但无效果 | 模型不支持、partner 平台忽略 header | 对照 capability 文档并比较 usage 字段 |

## 9. 上线检查清单

- [ ] 路由规则可解释、可回滚，默认不是最高 effort。
- [ ] 每个 task family 有固定 eval set 和成功判据。
- [ ] 多轮工具调用保留供应商要求的状态对象。
- [ ] 有总 token、总时长、最大轮次和最大重试预算。
- [ ] 不可逆操作经过 policy gate；模型没有最终授权权。
- [ ] 日志不保存敏感 thinking 内容，只保存必要证据与操作链。
- [ ] provider/model capability 由探针验证，不靠模型名推断。
