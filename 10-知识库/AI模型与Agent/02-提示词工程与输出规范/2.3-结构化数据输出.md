# 结构化数据输出

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。

## 核心概念

结构化输出（Structured Output）就是让 LLM 不再"自由发挥"，而是严格按照预定义的 Schema 输出 JSON、XML 等机器可解析的数据格式。如果把 LLM 比作一个 C# 方法，**普通对话是返回 `string`，结构化输出是返回强类型的 `T`——编译期就能检查格式对不对**。

```csharp
// 类比理解
// 弱类型输出（传统对话）
string response = await llm.ChatAsync("分析这段代码");  
// 返回自由文本，你得自己 regex 解析

// 强类型输出（结构化）
CodeAnalysis result = await llm.ChatAsync<CodeAnalysis>("分析这段代码");
// 直接反序列化为对象，字段有保障
```

### 为什么需要结构化输出？

在 Agent 工作流和企业集成场景中，LLM 的输出经常要喂给下游系统——写入数据库、调用 API、触发工作流。**非结构化的自由文本是管线中最脆弱的环节**，就像 SQL Server 里用 `NVARCHAR(MAX)` 存 JSON 但没有 Schema 约束，迟早出事。

核心需求：
- **可靠性**：每次输出都能 `JsonSerializer.Deserialize<T>()` 成功
- **一致性**：同类任务的输出格式完全相同，不会今天多个字段明天少个字段
- **可组合性**：输出可以直接作为下一步工具调用或 API 请求的参数

## 关键机制与原理解析

### 1. 各大模型的结构化输出能力（2025-2026）

#### OpenAI Structured Outputs（最成熟）

OpenAI 在 2024 年 8 月推出 Structured Outputs，到 2025-2026 年已经是最成熟的方案：

```json
// API 请求示例
{
  "model": "gpt-4.1",
  "messages": [
    {"role": "user", "content": "分析这段 C# 代码的性能问题"}
  ],
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "code_analysis",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {
          "issues": {
            "type": "array",
            "items": {
              "type": "object",
              "properties": {
                "severity": {"type": "string", "enum": ["critical", "warning", "info"]},
                "line_number": {"type": "integer"},
                "description": {"type": "string"},
                "suggestion": {"type": "string"}
              },
              "required": ["severity", "line_number", "description", "suggestion"],
              "additionalProperties": false
            }
          },
          "overall_score": {"type": "integer", "description": "1-10 分"},
          "summary": {"type": "string"}
        },
        "required": ["issues", "overall_score", "summary"],
        "additionalProperties": false
      }
    }
  }
}
```

关键特性：
- **`strict: true`**：开启严格模式后，输出 **100% 符合 JSON Schema**——不是"尽量"，是"保证"
- 底层使用 **Constrained Decoding（约束解码）** 技术，在 token 生成阶段就屏蔽不合法的 token
- 支持 `gpt-4.1`、`gpt-4.1-mini`、`gpt-4.1-nano`、`o3`、`o4-mini` 等全系列模型
- 首次请求某 Schema 时有额外延迟（Schema 编译），后续请求无额外开销

> [!tip] .NET 开发者提示
> `strict: true` 要求 Schema 中所有属性都列入 `required`，且必须设置 `additionalProperties: false`。这跟 C# 的 `record` 类型理念一致——字段全部必填，不允许动态属性。

#### Claude 的结构化输出方案

Anthropic 的 Claude 采用不同的技术路线：

**a) Tool Use（函数调用）方式——推荐**
```python
# Claude 推荐用 Tool Use 来实现结构化输出
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=1024,
    tools=[{
        "name": "code_analysis",
        "description": "输出代码分析结果",
        "input_schema": {
            "type": "object",
            "properties": {
                "issues": {
                    "type": "array",
                    "items": {
                        "type": "object",
                        "properties": {
                            "severity": {"type": "string", "enum": ["critical", "warning", "info"]},
                            "description": {"type": "string"},
                            "suggestion": {"type": "string"}
                        },
                        "required": ["severity", "description", "suggestion"]
                    }
                },
                "overall_score": {"type": "integer"}
            },
            "required": ["issues", "overall_score"]
        }
    }],
    tool_choice={"type": "tool", "name": "code_analysis"},  # 强制使用该工具
    messages=[{"role": "user", "content": "分析这段 C# 代码..."}]
)
# tool_choice 强制模型调用指定工具，输出严格符合 input_schema
```

**b) Prefill + JSON 方式**
```python
# 用 assistant prefill 引导 JSON 输出
messages = [
    {"role": "user", "content": "分析代码，以 JSON 格式输出"},
    {"role": "assistant", "content": "{"}  # 预填充 JSON 开头
]
# 模型会接着 { 继续生成合法 JSON
```

**Claude vs OpenAI 结构化输出对比**：

| 特性 | OpenAI Structured Outputs | Claude Tool Use |
|------|--------------------------|-----------------|
| 保证合规率 | 100%（strict 模式） | ~99%+（极少数边界 case） |
| 底层技术 | Constrained Decoding | 训练时强化 + Schema 验证 |
| Schema 定义 | JSON Schema 标准 | JSON Schema（通过 Tool） |
| 嵌套复杂度 | 支持最多 5 层嵌套 [待验证] | 无明确层级限制 |
| 首次延迟 | 有（Schema 编译） | 无 |

#### Gemini 的结构化输出

Google Gemini 从 1.5 Pro 开始支持，2.5 系列进一步强化：

```python
import google.generativeai as genai
from pydantic import BaseModel

# 方式一：直接传 JSON Schema
model = genai.GenerativeModel(
    "gemini-2.5-pro",
    generation_config={
        "response_mime_type": "application/json",
        "response_schema": {
            "type": "object",
            "properties": {
                "issues": {"type": "array", "items": {"type": "object"}},
                "score": {"type": "integer"}
            }
        }
    }
)

# 方式二：用 Python Enum/TypedDict 定义（更 Pythonic）
from enum import Enum
class Severity(Enum):
    CRITICAL = "critical"
    WARNING = "warning"
    INFO = "info"
```

Gemini 的特色是支持 `response_mime_type` 设为 `text/x.enum`，让模型只能输出预定义的枚举值——适合分类任务。

### 2. Constrained Decoding（约束解码）——底层原理

结构化输出的技术核心是约束解码。理解它需要知道 LLM 的生成过程：

```
LLM 每次生成一个 token → 从词表中选概率最高的

约束解码的做法：
  生成每个 token 时，根据当前 JSON Schema 状态，
  把不合法的 token 概率设为 -∞（mask 掉）

例子：已输出 {"severity": " → 下一个 token 只能是 "critical"/"warning"/"info" 之一
```

```csharp
// 类比：就像 SQL Server 的 CHECK CONSTRAINT
// ALTER TABLE Issues ADD CONSTRAINT CK_Severity 
//     CHECK (Severity IN ('critical', 'warning', 'info'));
// 数据库在 INSERT 时就拒绝非法值，而不是事后检查

// 约束解码 = 在"生成时"就拒绝非法 token
// 传统 prompt 方式 = 生成后再 try-catch 解析（不可靠）
```

**开源约束解码方案**：
- **Outlines**（Python）：最流行的开源实现，支持 JSON Schema、正则表达式约束
- **Guidance**（微软）：与 Semantic Kernel 集成好，支持多种约束模式
- **lm-format-enforcer**：轻量级，支持 HuggingFace Transformers
- **XGrammar**：2025 年新起的高性能方案，被 vLLM/SGLang 等推理框架集成 [待验证]

### 3. Function Calling（函数调用）——结构化输出的"另一扇门"

Function Calling 本质上也是结构化输出——模型输出的是函数名 + 参数 JSON：

```csharp
// OpenAI Function Calling 在 .NET 中的使用
var tools = new List<ChatTool>
{
    ChatTool.CreateFunctionTool(
        name: "query_database",
        description: "执行 SQL 查询",
        parameters: BinaryData.FromObjectAsJson(new
        {
            type = "object",
            properties = new
            {
                sql = new { type = "string", description = "SQL 查询语句" },
                database = new { type = "string", @enum = new[] { "production", "staging" } },
                timeout_seconds = new { type = "integer", @default = 30 }
            },
            required = new[] { "sql", "database" }
        })
    )
};

var response = await client.CompleteChatAsync(messages, new ChatCompletionOptions
{
    Tools = tools,
    ToolChoice = ChatToolChoice.CreateRequiredChoice()  // 强制调用工具
});

// 解析工具调用结果
var toolCall = response.Value.ToolCalls[0];
var args = JsonSerializer.Deserialize<QueryArgs>(toolCall.FunctionArguments);
```

**2025-2026 Function Calling 进展**：
- OpenAI `gpt-4.1` 系列在函数调用准确率上相比 gpt-4o 提升显著，官方声称是 "best function calling model"
- Claude 支持在 Extended Thinking 模式下进行函数调用（边推理边调工具）
- Gemini 2.5 系列支持 Parallel Function Calling（一次返回多个函数调用）
- **MCP（Model Context Protocol）** 正在成为工具调用的标准化协议——详见 [[3.2-Model_Context_Protocol规范解析]]

### 4. Pydantic + AI 框架——Python 生态的类型安全方案

Python 生态中，Pydantic 已经成为定义 LLM 输出 Schema 的事实标准：

```python
from pydantic import BaseModel, Field
from typing import Literal

# 定义输出模型——就像 C# 的 record 类型
class CodeIssue(BaseModel):
    severity: Literal["critical", "warning", "info"]
    line_number: int = Field(ge=1, description="代码行号")
    description: str = Field(max_length=500)
    suggestion: str

class CodeAnalysis(BaseModel):
    issues: list[CodeIssue]
    overall_score: int = Field(ge=1, le=10)
    summary: str

# OpenAI 的 Python SDK 直接支持 Pydantic
from openai import OpenAI
client = OpenAI()

completion = client.beta.chat.completions.parse(
    model="gpt-4.1",
    messages=[{"role": "user", "content": "分析这段代码..."}],
    response_format=CodeAnalysis  # 直接传 Pydantic Model！
)
result: CodeAnalysis = completion.choices[0].message.parsed
# result.issues[0].severity → 类型安全访问
```

**主流 AI 框架的结构化输出支持**：

| 框架 | 语言 | 结构化输出方式 | 特色 |
|------|------|--------------|------|
| **OpenAI SDK** | Python/JS/.NET | Pydantic / JSON Schema / Zod | 原生 Structured Outputs |
| **Semantic Kernel** | C# / Python | .NET 类型系统 | 微软生态，与 Azure 深度集成 |
| **LangChain** | Python/JS | `with_structured_output()` | 跨模型统一接口 |
| **Instructor** | Python | Pydantic + 重试机制 | 专注结构化输出，支持多种 LLM |
| **Marvin** | Python | Pydantic + 函数式 API | 轻量级，适合快速原型 |
| **PydanticAI** | Python | Pydantic 原生 | Pydantic 团队出品，2025 年新起 |

### 5. .NET/Semantic Kernel 中的结构化输出实战

对 .NET 开发者，Semantic Kernel 提供了类型安全的结构化输出支持：

```csharp
using Microsoft.SemanticKernel;
using System.ComponentModel;
using System.Text.Json.Serialization;

// 定义输出类型——就像定义 EF Core 的 Entity
public record CodeAnalysisResult
{
    [Description("发现的问题列表")]
    public required List<CodeIssue> Issues { get; init; }

    [Description("总体评分 1-10")]
    public required int OverallScore { get; init; }

    [Description("分析总结")]
    public required string Summary { get; init; }
}

public record CodeIssue
{
    [JsonConverter(typeof(JsonStringEnumConverter))]
    public required Severity Severity { get; init; }
    public required int LineNumber { get; init; }
    public required string Description { get; init; }
    public required string Suggestion { get; init; }
}

public enum Severity { Critical, Warning, Info }

// 使用 Semantic Kernel 获取结构化输出
var kernel = Kernel.CreateBuilder()
    .AddOpenAIChatCompletion("gpt-4.1", apiKey)
    .Build();

var settings = new OpenAIPromptExecutionSettings
{
    ResponseFormat = typeof(CodeAnalysisResult)  // 传入类型
};

var result = await kernel.InvokePromptAsync<CodeAnalysisResult>(
    "分析以下 C# 代码的性能问题：{{$code}}",
    new KernelArguments(settings) { ["code"] = sourceCode }
);

// result.Issues[0].Severity → 强类型访问
// result.OverallScore → int，不是 string
```

> [!tip] 老王特别提示
> Semantic Kernel 的 `ResponseFormat = typeof(T)` 底层会自动将 C# 类型转换为 JSON Schema，传给 OpenAI 的 Structured Outputs API。这意味着你用熟悉的 C# record/class 就能定义 LLM 的输出格式——**跟定义 EF Core 的 Entity 一模一样的体验**。

### 6. 结构化输出的常见陷阱与最佳实践

**陷阱一：Schema 过于复杂导致质量下降**
```
❌ 20 个字段、5 层嵌套的巨型 Schema → 模型忙于凑格式，内容质量骤降
✅ 拆分为多次调用，每次输出简单 Schema → 类似数据库的范式化设计
```

**陷阱二：enum 值拼写不一致**
```csharp
// ❌ 模型可能输出 "Critical"、"critical"、"CRITICAL"
// ✅ 在 Schema 中用 enum 严格限定：
//    "enum": ["critical", "warning", "info"]
//    配合 strict: true，保证大小写一致
```

**陷阱三：数值范围失控**
```csharp
// ❌ "score": {"type": "integer"} → 模型可能输出 -1 或 99999
// ✅ Pydantic: Field(ge=1, le=10)
// ✅ JSON Schema: {"type": "integer", "minimum": 1, "maximum": 10}
// 注意：OpenAI strict mode 目前不支持 minimum/maximum 约束 [待验证]
//       需要在应用层额外校验
```

**陷阱四：忽略 `null` 处理**
```csharp
// 某些字段可能合法地为空
// JSON Schema 中需要用 "anyOf" 处理：
// "suggestion": {"anyOf": [{"type": "string"}, {"type": "null"}]}
// C# 中对应 string? 可空引用类型
```

**最佳实践清单**：
1. **Schema 先行**：先用 Pydantic/C# record 定义好类型，再写 prompt——跟 Database First vs Code First 一个道理
2. **Description 字段不能省**：`description` 是模型理解字段语义的关键线索
3. **测试驱动**：写结构化输出的单元测试，验证 Schema 兼容性
4. **降级策略**：结构化输出失败时 fallback 到纯文本 + 正则解析
5. **版本控制 Schema**：Schema 变更等同于 API Breaking Change，要版本管理

### 7. 结构化输出 vs 其他方案对比

```
方案选择决策树：

需要 LLM 输出结构化数据？
├── 简单 key-value → JSON Mode 就够（response_format: { type: "json_object" }）
├── 复杂嵌套 + 严格合规 → Structured Outputs + strict: true
├── 需要触发下游操作 → Function Calling / Tool Use
├── 多步推理 + 结构化 → Extended Thinking + Tool Use（Claude）
└── 分类/枚举任务 → Gemini enum mode 或 Logit Bias 方案
```
