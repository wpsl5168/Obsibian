# 结构化输出 — 工程实战与最佳实践

> 📚 上级页面：[[10-知识库/AI模型与Agent/02-提示词工程与输出规范/2.3-结构化数据输出.md]]

结构化输出解决的是“语法和 schema 合规”，不是“事实正确”。`strict: true` 可以约束字段、类型、枚举和对象结构，但不能证明金额、日期、引用来源或业务判断正确。生产链路必须拆成：**生成约束 → 解析 → 业务校验 → 证据校验 → 版本兼容 → 降级/重试**。

## 1. 四类方案的真实边界

| 方案 | 保证 | 不保证 | 适用场景 |
|---|---|---|---|
| Prompt + 正则 | 几乎无协议保证 | JSON 合法、字段齐全、转义正确 | 一次性脚本，不进入关键链路 |
| JSON Mode | 语法上是 JSON | 符合目标 schema | 老模型兼容、简单对象 |
| Structured Outputs | 支持子集内的 schema adherence | 事实正确、业务规则、完整响应 | 抽取、分类、UI 数据、内部 DTO |
| Function/Tool Calling | 工具参数按 schema 生成；strict 时约束更强 | 工具调用本身安全、幂等、获授权 | 查询、写入、执行动作 |

**选择规则**：输出只是给用户/UI 展示，用 structured response；输出会触发代码或外部系统，用 tool calling；若供应商/模型不支持 strict schema，再降级 JSON Mode + 本地 validator，不要直接降级到正则。

## 2. Schema 设计原则

1. 根节点用 `object`，明确 `required`；严格模式下通常把所有属性列入 required。
2. 对象设置 `additionalProperties: false`，避免静默注入未知字段。
3. 可空字段用 `anyOf: [{"type": "string"}, {"type": "null"}]` 表达，而不是省略。
4. enum 只放稳定机器值，展示文案在应用层映射。
5. 日期优先 ISO 8601 字符串，但仍需业务层解析和时区校验。
6. 不把 20 个字段、5 层嵌套塞进一次抽取；按业务聚合边界拆 schema。
7. schema 是 API contract：命名版本、写 migration、做 consumer contract test。

```json
{
  "type": "object",
  "properties": {
    "schema_version": {"type": "string", "enum": ["1.0"]},
    "decision": {"type": "string", "enum": ["approve", "reject", "review"]},
    "reason_codes": {
      "type": "array",
      "items": {"type": "string", "enum": ["MISSING_DATA", "POLICY_MATCH", "POLICY_CONFLICT"]}
    },
    "evidence_ids": {"type": "array", "items": {"type": "string"}},
    "note": {"anyOf": [{"type": "string"}, {"type": "null"}]}
  },
  "required": ["schema_version", "decision", "reason_codes", "evidence_ids", "note"],
  "additionalProperties": false
}
```

注意：不同供应商仅支持 JSON Schema 的子集。OpenAI 官方明确 strict mode 并不支持全部关键字；Azure 支持范围还受 deployment model 与 API version 影响。上线前应以实际 endpoint 做 schema capability test，不能只在本地 validator 通过就算兼容。

## 3. 生产示例一：Python + Pydantic + 完整失败分流

该例抽取工单路由结果，并区分网络错误、拒答、响应截断和本地业务校验。模型名通过环境变量配置，避免代码绑定快照。

```python
from __future__ import annotations
import os
from typing import Literal
from pydantic import BaseModel, Field, model_validator
from openai import OpenAI, APIError

class TicketRoute(BaseModel):
    schema_version: Literal["1.0"]
    queue: Literal["billing", "security", "technical", "manual_review"]
    priority: Literal["p0", "p1", "p2", "p3"]
    evidence: list[str] = Field(min_length=1, max_length=5)
    customer_id: str | None

    @model_validator(mode="after")
    def validate_policy(self):
        if self.priority == "p0" and self.queue != "security":
            raise ValueError("only security incidents may be p0")
        return self

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"], timeout=30.0)

def route_ticket(text: str) -> TicketRoute:
    try:
        completion = client.chat.completions.parse(
            model=os.getenv("STRUCTURED_MODEL", "gpt-5.6"),
            messages=[
                {"role": "system", "content": "Route support tickets. Never invent evidence."},
                {"role": "user", "content": text},
            ],
            response_format=TicketRoute,
        )
    except APIError as exc:
        raise RuntimeError(f"upstream API failed: {exc.status_code}") from exc

    message = completion.choices[0].message
    if message.refusal:
        raise PermissionError(f"model refused: {message.refusal}")
    if message.parsed is None:
        finish = completion.choices[0].finish_reason
        raise RuntimeError(f"no parsed payload; finish_reason={finish}")

    # parsed 仍会经过 Pydantic 的跨字段业务规则
    return message.parsed
```

不要把 fallback 写成“失败后让同一个模型再输出一次 JSON 字符串”。合理顺序是：

1. transient network/429/5xx：指数退避，带 request id，限制总次数。
2. 截断：缩小输入或提高输出上限，禁止直接拼接残缺 JSON。
3. schema 不支持：部署时失败并报警，不在运行时悄悄改 schema。
4. 业务校验失败：携带最小错误摘要重试一次，仍失败进入人工队列。
5. refusal/content filter：单独处理，不伪装成 parse error。

## 4. 生产示例二：Azure OpenAI / .NET 强类型边界

对企业 .NET 服务，DTO 与 API contract 分开：DTO 用于反序列化，业务校验放在 domain service。以下使用 Azure OpenAI 文档中的 `ChatResponseFormat.CreateJsonSchemaFormat` 形态；deployment name、API version 和 model 支持需在目标订阅验证。

```csharp
using System.ClientModel;
using System.Text.Json;
using Azure.AI.OpenAI;
using OpenAI.Chat;

public sealed record InvoiceExtraction(
    string SchemaVersion,
    string InvoiceNumber,
    string Currency,
    decimal Total,
    string[] EvidenceLines);

var endpoint = new Uri(Environment.GetEnvironmentVariable("AZURE_OPENAI_ENDPOINT")!);
var credential = new ApiKeyCredential(
    Environment.GetEnvironmentVariable("AZURE_OPENAI_API_KEY")!);
var deployment = Environment.GetEnvironmentVariable("AZURE_OPENAI_DEPLOYMENT")!;

var azureClient = new AzureOpenAIClient(endpoint, credential);
ChatClient chat = azureClient.GetChatClient(deployment);

BinaryData schema = BinaryData.FromString("""
{
  "type": "object",
  "properties": {
    "schemaVersion": {"type": "string", "enum": ["1.0"]},
    "invoiceNumber": {"type": "string"},
    "currency": {"type": "string", "enum": ["CNY", "USD", "EUR"]},
    "total": {"type": "number"},
    "evidenceLines": {"type": "array", "items": {"type": "string"}}
  },
  "required": ["schemaVersion", "invoiceNumber", "currency", "total", "evidenceLines"],
  "additionalProperties": false
}
""");

var options = new ChatCompletionOptions
{
    ResponseFormat = ChatResponseFormat.CreateJsonSchemaFormat(
        jsonSchemaFormatName: "invoice_extraction_v1",
        jsonSchema: schema,
        jsonSchemaIsStrict: true)
};

ChatCompletion completion = await chat.CompleteChatAsync(
    [
        new SystemChatMessage("Extract only values supported by source lines."),
        new UserChatMessage(invoiceText)
    ],
    options);

if (completion.FinishReason != ChatFinishReason.Stop)
    throw new InvalidOperationException($"Incomplete model output: {completion.FinishReason}");

var result = JsonSerializer.Deserialize<InvoiceExtraction>(
    completion.Content[0].Text,
    new JsonSerializerOptions { PropertyNameCaseInsensitive = true })
    ?? throw new JsonException("Empty invoice payload");

if (result.Total < 0 || result.EvidenceLines.Length == 0)
    throw new InvalidDataException("Business validation failed");
```

金额类数据还要做：decimal 精度、币种与符号一致、明细求和、税额校验、原文 evidence 定位。Schema 合规不等于 OCR 或抽取结果正确。

## 5. Function calling 不是授权系统

工具参数通过 strict schema，只说明参数结构正确。仍必须在工具执行层完成：

- 身份认证与 RBAC/ABAC；模型不能给自己提权。
- 幂等键与去重；重试不能重复扣款或发信。
- 参数语义校验；`amount: 1000000` 虽是 number 也可能越权。
- dry-run、审批与审计日志；高风险动作先生成 plan，再执行。
- SSRF、路径遍历、SQL 参数化和 allowlist；schema 防不了注入到下游解释器。

```text
model tool arguments
  → JSON Schema validation
  → authentication / authorization
  → business policy validation
  → idempotency check
  → dry-run or approval gate
  → execution
  → immutable audit event
```

## 6. Schema 演进与兼容

| 变更 | 风险 | 推荐处理 |
|---|---|---|
| 新增 required 字段 | 旧 consumer 解析失败 | 新建 v2；双写或适配层过渡 |
| enum 增值 | switch default 崩溃/误判 | consumer 必须有 unknown 分支 |
| 字段改名 | 直接 breaking | 保留旧字段一个周期或 migration |
| string 改 number | 历史数据不兼容 | 新字段 + backfill，禁止原地切换 |
| 收紧长度/范围 | 旧数据无法回放 | 先审计存量，再启用新 validator |

建议把 schema 独立保存并生成 hash。每次请求日志记录 `schema_name`、`schema_version`、`schema_hash`、model deployment、finish reason 和 validator error code；不要记录包含敏感数据的完整 payload，除非已有脱敏和保留策略。

## 7. Eval：格式通过率只是最低门槛

至少分四层指标：

1. **Syntax pass rate**：能否解析 JSON。
2. **Schema pass rate**：是否满足供应商/本地 schema。
3. **Field accuracy**：逐字段 precision、recall、exact match；金额/日期单独统计。
4. **Business success rate**：下游流程是否正确完成，是否触发人工复核或错误动作。

测试集必须覆盖：空输入、超长输入、冲突证据、多语言、恶意文本、缺失字段、极端数值、拒答和截断。对抽取任务保留 source span/evidence id，才能定位“格式正确但事实错”的 silent failure。

## 8. 决策树与上线清单

```text
需要机器消费输出？
├─ 否 → 普通文本
└─ 是
   ├─ 要调用外部能力？ → strict tool calling + policy gate
   └─ 只返回数据？
      ├─ endpoint 支持 JSON Schema strict → Structured Outputs
      ├─ 仅支持 JSON Mode → JSON Mode + 本地 validator + 有界重试
      └─ 均不支持 → 更换模型/endpoint；关键链路不使用正则兜底
```

- [ ] capability probe 已在真实 provider/deployment/API version 跑通。
- [ ] schema 有版本、hash、owner 和 consumer contract test。
- [ ] 处理 refusal、截断、content filter、429/5xx、parse error。
- [ ] 有本地业务规则和证据校验，未把 strict 当事实保证。
- [ ] 工具执行层具备鉴权、幂等、限额和审批。
- [ ] eval 覆盖字段正确率与业务成功率，不只统计 JSON 合法率。
- [ ] 重试有总次数、总时长和 dead-letter/manual-review 去向。
