# 模型评测基准与 Evals 驱动开发

> [!note] 说明
> 本文档为老王知识库深度整理。覆盖主流评测基准体系、Evals 驱动开发范式，以及 2025-2026 年评测领域最新进展。

## 核心概念

### 什么是 LLM Evaluation

LLM Evaluation（大模型评测）是对语言模型能力的系统化度量。类比 .NET 工程中的单元测试 + 集成测试 + 性能基准测试：

| 传统软件测试 | LLM Evaluation |
|---|---|
| xUnit 单元测试 | 单项能力 Benchmark（MMLU、HumanEval） |
| 集成测试 | 端到端任务评测（SWE-bench、GAIA） |
| 性能基准（BenchmarkDotNet） | 推理速度、吞吐量、TTFT 指标 |
| 回归测试套件 | Evals 套件（防止模型升级后能力退化） |

核心挑战：LLM 输出是非确定性的，不像 `Assert.Equal()` 那样有确定的期望值。因此评测需要采用模糊匹配、LLM-as-Judge、人工评审等多种策略。

### Evals 驱动开发（EDD）

Evals 驱动开发是 AI 应用工程化的核心范式，由 OpenAI 在 2023 年提出并逐步完善。其核心理念：

> **先写 Evals，再调 Prompt，最后上线。** 类比 TDD：先写测试，再写实现。

```
传统 TDD 循环：    Red → Green → Refactor
EDD 循环：         Define Evals → Tune Prompt/Model → Evaluate → Iterate
```

## 关键机制与原理解析

### 一、主流评测基准体系（2025-2026）

#### 1. 通用知识与推理

| 基准 | 发布方 | 核心能力 | 当前 SOTA（2026Q1） | 说明 |
|---|---|---|---|---|
| **MMLU-Pro** | 社区改进版 | 多学科知识 + 推理 | ~92%（GPT-5） [待验证] | MMLU 的升级版，去除了过于简单的题目，增加 10 选项，需要推理链 |
| **GPQA Diamond** | NYU | 研究生级科学问答 | ~75%（Claude 4 Opus） [待验证] | 领域专家都只有 65% 准确率的高难度基准 |
| **ARC-AGI-2** | François Chollet | 抽象推理 | ~50%（最佳系统） [待验证] | 2025 年 12 月发布，比 ARC-AGI-1 难度大幅提升 |
| **MATH-500** | Hendrycks | 数学推理 | ~97%（o3） [待验证] | 数学竞赛级别，顶级模型已接近饱和 |
| **BIG-Bench Hard** | Google | 多任务推理 | >95% | 被认为正在"饱和"，区分度下降 |

#### 2. 代码能力评测

| 基准 | 核心场景 | 当前 SOTA（2026Q1） | 说明 |
|---|---|---|---|
| **SWE-bench Verified** | 真实 GitHub Issue 修复 | ~65%（Claude 4 Opus + scaffold） [待验证] | 2024 年推出 Verified 子集（500 题），修正了原版的噪声问题 |
| **SWE-bench Multilingual** | 多语言代码修复 | 新增 Java/C++/Go/Rust [待验证] | 2025Q4 发布，解决原版只有 Python 的局限 |
| **HumanEval+** | 函数级代码生成 | >95% | 基本饱和，已不足以区分顶级模型 |
| **LiveCodeBench** | 竞赛编程（动态更新） | ~45%（hard 分区） | 定期从 Codeforces/LeetCode 抓取新题，防止数据污染 |
| **Aider Polyglot** | 多语言编辑能力 | 排行榜持续更新 | aider 团队维护，测试模型在真实代码编辑场景的表现 |

> [!tip] 老王点评
> SWE-bench 之于 AI 编码，就像 TPC-C 之于数据库——它测的不是"会不会写代码"，而是"能不能在真实代码库里定位问题、理解上下文、写出正确 patch"。这跟我们日常修 Bug 的工作流完全一致。

#### 3. Agent 能力评测

| 基准 | 核心场景 | 说明 |
|---|---|---|
| **GAIA** | 多步骤真实世界任务 | 需要搜索、计算、文件处理等多工具协作 |
| **WebArena** | 网页操作 | 在真实网站上完成任务（购物、论坛发帖等） |
| **TAU-bench** | 工具使用准确性 | 2025 年 Salesforce 发布，测试 Agent 在零售/航空等场景的工具调用准确率 |
| **SWE-bench Multimodal** | 含 UI 截图的 Issue 修复 | 2025 年新增，测试模型理解 UI 截图并修复前端 Bug 的能力 |
| **MLE-bench** | 机器学习工程 | OpenAI 发布，测试模型完成 Kaggle 竞赛任务的能力 |

#### 4. 安全与对齐评测

| 基准 | 核心场景 |
|---|---|
| **WMDP（Weapons of Mass Destruction Proxy）** | 测试模型在生化武器、网络攻击等危险领域的知识边界 |
| **TruthfulQA** | 模型是否会生成常见的人类误解 |
| **HarmBench** | 系统化的有害输出测试 |
| **MACHIAVELLI** | 测试 Agent 在博弈场景中的道德决策 |

### 二、评测方法论

#### 1. LLM-as-Judge（模型互评）

最流行的自动评测方法。用一个强模型（如 GPT-4o、Claude 3.5 Sonnet）作为评委来打分。

```python
# 典型的 LLM-as-Judge 评测 prompt 结构
judge_prompt = """
请对以下回答进行评分（1-5分）：

[评分标准]
5分：完全正确，且表述清晰
4分：基本正确，有小瑕疵
3分：部分正确
2分：大部分错误
1分：完全错误或有害

[问题]
{question}

[参考答案]
{reference}

[待评回答]
{response}

请先给出分析，再给出评分。
"""
```

**已知问题：**
- **位置偏见**：Judge 倾向于给第一个出现的答案更高分
- **冗长偏见**：更长的回答往往得分更高
- **自我偏见**：GPT-4 做 Judge 时倾向于给 GPT-4 的回答更高分

**缓解策略：**
- 交换答案顺序，取平均分
- 使用多个不同的 Judge 模型
- 混入人工标注作为校准锚点

#### 2. Elo Rating 竞技场

**Chatbot Arena**（lmsys.org）采用类似国际象棋 Elo 评分的方式：

- 用户盲测两个模型的回答，选择更好的一个
- 通过大量成对比较计算 Elo 分数
- 截至 2026Q1，累计投票超过 200 万次 [待验证]
- **优势**：最接近真实用户体验，难以刷分
- **劣势**：样本有偏（技术用户为主），更新较慢

> [!info] .NET 类比
> Chatbot Arena 就像是 `TechEmpower Web Framework Benchmarks` 之于 Web 框架——不是某一项指标最高就赢，而是综合实战表现的排名。

### 三、2025-2026 评测领域重要进展

#### 1. Benchmark 饱和与新基准涌现

2025 年的一个核心主题是 **基准饱和**：MMLU、HumanEval、GSM8K 等经典基准被顶级模型"解决"，失去区分度。应对策略：

- **MMLU → MMLU-Pro**：从 4 选项增加到 10 选项，需要推理链
- **HumanEval → SWE-bench**：从函数级提升到项目级
- **静态 → 动态基准**：LiveCodeBench、Chatbot Arena 等持续更新的基准

#### 2. 评测基础设施工具化

| 工具 | 定位 | 关键特性 |
|---|---|---|
| **OpenAI Evals** | 开源评测框架 | 2025 年内置到 OpenAI Platform 控制台 |
| **Braintrust** | 商业评测平台 | 对比实验、在线评测、协作 |
| **Promptfoo** | 开源 CLI 工具 | 本地快速评测，支持红队测试 |
| **Inspect AI（UK AISI）** | 英国 AI 安全研究所出品 | 专注安全评测，2025 年开源 |
| **LangSmith Evals** | LangChain 生态 | 与 LangGraph 深度集成 |
| **DeepEval** | 开源 Python 库 | 类 pytest 风格，CI/CD 友好 |

#### 3. 多模态评测成为标配

随着 GPT-4o、Gemini 2.5、Claude 4 等多模态模型的普及，评测也必须覆盖：

- **视觉理解**：MMMU（多学科多模态理解）
- **视频理解**：Video-MME
- **音频理解**：尚缺乏权威基准
- **跨模态推理**：给图片 + 文字，做复合推理

#### 4. 评测污染（Contamination）仍是核心问题

模型训练数据可能包含评测题目，导致分数虚高。2025-2026 年的应对：

- **动态基准**：题目持续更新，训练截止日期之后的题目不会被污染
- **私有评测集**：企业内部构建不公开的评测集
- **对抗式评测**：故意变换题目形式，测试真实理解而非记忆

### 四、实战建议：为你的 AI 应用构建 Evals

```python
# 示例：用 promptfoo 定义评测
# promptfoo.yaml
prompts:
  - "你是一个SQL专家。请将以下自然语言查询转换为T-SQL：\n{{query}}"
  
providers:
  - openai:gpt-4o
  - anthropic:claude-sonnet-4-20250514
  
tests:
  - vars:
      query: "查询Orders表中2024年的所有订单总金额"
    assert:
      - type: contains
        value: "SUM"
      - type: contains  
        value: "2024"
      - type: llm-rubric
        value: "生成的SQL语法正确且能在SQL Server上执行"
        
  - vars:
      query: "找出购买次数最多的前10个客户"
    assert:
      - type: contains
        value: "TOP 10"  # T-SQL 风格
      - type: not-contains
        value: "LIMIT"   # 不应使用 MySQL 语法
```

> [!tip] 老王经验
> 做 Evals 最大的坑不是工具选型，而是**评测用例的质量**。就像写单元测试——测试用例设计得烂，覆盖率 100% 也没用。建议从线上真实 case 中筛选，特别是那些用户投诉过的 bad case。
