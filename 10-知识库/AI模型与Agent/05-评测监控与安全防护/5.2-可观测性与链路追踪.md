# 可观测性与链路追踪

> [!note] 说明
> 本文档为老王知识库深度整理。覆盖 LLM 应用的可观测性体系、主流链路追踪工具对比，以及 2025-2026 年最新进展。

## 核心概念

### 为什么 LLM 应用需要专门的可观测性？

传统微服务可观测性（Metrics / Logs / Traces 三支柱）在 LLM 应用场景下严重不足：

| 维度 | 传统微服务 | LLM 应用 |
|---|---|---|
| **延迟** | 毫秒级，确定性 | 秒级，波动大（streaming 尤其） |
| **输出** | 结构化 JSON / 状态码 | 非结构化自然语言，需要质量评估 |
| **成本** | 按计算资源计费 | 按 Token 计费，成本与输入长度强相关 |
| **调用链** | HTTP/gRPC 调用 | Prompt → LLM → Tool Call → LLM → 输出（多轮嵌套） |
| **调试** | 看日志、看堆栈 | 需要看完整 Prompt、Completion、中间推理过程 |
| **质量** | 功能对/错 | 回答"好不好"是模糊的，需要评分体系 |

> [!info] .NET 类比
> 如果说 Application Insights / OpenTelemetry 是传统 .NET 应用的可观测性标配，那 LangSmith / Langfuse 就是 LLM 应用的 Application Insights。它们做的不只是记录调用链，还包括**质量评估**和**成本追踪**——这在传统 APM 里是没有的。

### 核心指标体系

LLM 应用可观测性需要追踪的指标分三层：

```
┌─────────────────────────────────────────────┐
│  业务层指标                                   │
│  ├─ 用户满意度（点赞/踩）                     │
│  ├─ 任务完成率                                │
│  └─ 回答质量评分（LLM-as-Judge）              │
├─────────────────────────────────────────────┤
│  应用层指标                                   │
│  ├─ Token 消耗（输入/输出/总计）              │
│  ├─ 成本（按模型计费单价折算）                │
│  ├─ 延迟（TTFT / Total Latency / Streaming） │
│  ├─ 工具调用成功率                            │
│  └─ Retrieval 命中率（RAG 场景）              │
├─────────────────────────────────────────────┤
│  基础设施层指标                                │
│  ├─ API 可用率 / 限流情况                     │
│  ├─ GPU 利用率（自部署场景）                   │
│  └─ 缓存命中率（Semantic Cache）              │
└─────────────────────────────────────────────┘
```

## 关键机制与原理解析

### 一、LLM Trace 的数据模型

LLM 应用的 Trace（链路）与传统分布式追踪的 Span 模型类似，但增加了 LLM 特有的语义：

```
Trace（一次完整用户请求）
├── Span: Chain/Agent（编排层）
│   ├── Span: Retrieval（检索）
│   │   ├── Span: Embedding（向量化查询）
│   │   └── Span: VectorDB Search（向量搜索）
│   ├── Span: LLM Call（第一次模型调用）
│   │   ├── input: prompt（含 system + user + context）
│   │   ├── output: completion（含 tool_calls）
│   │   ├── model: claude-sonnet-4-20250514
│   │   ├── tokens: {input: 2340, output: 567}
│   │   ├── cost: $0.023
│   │   └── latency: 3.2s
│   ├── Span: Tool Execution（工具调用）
│   │   ├── tool: sql_query
│   │   ├── input: "SELECT TOP 10..."
│   │   └── output: [{...}, {...}]
│   └── Span: LLM Call（第二次模型调用，处理工具结果）
│       ├── input: prompt + tool_result
│       ├── output: final_answer
│       └── ...
└── Metadata
    ├── user_id, session_id
    ├── feedback: thumbs_up
    └── eval_score: 4.2/5
```

> [!tip] 对比 SQL Server
> 这就像 SQL Server Profiler / Extended Events 追踪一条 SQL 的执行计划——你需要看到的不只是"这条查询花了 3 秒"，而是"它在 Index Scan 上花了 2.5 秒，因为缺了一个覆盖索引"。LLM Trace 同理：你需要看到哪个 Span 消耗了多少 Token，Prompt 组装是否合理。

### 二、主流工具深度对比（2025-2026）

#### 1. LangSmith（LangChain 官方）

| 属性 | 说明 |
|---|---|
| **定位** | LangChain/LangGraph 全家桶配套的全功能观测平台 |
| **核心功能** | Tracing、Evaluation、Prompt Management、Datasets |
| **接入方式** | 自动（LangChain 项目零配置）+ 手动 SDK |
| **定价** | 免费版 5K traces/月，Plus $39/月，Enterprise 定制 |
| **优势** | LangGraph 深度集成、UI 完善、内置 Evaluation |
| **劣势** | 与 LangChain 生态绑定较深、闭源 |
| **2025-2026 更新** | 新增 Prompt Playground、Online Evaluation 自动评测管线、支持 Multi-agent Trace [待验证] |

#### 2. Langfuse（开源方案）

| 属性 | 说明 |
|---|---|
| **定位** | 开源的 LLM 可观测平台，框架无关 |
| **核心功能** | Tracing、Scoring、Prompt Management、Cost Tracking |
| **接入方式** | 装饰器 / SDK / OpenAI 兼容层 / LangChain Callback |
| **部署** | 自托管（Docker / Kubernetes）或 Cloud 版 |
| **优势** | 开源透明、框架无关、支持自部署（数据不出境） |
| **劣势** | 社区维护，UI/功能不如 LangSmith 完善 |
| **2025-2026 更新** | v3.0 重构了核心架构，支持 OpenTelemetry 导出、新增 LLM-as-Judge 在线评分 [待验证] |

#### 3. OpenTelemetry for LLM（OpenLLMetry / Traceloop）

| 属性 | 说明 |
|---|---|
| **定位** | 基于 OpenTelemetry 标准的 LLM 可观测方案 |
| **核心思路** | 用 OTel Span 扩展 LLM 语义约定（Semantic Conventions） |
| **优势** | 标准化、与现有 OTel 生态兼容、厂商中立 |
| **劣势** | LLM 语义约定仍在演进中、缺乏专用 UI |
| **2025-2026 进展** | OpenTelemetry 官方 Gen AI Semantic Conventions 进入 Experimental 阶段 [待验证] |

### 三、生产环境监控最佳实践

#### 1. 成本监控与预警

```
// 伪代码：Token 成本追踪 Dashboard 指标
daily_cost = SUM(traces.total_tokens * model_price_per_token)
cost_per_query = AVG(trace.cost) GROUP BY endpoint
cost_anomaly = daily_cost > 7d_moving_avg * 1.5  // 成本异常告警

// 类比 SQL Server：就像监控 DTU 消耗和查询开销
// 你不会让一条未优化的查询烧光你的 Azure SQL 预算
// 同理，一个拼错的 Prompt 可能让 Token 消耗暴涨 10 倍
```

#### 2. 质量监控（在线 Eval）

```
// 生产环境持续质量监控
对每个 trace 的输出，异步执行：
  1. 用 LLM-as-Judge 评分（1-5 分）
  2. 检测幻觉（Faithfulness Score：输出是否有 Context 支撑）
  3. 检测有害内容（Safety Score）
  4. 记录用户反馈（显式 thumbs up/down）

告警条件：
  - 质量评分 7 日滑动均值下降 > 10%
  - 幻觉率 > 阈值（如 15%）
  - 用户踩/赞比 > 0.3
```

#### 3. 延迟优化追踪

**TTFT（Time To First Token）** 是用户体验的核心指标：

| 优化手段 | 效果 | 追踪方式 |
|---|---|---|
| Prompt 缓存（Anthropic / OpenAI） | TTFT 降低 50-80% | 追踪 `cache_hit` 字段 |
| 语义缓存（Semantic Cache） | 相似查询直接命中 | 追踪 cache hit rate |
| 流式输出（Streaming） | 感知延迟大幅降低 | 追踪 TTFT vs Total Latency |
| 模型路由 | 简单问题用小模型 | 追踪不同模型的调用比例 |

### 四、架构选型建议

```
┌─────────────────────────────────────────────────────────┐
│                 选型决策树                                 │
│                                                           │
│  Q1: 用的是 LangChain/LangGraph？                         │
│  ├─ Yes → LangSmith 是最省事的选择                        │
│  └─ No → 继续                                             │
│                                                           │
│  Q2: 数据合规要求（不能出境）？                             │
│  ├─ Yes → Langfuse 自部署 / Arize Phoenix                 │
│  └─ No → 继续                                             │
│                                                           │
│  Q3: 已有 OTel 基础设施？                                  │
│  ├─ Yes → OpenLLMetry + 现有 Grafana/Jaeger               │
│  └─ No → Langfuse Cloud / Helicone                        │
│                                                           │
│  Q4: 团队规模？                                            │
│  ├─ 小团队 → Helicone（一行代码搞定）                      │
│  └─ 大团队 → Langfuse + 定制 Dashboard                    │
└─────────────────────────────────────────────────────────┘
```

> [!tip] 老王经验
> 可观测性是 LLM 应用从"Demo"走向"生产"的分水岭。我见过太多团队 Prompt 调了三个月效果越来越差，根本原因是没有评测和监控——等于蒙着眼睛开车。先把 Trace 接上（哪怕只用 Langfuse 最基础的功能），你会发现 90% 的问题在 Trace 里一目了然。
