# MCP 协议架构与传输层

> 📚 上级页面：[[3.2-Model_Context_Protocol规范解析]]

本文剥离自父页“协议架构详解”与“协议传输层”两节，覆盖 MCP 原语、JSON-RPC 消息格式、stdio/Streamable HTTP，以及 `2026-07-28` 现代协议与 `2025-11-25` 旧协议的兼容边界。

> [!warning] 版本边界
> `2026-07-28` 起，现代 MCP 不再依赖 `initialize` 建立连接级会话：版本、身份与 capabilities 改为每请求 metadata；`initialize` 属于 `2025-11-25` 及更早版本。实现和排障必须先确认协议版本，不能混用两套状态机。

## 2026-07-28 核心变化

| 维度 | 现代协议（2026-07-28+） | 旧协议（2025-11-25及以前） | 工程影响 |
|---|---|---|---|
| 版本声明 | 每个 request 的 `_meta`；HTTP 同步镜像到 `MCP-Protocol-Version` | `initialize` 握手协商 | 网关可按 header 路由；body 仍是事实源 |
| 会话 | 核心协议无连接级会话要求 | stdio 进程或 HTTP `Mcp-Session-Id` | 横向扩容不再强制 sticky session |
| 能力发现 | `server/discover`，可选预探测 | `initialize` result | 客户端可 optimistic call，遇不支持版本再重试 |
| 消息方向 | Client 发 request/notification；Server 发 response/notification | 可存在 server-initiated request | 双时代实现必须按版本切换行为 |
| 不兼容处理 | `UnsupportedProtocolVersionError`（code `-32022`）返回 supported 列表 | 实现相关错误 | 客户端应自动选择交集版本，不应盲目 fallback |

现代请求必须携带版本和能力 metadata。Streamable HTTP 会把部分字段镜像为 header，供 API Gateway/LB 在不解析 JSON body 时做路由，但 header 与 body 冲突时应拒绝请求，不能静默选一边。

```json
{
  "jsonrpc": "2.0",
  "id": "req-8f2c",
  "method": "tools/call",
  "params": {
    "name": "query_database",
    "arguments": {"query_id": "sales_by_day", "days": 7},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {"name": "ops-client", "version": "2.4.0"},
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

## 协议架构详解

### 三层角色模型

```
┌─────────────────────────────────────────┐
│                 Host                     │
│  (Claude Desktop / VS Code / IDE)       │
│                                          │
│  ┌──────────┐  ┌──────────┐             │
│  │ MCP      │  │ MCP      │             │
│  │ Client 1 │  │ Client 2 │  ...        │
│  └────┬─────┘  └────┬─────┘             │
└───────┼──────────────┼──────────────────┘
        │              │
   ┌────▼─────┐  ┌────▼─────┐
   │ MCP      │  │ MCP      │
   │ Server A │  │ Server B │
   │ (GitHub) │  │ (数据库)  │
   └──────────┘  └──────────┘
```

- **Host**：用户侧 AI 应用，负责管理多个 MCP Client 实例
- **Client**：与单个 MCP Server 保持 1:1 连接的协议客户端
- **Server**：暴露工具、资源、提示词的服务端

> [!tip] ADO.NET 三层类比
> | 角色 | .NET 类比 | 职责 |
> |---|---|---|
> | Host | ASP.NET 宿主进程 (IIS/Kestrel) | 运行环境，管理生命周期 |
> | Client | ADO.NET 的 `SqlConnection` | 维护与单个 Server 的连接，1:1 关系 |
> | Server | SQL Server 实例 | 暴露存储过程(Tools)、表/视图(Resources)、查询模板(Prompts) |
>
> Host 内部为每个 Server 维护一个 Client 实例——就像你的 ASP.NET 应用为每个数据源维护一个 `SqlConnection`。

### 三大原语 (Primitives)

MCP Server 可以暴露三类能力：

| 原语 | 控制方 | 描述 | SQL Server 类比 |
| :--- | :--- | :--- | :--- |
| **Tools** | 模型控制 | 可执行的函数，模型决定何时调用 | 存储过程 (Stored Procedure) |
| **Resources** | 应用控制 | 只读数据源（文件、DB 记录等） | 视图 (View) |
| **Prompts** | 用户控制 | 预定义的提示词模板，用户手动选择 | 查询模板 (SQL Template) |

#### Tools（工具）= 存储过程

这是 MCP 最核心的原语。每个 Tool 就像一个存储过程——有名称、描述、参数 Schema、返回值。

```json
// MCP Tool 声明，类似存储过程签名
{
  "name": "query_database",
  "description": "对生产数据库执行只读 SQL 查询",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sql": {
        "type": "string",
        "description": "SELECT 语句，禁止 DML/DDL"
      },
      "database": {
        "type": "string",
        "enum": ["production_readonly", "analytics"],
        "description": "目标数据库"
      }
    },
    "required": ["sql", "database"]
  },
  "annotations": {
    "readOnlyHint": true,
    "openWorldHint": false
  }
}
```

```sql
-- SQL Server 类比：这就是一个存储过程签名
CREATE PROCEDURE [dbo].[query_database]
    @sql NVARCHAR(MAX),
    @database NVARCHAR(50)  -- 约束: 'production_readonly' | 'analytics'
AS
```

> [!note] Tool Annotations（2025.3 新增）
> 类似 .NET 的 `[Attribute]` 标注，给工具加元数据。通过 `readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint` 等字段标注工具的行为特征。
>
> ```json
> {
>   "name": "delete_file",
>   "annotations": {
>     "destructiveHint": true,
>     "idempotentHint": false,
>     "readOnlyHint": false,
>     "openWorldHint": true
>   }
> }
> ```
>
> 这些标注不影响协议行为，但 Host 可以据此做安全决策——比如对 `destructiveHint: true` 的工具自动触发人工审批，就像 SQL Server Management Studio 执行 DELETE 前的警告。

#### Resources（资源）= 视图

只读数据暴露。Agent 可以读取但不能修改。

```json
{
  "uri": "file:///project/src/main.py",
  "name": "主程序源码",
  "mimeType": "text/x-python"
}
```

类比：就像给 Agent 开了一个只读的数据库视图权限。

#### Prompts（提示模板）= 查询模板

预定义的 Prompt 模板，用户或 Agent 可以填参数使用。

```json
{
  "name": "code_review",
  "description": "代码审查提示模板",
  "arguments": [
    { "name": "language", "description": "编程语言", "required": true },
    { "name": "code", "description": "待审查代码", "required": true }
  ]
}
```

类比：就像团队共享的 SQL 查询模板，参数化后复用。

### 消息协议：JSON-RPC 2.0

MCP 基于 **JSON-RPC 2.0** 协议通信——对 .NET 开发者应该很熟悉，和 WCF/gRPC 的 RPC 调用模式一样。三种消息类型：

```jsonc
// 1. Request（需要对方响应）
{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {...}}

// 2. Response（对 Request 的响应）  
{"jsonrpc": "2.0", "id": 1, "result": {...}}

// 3. Notification（单向通知，无需响应）
{"jsonrpc": "2.0", "method": "notifications/tools/list_changed"}
```

**完整请求/响应示例：**

```json
// 请求：调用工具（类似 EXEC sp_get_weather @city='北京'）
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "北京" }
  }
}

// 响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "北京：多云转小雨，15-22°C"
      }
    ]
  }
}
```

> [!tip] JSON-RPC 批处理（2025.3 新增）
> 可以一次发送多个请求，减少网络往返——就像 SQL Server 的批量查询：
> ```json
> [
>   {"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_weather","arguments":{"city":"北京"}}},
>   {"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"get_weather","arguments":{"city":"上海"}}}
> ]
> ```

### 生命周期：现代协议与旧协议分流

现代协议没有连接初始化状态机。Client 可以先调用 `server/discover` 获取版本与 capabilities，也可以直接发送首个业务请求；Server 不支持请求中的版本时，必须返回 `-32022` 及 `supported` 列表。Client 选择双方交集中的版本重试；没有交集才报错。

```python
# 生产级双时代客户端伪代码：先识别时代，再缓存到 server origin/process
def call_with_version_fallback(transport, request, preferred_versions):
    era = era_cache.get(transport.identity)
    if era == "legacy":
        return legacy_initialized_call(transport, request)

    for version in preferred_versions:
        response = transport.call(add_request_meta(request, version))
        if response.ok:
            era_cache[transport.identity] = "modern"
            return response
        if response.error.code == -32022:
            preferred_versions = intersect(
                preferred_versions, response.error.data["supported"]
            )
            continue
        # stdio 非现代错误/超时，或 HTTP 400 且无可识别现代错误体，才回退旧协议
        if is_legacy_signal(response):
            era_cache[transport.identity] = "legacy"
            return legacy_initialized_call(transport, request)
        raise ProtocolError(response.error)
    raise ProtocolError("No mutually supported MCP protocol version")
```

旧版 `initialize → initialized → 正常通信` 流程仅用于 `2025-11-25` 及以前版本：

```
Client                          Server
  │                                │
  ├── initialize ─────────────────▶│  (版本协商、能力声明)
  │◀──────────── initialize result─┤  (类似 TLS 握手/连接协商)
  │                                │
  ├── initialized ────────────────▶│  (确认就绪)
  │                                │
  │  ═══ 正常通信阶段 ═══           │
  │                                │
  ├── tools/list ─────────────────▶│  获取工具列表
  │◀──────────── tools list result─┤  (类似 sp_helptext 查看存储过程)
  │                                │
  ├── tools/call ─────────────────▶│  调用工具
  │◀──────────── tool call result──┤  (类似 EXEC stored_procedure)
  │                                │
  ├── ping ───────────────────────▶│  (心跳检测)
  │◀──────────── pong ─────────────┤
  │                                │
  ├── close/transport termination ─▶│  (优雅关闭)
  └────────────────────────────────┘
```

双时代检测要点：

- stdio：先发 `server/discover`；收到规范化现代响应或 `-32022` 即确认现代，其他错误/超时才考虑旧协议。
- Streamable HTTP：先发带现代 metadata/header 的请求；只有 `400` 且 body 不是可识别现代 JSON-RPC error 时，才回退旧握手。
- 时代判断应按 stdio server process 或 HTTP origin 缓存；缓存失效后重新探测。
- 不能看到任意 `4xx` 就 fallback，否则认证失败、限流和真实协议错误会被误诊成版本问题。

## 协议传输层

MCP 定义了两种标准传输方式：

| 传输方式 | 通信模型 | 适用场景 | .NET 类比 |
| :--- | :--- | :--- | :--- |
| **stdio** | 进程内管道 | 本地工具、CLI 应用 | `Process.Start()` + `StandardInput/Output` |
| **Streamable HTTP** | HTTP + SSE | 远程服务、云端部署 | SignalR |
| ~~HTTP+SSE~~ | ~~Server-Sent Events~~ | ~~已 deprecated~~ | ~~Long Polling~~ |

> [!note] 协议版本变化
> `2025-03-26` 用 **Streamable HTTP** 替代旧 HTTP+SSE transport；`2026-07-28` 又把核心协议改为 per-request metadata。SSE 仍可作为单次 HTTP 请求的响应流，deprecated 的是“独立 GET SSE endpoint + POST endpoint”旧 transport，不能把“SSE 响应”本身误判为废弃。

### stdio 传输：本地进程通信

Server 作为子进程运行，通过标准输入/输出通信：

```
Host进程
  └── MCP Client
        └── 子进程: MCP Server (stdin/stdout)
```

```csharp
// .NET 类比：Process.Start() 启动子进程通信
var process = new Process();
process.StartInfo.FileName = "mcp-server-sqlite";
process.StartInfo.RedirectStandardInput = true;
process.StartInfo.RedirectStandardOutput = true;
process.Start();

// 发送 JSON-RPC 请求
await process.StandardInput.WriteLineAsync(jsonRpcRequest);
// 读取响应
var response = await process.StandardOutput.ReadLineAsync();
```

### Streamable HTTP：远程传输

每条 Client 消息通过 HTTP `POST` 发送到单一 MCP endpoint。Server 可返回普通 JSON，也可为该请求打开 SSE response stream。取消请求时，Client 关闭对应 response stream；不要把应用级 `tools/call` 超时简单等价为 TCP 断开。

**生产请求模板：**

```http
POST /mcp HTTP/1.1
Host: mcp.example.com
Content-Type: application/json
Accept: application/json, text/event-stream
Authorization: Bearer <access-token>
MCP-Protocol-Version: 2026-07-28
Idempotency-Key: op-01J8Y7S6M4

{"jsonrpc":"2.0","id":"req-42","method":"tools/call","params":{"name":"create_ticket","arguments":{"title":"DB latency","severity":"P2"},"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}
```

`Idempotency-Key` 不是 MCP 核心字段，但对会产生副作用的远程工具非常必要。Server 应将业务身份、tool name 与 key 组合建唯一索引，并缓存成功响应；超时重试不能重复建单、扣款或发消息。

### 网关、负载均衡与安全基线

| 控制点 | 最低要求 | 失败症状 |
|---|---|---|
| 请求体限制 | 按 tool schema 设上限；拒绝无界 base64 | 内存放大、网关 413 |
| SSE 超时 | idle timeout 高于最长工具心跳间隔 | 长工具调用固定时长断流 |
| Header 透传 | 保留 `MCP-Protocol-Version`、认证、trace ID | Server 误判版本或链路不可追踪 |
| Origin/Host 校验 | 拒绝未允许 origin；绑定预期 host/interface | DNS rebinding、内网工具被跨站调用 |
| 认证授权 | 远程 endpoint 必须鉴权；按 tool/resource 做最小权限 | “已登录”却能调用全部高危工具 |
| 日志脱敏 | 记录 request id/tool/latency/status，不落 token 与完整敏感参数 | 凭据进入 SIEM/日志平台 |
| 限流与并发 | user、client、tool 三维配额；高危工具单独限流 | 一个昂贵工具拖垮整个 server |

**反向代理示例（核心片段）：**

```nginx
location = /mcp {
    proxy_pass http://mcp_pool;
    proxy_http_version 1.1;
    proxy_buffering off;             # SSE 必须及时下发
    proxy_read_timeout 300s;
    client_max_body_size 2m;
    proxy_set_header Host $host;
    proxy_set_header X-Request-ID $request_id;
    proxy_set_header MCP-Protocol-Version $http_mcp_protocol_version;
    proxy_set_header Authorization $http_authorization;
}
```

不要把 CORS 当认证，也不要因为 Tool Annotation 标记 `readOnlyHint: true` 就跳过授权。Annotations 只是提示，不是安全保证；Server 必须按真实实现做权限校验和输入约束。

### 传输选择指南

| 场景 | 传输方式 | 类比 |
|---|---|---|
| 本地 IDE 插件 | stdio | 进程间通信 (IPC) |
| 云端服务集成 | Streamable HTTP | REST API / SignalR |
| 已有 SSE 实现 | SSE（deprecated，迁移中） | 旧版 WebSocket polyfill |

决策规则：

```text
Server 是否与 Host 同机且由 Host 拉起？
├─ 是 → stdio；stdout 只写 JSON-RPC，诊断日志全部写 stderr
└─ 否 → Streamable HTTP
    ├─ 有副作用工具 → 加认证、细粒度授权、幂等键、审计
    ├─ 长任务/流式结果 → 校准 SSE idle timeout 与取消语义
    └─ 特殊消息总线需求 → 可做 custom transport，但必须保留 JSON-RPC、metadata、framing 与 cancellation 语义
```
