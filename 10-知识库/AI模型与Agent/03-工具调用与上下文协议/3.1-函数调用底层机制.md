# 函数调用底层机制

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。硬核技术向，聚焦 LLM Function Calling 的底层实现原理。

## 核心概念

**Function Calling**（函数调用）是 LLM 厂商提供的一种结构化输出能力：模型在推理过程中不直接返回自然语言，而是生成一个符合预定义 JSON Schema 的函数调用请求，由客户端执行后将结果回传给模型继续推理。

> [!tip] .NET 类比
> 把 Function Calling 想象成 C# 的 `interface` + 依赖注入：你在 System Prompt 里通过 JSON Schema "声明接口"，模型在推理时"选择调用哪个接口方法"并填充参数，而真正的实现（执行函数）在你的应用层——就像 DI 容器在运行时注入具体实现一样。

### 底层通信流程

```
用户消息 ──→ LLM（含 tools 定义）
                │
                ├──→ 判断是否需要调用工具
                │     ├── 否 → 直接返回文本响应
                │     └── 是 → 返回 tool_calls 数组
                │
客户端执行函数 ←──┘
                │
函数结果（role: tool）──→ LLM 继续推理 ──→ 最终响应
```

这个流程在底层是一个**多轮消息协议**，关键在于 `messages` 数组中新增了两种角色：
- `assistant`（含 `tool_calls` 字段）：模型决定调用哪些函数
- `tool`（含 `tool_call_id` 字段）：函数执行结果的回传

### 各厂商 API 格式对比（2026 年 4 月最新）

| 特性 | OpenAI (GPT-4o/o3) | Anthropic (Claude 3.5/4) | Google (Gemini 2.5) |
| :--- | :--- | :--- | :--- |
| 工具定义位置 | `tools` 参数 | `tools` 参数 | `tools` 参数 |
| Schema 标准 | JSON Schema (draft 2020-12) | JSON Schema (子集) | OpenAPI 子集 |
| 调用返回字段 | `tool_calls[].function` | `content[].type="tool_use"` | `functionCall` |
| 结果回传角色 | `role: "tool"` | `role: "user"` 内嵌 `tool_result` | `functionResponse` |
| 并行调用 | ✅ 原生支持 | ✅ 原生支持 | ✅ 原生支持 |
| 强制调用 | `tool_choice: {"type":"function","function":{"name":"xxx"}}` | `tool_choice: {"type":"tool","name":"xxx"}` | `tool_config.function_calling_config` |
| Streaming 工具调用 | ✅ 增量 JSON delta | ✅ 增量 content block | ✅ |

## 关键机制与原理解析

### 1. 模型如何"学会"调用函数

Function Calling 并非纯 prompt engineering，而是模型在训练阶段（SFT + RLHF）就被注入了结构化输出能力：

1. **训练数据构造**：用大量 `(用户问题, 工具定义, 正确的函数调用JSON)` 三元组进行微调
2. **特殊 Token 注入**：部分模型在 tokenizer 层面新增了 `<tool_call>`、`</tool_call>` 等特殊标记（如 Mistral 的实现），引导模型进入"结构化输出模式"
3. **Constrained Decoding**：在推理阶段，部分实现使用 Grammar-based Sampling 或 Finite State Machine 约束 token 生成，确保输出严格符合 JSON Schema

> [!tip] SQL Server 类比
> 这类似于 SQL Server 的 **Constraint**：`CHECK` 约束在数据写入时强制验证格式，Constrained Decoding 则在 token 生成时强制验证结构。两者都是在"写入端"做约束而非"读取端"做过滤。

### 2. 并行函数调用 (Parallel Function Calling)

2024 年底 OpenAI 率先支持、到 2025 年已成为行业标配的能力。模型在一次推理中可以返回多个 `tool_calls`，客户端并行执行后一次性回传所有结果。

**工程实践要点**：
```python
# OpenAI 风格的并行调用处理
response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    tools=tools,
    parallel_tool_calls=True  # 默认开启
)

# 一次响应可能包含多个 tool_calls
for tool_call in response.choices[0].message.tool_calls:
    result = execute_function(tool_call.function.name, 
                              json.loads(tool_call.function.arguments))
    messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": json.dumps(result)
    })
```

> [!warning] 并行调用的陷阱
> 当多个函数之间存在**数据依赖**时（如先查用户ID再查订单），模型可能错误地并行调用。工程上建议：
> 1. 在工具描述中明确标注依赖关系
> 2. 对有副作用的写操作，设置 `parallel_tool_calls=false`
> 3. 使用编排层（如 [[10-知识库/AI模型与Agent/03-工具调用与上下文协议/3.2-Model_Context_Protocol规范解析.md|MCP]]）做依赖拓扑排序

### 3. Strict Mode 与 Structured Outputs

OpenAI 在 2024 年 8 月引入的 Strict Mode (`strict: true`) 是一个重要里程碑，它保证函数调用的参数 **100% 符合 JSON Schema**——不再有"差不多对了"的情况。

底层实现是 **Constrained Decoding with CFG (Context-Free Grammar)**：
- 将 JSON Schema 编译为一个有限状态自动机 (FSA)
- 每一步 token 采样时，mask 掉不符合当前 FSA 状态的所有 token
- 确保生成的 JSON 在语法和 Schema 两个层面都严格合规

2025-2026 年的进展：
- **Anthropic Claude** 在 2025 年 Q3 跟进了类似的 `tool_schema_enforcement` 能力
- **Google Gemini 2.5** 通过 `response_schema` + `response_mime_type` 实现了等价功能
- OpenAI 在 2025 年底将 Strict Mode 扩展到支持 `$ref`、`oneOf`、递归 Schema 等更复杂的结构 [待验证]

### 4. 工具选择策略 (Tool Choice)

| 策略 | OpenAI 写法 | 含义 |
| :--- | :--- | :--- |
| 自动 | `tool_choice: "auto"` | 模型自行决定是否调用 |
| 强制任意一个 | `tool_choice: "required"` | 必须调用至少一个工具 |
| 强制指定 | `tool_choice: {"type":"function","function":{"name":"get_weather"}}` | 必须调用指定工具 |
| 禁止 | `tool_choice: "none"` | 禁止调用任何工具 |

### 5. 2025-2026 年重要进展

**OpenAI 方面**：
- **o3/o4-mini 推理模型的工具调用**：2025 年 4 月发布的 o3 和 o4-mini 模型原生支持 Function Calling，打通了"深度推理 + 工具调用"的链路。推理模型在 Chain-of-Thought 阶段就能规划工具调用时机
- **Responses API**：2025 年 3 月发布的新一代 API 格式，用 `input` 替代 `messages`，内置了 `web_search`、`file_search`、`computer_use` 等内建工具，模型可以直接调用无需自定义
- **Agents SDK**：Python-first 的 Agent 框架，将 Function Calling 封装为 `@tool` 装饰器，大幅简化工具定义

**Anthropic 方面**：
- **Claude 的 Extended Thinking + Tool Use**：Claude 3.5 Opus 及后续版本支持在 extended thinking 模式下进行工具调用，模型会先在思维链中规划调用策略再执行
- **Token-efficient tool use**：2025 年引入的优化，对已缓存的工具定义使用压缩表示，减少约 40-60% 的 input token 消耗 [待验证]
- **MCP 集成**：Claude Desktop 等客户端通过 [[10-知识库/AI模型与Agent/03-工具调用与上下文协议/3.2-Model_Context_Protocol规范解析.md|MCP]] 协议直接暴露本地工具

**Google 方面**：
- **Gemini 2.5 Pro/Flash** 在工具调用精度上有显著提升，特别是在多工具场景的选择准确率
- **Grounding with Google Search**：原生搜索工具作为内建 Function，无需自定义

### 6. Function Calling 最佳实践

**工具定义的工程规范**：

```json
{
  "type": "function",
  "function": {
    "name": "query_inventory",
    "description": "查询指定商品的库存数量。当用户询问某商品是否有货、库存多少时调用此函数。不要用于查询价格。",
    "strict": true,
    "parameters": {
      "type": "object",
      "properties": {
        "product_id": {
          "type": "string",
          "description": "商品的唯一标识符，格式为 SKU-XXXXX"
        },
        "warehouse": {
          "type": "string",
          "enum": ["east", "west", "central"],
          "description": "仓库区域"
        }
      },
      "required": ["product_id"],
      "additionalProperties": false
    }
  }
}
```

**黄金法则**：
1. **描述要精确到边界**：不仅说"能做什么"，更要说"不要在什么情况下用"
2. **参数用 enum 约束**：能枚举的绝不用 string 自由输入
3. **工具数量控制在 20 个以内**：超过后模型选择准确率显著下降，可用 MCP 的动态工具注册解决
4. **每个工具配 1-2 个 few-shot example**：放在 system prompt 中，显著提升参数填充准确率
5. **错误处理要友好**：函数返回的错误信息要让模型能理解并调整策略，不要返回堆栈跟踪
