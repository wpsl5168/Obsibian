# RAG 系统架构与演进

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。聚焦 RAG（Retrieval-Augmented Generation）从经典架构到 2026 年前沿的技术演进。

## 核心概念

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种将外部知识检索与 LLM 生成相结合的架构模式。其核心思想：不要指望模型"记住"所有知识，而是在推理时动态检索相关上下文，注入到 prompt 中供模型参考。

> [!tip] SQL Server 类比
> RAG 就像 SQL Server 中的 **Linked Server + 视图**：
> - 数据不在本地表里（模型参数），而是通过 Linked Server（检索系统）从外部数据源实时拉取
> - 视图层（Prompt 拼装）把本地数据和远程数据做 JOIN 后呈现给调用方
> - 相比把所有数据都 INSERT 进本地表（微调/Fine-tuning），Linked Server 方案更灵活、数据更新更实时

### RAG 解决的核心问题

| 问题 | 说明 |
| :--- | :--- |
| **知识时效性** | 模型训练数据有截止日期，RAG 可接入实时数据 |
| **幻觉问题** | 提供真实文档作为 grounding，减少模型编造 |
| **领域知识** | 企业私有数据无法/不宜用于训练，RAG 以检索方式接入 |
| **可追溯性** | 生成结果可标注引用来源，增强可信度 |

## 经典 RAG 架构（Naive RAG）

### 三阶段流水线

```
         Indexing (离线)              Retrieval (在线)          Generation (在线)
┌─────────────────────┐    ┌─────────────────────┐    ┌─────────────────────┐
│  文档加载 & 切片      │    │  用户问题 → Embedding  │    │  Context + Question   │
│  (Document Chunking) │    │         ↓              │    │         ↓              │
│         ↓            │    │  向量相似度检索         │    │  LLM 生成回答         │
│  Embedding 向量化    │    │  (ANN Search)          │    │  (带引用来源)          │
│         ↓            │    │         ↓              │    │                       │
│  存入向量数据库       │    │  Top-K 文档块          │    │                       │
└─────────────────────┘    └─────────────────────┘    └─────────────────────┘
```

### Chunking 策略

文档切片（Chunking）是 RAG 质量的**第一个关键瓶颈**：

| 策略 | 实现方式 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 固定长度切片 | 按 token 数量切（如 512 tokens） | 简单可控 | 可能切断语义 |
| 递归字符切片 | LangChain 的 `RecursiveCharacterTextSplitter` | 尊重段落/句子边界 | 需要调参 |
| 语义切片 | 基于 Embedding 相似度检测语义边界 | 语义完整 | 计算开销大 |
| 文档结构感知 | 按 Markdown 标题、PDF 章节切片 | 保持文档逻辑结构 | 需适配不同格式 |
| Agentic Chunking | 用 LLM 判断切片边界 | 质量最高 | 成本最高 |

> [!tip] 实践建议
> 对于大多数业务文档，**递归字符切片 + 20% overlap** 是性价比最高的方案。chunk_size 建议 512-1024 tokens，具体取决于你的 embedding 模型的最佳输入长度。

## Advanced RAG（进阶 RAG 技术）

### 1. Query Transformation（查询变换）

用户的原始查询往往不是最佳的检索 query。进阶方案：

- **HyDE (Hypothetical Document Embeddings)**：让 LLM 先生成一个"假设答案"，用假设答案的 embedding 去检索，效果优于原始 query
- **Multi-Query**：LLM 将一个问题改写为 3-5 个不同表述，分别检索后合并结果
- **Step-back Prompting**：将具体问题抽象为更高层级的问题检索，获取更广泛的背景知识

### 2. 混合检索 (Hybrid Search)

单纯的向量相似度检索存在局限（如精确匹配弱、对关键词/ID 不敏感），业界标配方案是 **Dense + Sparse 混合检索**：

```
用户 Query
    ├── Dense Retrieval (Embedding 向量检索)
    │     → 语义相似的文档块
    ├── Sparse Retrieval (BM25 / TF-IDF)
    │     → 关键词精确匹配的文档块
    └── Reciprocal Rank Fusion (RRF)
          → 融合排序，取 Top-K
```

> [!tip] SQL Server 类比
> 这就像 SQL Server 的**全文索引 (Full-Text Index)** + 普通 B-Tree 索引的组合查询：全文索引处理模糊语义匹配，B-Tree 索引处理精确条件过滤，两者 UNION 后取交集或排序。

### 3. Reranking（重排序）

检索后用更精细的 Cross-Encoder 模型对候选文档重新打分：

1. 初始检索返回 Top-50
2. Reranker（如 Cohere Rerank、Jina Reranker、BGE-reranker-v2）对每个 `(query, document)` 对精细评分
3. 取重排后的 Top-5 送入 LLM

Reranking 几乎是 Advanced RAG 中**投入产出比最高**的优化手段。

### 4. ColBERT / Late Interaction

ColBERT (Contextualized Late Interaction over BERT) 是一种介于 Bi-Encoder 和 Cross-Encoder 之间的检索架构：

- 每个 token 独立编码为向量（而非整个文档一个向量）
- 检索时做 token 级别的 MaxSim 运算
- 精度接近 Cross-Encoder，速度接近 Bi-Encoder

2025-2026 年 **ColBERT v2** 和 **ColPali**（多模态版本，直接处理文档图像）已成为学术热点，RAGatouille 等库让 ColBERT 的工程落地更加便捷。

## 前沿 RAG 架构（2025-2026 年）

### GraphRAG

**GraphRAG** 由微软研究院于 2024 年提出，核心思想是用**知识图谱 (Knowledge Graph)** 替代或补充向量检索：

1. **索引阶段**：用 LLM 从文档中提取实体和关系，构建知识图谱；对图谱做社区检测（Leiden 算法），为每个社区生成摘要
2. **检索阶段**：
   - **Local Search**：从相关实体出发，沿图谱边遍历获取局部上下文
   - **Global Search**：利用社区摘要回答需要全局视角的问题

GraphRAG 特别适合回答"总结性"问题（如"这个代码库的整体架构是什么？"），这类问题传统向量检索几乎无法处理。

> [!warning] 成本提醒
> GraphRAG 的索引成本极高（大量 LLM 调用用于实体提取和摘要生成）。微软已推出 **GraphRAG Accelerator** 和开源的 `graphrag` Python 包来降低门槛，但对于大型文档集（>10万页），索引费用仍需仔细评估。

### Agentic RAG

**Agentic RAG** 是 2025 年最重要的 RAG 演进方向——将 RAG 从"检索-生成"两步流水线升级为 **Agent 驱动的多步推理检索**：

```
用户问题
    ↓
Agent 推理：需要哪些信息？
    ↓
├── 第一轮检索：向量库搜索 → 发现信息不足
├── Agent 反思：需要更具体的信息
├── 第二轮检索：调用 SQL 查询结构化数据
├── Agent 反思：需要交叉验证
├── 第三轮检索：调用 Web Search API
└── Agent 综合所有结果 → 生成最终回答
```

核心区别：
| 维度 | 传统 RAG | Agentic RAG |
| :--- | :--- | :--- |
| 检索次数 | 固定 1 次 | 动态多次 |
| 检索策略 | 预设 pipeline | Agent 自主决策 |
| 数据源 | 通常单一向量库 | 多源（向量库 + SQL + API + Web） |
| 质量控制 | 无 | Agent 自我评估检索质量 |

实现框架：LangGraph、LlamaIndex Workflows、Anthropic 的 tool_use + RAG 模式。

### Corrective RAG (CRAG)

2025 年兴起的 CRAG 模式在检索后增加一个**质量评估步骤**：

1. 检索 Top-K 文档
2. LLM 评估每个文档与 query 的相关性（Correct / Ambiguous / Incorrect）
3. 如果相关文档不足 → 触发 Web Search 补充
4. 只将高相关文档送入生成阶段

### Modular RAG 架构

2025-2026 年的共识是 RAG 已从固定流水线演进为**模块化可编排架构**：

```
┌─────────┐   ┌──────────┐   ┌─────────┐   ┌──────────┐   ┌─────────┐
│ Query    │──▶│ Routing  │──▶│Retrieval│──▶│Reranking │──▶│Generation│
│Transform │   │ (路由)    │   │(多源检索)│   │(重排序)   │   │(生成)    │
└─────────┘   └──────────┘   └─────────┘   └──────────┘   └─────────┘
                   │                              │
                   ▼                              ▼
              Query 分类            Self-Evaluation (自评估)
              选择检索策略                 ↓ 不满意则回溯
```

每个模块可独立替换和优化，Agent 作为编排者协调各模块。

## 工程实践：RAG 评估指标

衡量 RAG 系统质量的标准框架（基于 RAGAS / TruLens）：

| 指标 | 衡量什么 | 如何计算 |
| :--- | :--- | :--- |
| **Context Relevance** | 检索到的文档是否相关 | LLM 评估 query-context 相关性 |
| **Groundedness** | 生成的回答是否有据可依 | 逐句检查是否能在 context 中找到依据 |
| **Answer Relevance** | 回答是否切题 | LLM 评估 answer-query 相关性 |
| **Faithfulness** | 回答是否忠于原文 | 检测生成内容是否超出 context 范围 |

> [!tip] 生产级 RAG 的底线指标
> Context Relevance > 0.7，Faithfulness > 0.85。低于这个阈值说明检索层或生成层有严重问题。
