### 1. 开源模型生态进入关键期 — "Kubernetes 时刻"

**来源**: Tobi Knaup (Mesosphere 联合创始人) 个人博客  
**链接**: https://tobi.knaup.me/2026-07-25-open-weight-ai-is-having-its-kubernetes-moment/

**核心观点**:
- 开放权重(open-weight)模型正在复制 Kubernetes 的生态演化路径 — 一旦一个足够强的开放平台成为生态重心,单一闭源厂商无法对抗整个生态的创新速率
- Hugging Face 托管超 200 万公开模型;中国模型(Qwen 系列)占下载量 41%
- 最新中国开源模型(Z.ai GLM-5.2、Moonshot Kimi K3)已接近 GPT-5.5/Opus 4.8 级别,且承诺开放权重(Kimi K3 将于 7 月 27 日发布权重,MIT 协议)
- 作者强烈反对美国政府封禁中国开源模型的提议,认为这会把美国开发者隔离在全球生态之外,是战略失误

**作者四条建议**:
1. 美国实验室应发布前沿级开放权重模型(真正可商用许可,而非目前 OpenAI/Google 保留最强模型闭源的做法)
2. 政府采购应要求可移植/可互操作系统,而非绑死单一 API 厂商
3. 美国公司应围绕开源模型构建完整栈(serving/tooling/支持/运维层)
4. 用独立测试+标准替代粗暴封禁(类似 Kubernetes conformance 的治理模式)

**技术细节**:
- 开放权重 != 开源(Open Source Initiative 定义要求包括训练数据+完整训练流程,目前大部分只提供训练后权重)
- 但生态演化机制类似:可下载+可修改的基座吸引大量互补创新(量化/LoRA/领域微调/模型合并/推理优化)
- 一旦基座模型"足够好",生态复利效应启动 — agent runtime、code harness、sandbox、evals、observability、专用 fine-tune 将形成生产级完整栈

### 2. Anthropic Claude 5 代模型的 context engineering 新范式

**来源**: Anthropic 官方博客(Thariq Shihipar,技术团队)  
**链接**: https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models

**核心变化**:
Anthropic 为 Claude Opus 5/Fable 5 **删掉了 Claude Code 80% 的系统提示词**,评测无损。原因:新一代模型判断力跃升,之前为避免最坏情况硬编码的规则现在成了过度约束。

**六大范式转变**:

| 旧范式(Opus 4 代) | 新范式(Opus 5/Fable 5) | 示例 |
|---|---|---|
| **给规则(Give rules)** | **让模型判断(Let Claude use judgement)** | 旧:"default to writing no comments. Never write multi-paragraph docstrings"<br>新:"Write code that reads like the surrounding code: match its comment density" |
| **给示例(Give examples)** | **设计接口(Design interfaces)** | 工具参数设计(枚举/类型约束)比示例更有效;示例反而限制探索空间 |
| **全部前置(Put it all upfront)** | **渐进披露(Progressive disclosure)** | 代码审查指令移入独立 skill,按需加载;工具支持延迟定义(deferred loading via ToolSearch) |
| **重复指令(Repeat yourself)** | **简化工具描述(Simple tool descriptions)** | 指令只在工具描述里写一次,不在系统提示+工具描述双重编码 |
| **CLAUDE.md 记忆(Memory in files)** | **自动记忆(Auto-memory)** | 取消手动 `#` 触发记忆,模型自动保存相关上下文 |
| **简单 spec(Simple specs)** | **丰富引用(Rich references)** | spec 可以是 HTML artifact、完整测试套件、其他代码库的移植目标、rubrics(品味评分标准) |

**实操建议**:
- **System prompt**: 只写产品上下文,避免过细流程
- **CLAUDE.md**: 轻量描述 repo,重点写 gotchas(陷阱/坑),用渐进披露拆分长文档
- **Skills**: 编码特定观点/最佳实践,长 skill 拆成多文件树
- **References**: @提及文件作为深度上下文,优先用代码形式(HTML mockup > 设计描述/截图)

**新命令**: `claude doctor;` — 自动检测并精简过度约束的 skills/CLAUDE.md

### 3. ESP32-S3 ($8 单片机)跑 28.9M 参数 LLM,9 tok/s

**来源**: GitHub slvDev/esp32-ai(HN 223 pts)  
**链接**: https://github.com/slvDev/esp32-ai

**技术突破**:
- 之前单片机上 LLM 只能跑 26 万参数(260K),本项目在 512KB SRAM + 8MB PSRAM + 16MB flash 的 ESP32-S3 上跑 **28.9M 参数**(100 倍提升)
- 核心技巧:**Per-Layer Embeddings**(来自 Google Gemma 3n/4),将 25M 参数的 embedding 表放在 flash,每 token 只读约 6 行(~450 字节),推理核心留在 SRAM
- 速度:9.5 tok/s 端到端(9.7 tok/s 纯计算),完全本地无联网
- 模型:TinyStories 数据集训练,只能写简单故事,不能问答/写代码/知识检索

**内存布局**:
```
SRAM(快/小)  → 推理核心,每 token 用
PSRAM(中)    → 输出头+工作内存
FLASH(大/慢) → 25M 参数表,每 token 读 ~6 行(450B)
```

**实用意义**:
- 架构验证:大模型可以用 flash 作存储层,只在 SRAM 做计算
- 成本:$8 单片机实现以前需要手机/GPU 的能力
- 限制:模型本身太小,只能简单任务;但架构可扩展

**作者公开**:完整训练/量化/烧录代码,包括早期 bug 修复的 commit 历史(参数统计曾有错误,后修正)
