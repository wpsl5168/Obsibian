### P1 — 报告项（涉及业务/架构判断，不动手）

1. **`searchKnowledge` 单次请求 3× 文件 IO + 全表线性扫描**（性能）
   - `searchKnowledge` → `rankThemes`（全 themes 扫）+ `rankExamples`（全 examples 扫，每 example 拼接 7 个字段做 substring）+ `loadGeneratedOmrMetadata`（每次 `getOmrMergeCacheToken` 跑 `fs.statSync` 两次）。
   - 模块级缓存（`taxonomyCache`/`omrCache`/`corpusCache`）虽然防重复 parse，但 `mergedExamples` 每次都查 mtime 决定是否重建，正常运行不会刷新缓存所以热路径其实 OK；真正成本在每请求重跑 O(examples × tokens × fields) 的 substring 累加。
   - 建议（让老王拍板）：(a) 预计算 examples 的 `searchable_lower` 字段；(b) 给 tokens 建倒排索引；(c) `getKnowledgeExampleById` 当前会 lazy build `examplesByLdrawId`——保留，但 corpus preview lookup（`corpus.find` O(N) 每次调用）应做一次 Map 化。

2. **`PREVIEW_FALLBACKS` 只覆盖 4 类，但 `CATEGORY_KEYWORDS` 有 8 类**（功能缺陷）
   - `vehicle / f1 / tank / building` 有 fallback；`ship / aircraft / tree / playground` **无 fallback**，落到 `PREVIEW_FALLBACKS.vehicle` 兜底——船/飞机/树/游乐场全部预览成 vehicle 模型，体验上是错的。
   - 修复属业务决策（要么补 4 个 LDraw fallback，要么改逻辑显式"无 preview"），不自动改。

3. **`detectQueryCategory` 比对逻辑可能误命中**（语义）
   - `keyword.includes(token) || token.includes(keyword)` 双向 substring，例如 query 含 "race"（token），keyword 含 "racing"——`"racing".includes("race")` true，OK；但 query 含 "ar"（极短 token，未被 length 过滤，因为这里没有 `length > 1` 守卫），`"ar".includes("ar")`、`"car".includes("ar")` 都会命中。
   - `scoreTokenOverlap` 里有 `token.length <= 1 continue` 守卫，但 `detectQueryCategory` 没有。建议加 `token.length >= 2` 过滤。
   - 报告，不自动改（涉及检索召回率，需 A/B）。

4. **`loadJsonOnce` 用 getter/setter ref pattern 但 IIFE 重复了 3 次**（架构，DRY）
   - `loadTaxonomy`/`loadOmrMetadata`/`loadCreativeCorpus` 三个函数各自构造一个 getter/setter 闭包，纯 boilerplate。可用更简洁的 `loadJsonOnce(path, cacheKey)` + 单 Map 缓存。属重构建议，不动。

5. **`formatKnowledgeForPrompt` 输出含硬编码英文规则段**（LLM prompt 内容）
   - 末尾 "Rules:\n- Borrow structural patterns..." 是硬编码英文，但 BrickHub 主交互是中英混合（CATEGORY_KEYWORDS 有中文 keyword）。模型可能因 system message 全英文而输出英文倾向。
   - 涉及 prompt 链路（Pitfall #19/#32），仅报告，让老王评估是否需要中英双语 rules 或交给 prompt 编排层做语言切换。
