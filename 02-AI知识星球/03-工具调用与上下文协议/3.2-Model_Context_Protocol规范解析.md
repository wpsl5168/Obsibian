# Model Context Protocol 规范解析

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。聚焦 MCP 协议的技术规范、架构设计与生态演进。

## 核心概念

**Model Context Protocol (MCP)** 是 Anthropic 于 2024 年 11 月开源发布的一项开放协议标准，旨在为 LLM 应用提供**统一的上下文接入层**。它定义了 AI 模型如何与外部数据源、工具、服务进行标准化通信。

> [!tip] .NET 类比
> MCP 之于 AI 工具调用，就像 **ODBC/OLE DB 之于数据库访问**。在没有 ODBC 之前，每个数据库都需要专属驱动；有了 ODBC，应用程序通过统一接口就能连 SQL Server、Oracle、MySQL。MCP 做的是同样的事——让任何 AI 客户端通过统一协议连接任何工具/数据源。

### MCP 解决的核心问题

传统 Function Calling 的痛点：
1. **M×N 集成问题**：每个 AI 应用 × 每个工具都需要单独适配
2. **上下文碎片化**：工具定义、资源、提示词散落在各处
3. **无状态困境**：每次 API 调用都是独立的，缺乏会话级的上下文管理

MCP 将这些问题统一为标准化的 **Client-Server 架构**。

## 协议架构详解

### 三层角色模型

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│   MCP Host   │────▶│  MCP Client  │────▶│  MCP Server  │
│ (AI 应用)     │     │ (协议客户端)   │     │ (工具/数据提供者) │
│ Claude Desktop│     │  1:1 连接     │     │  文件系统/DB/API │
│ VS Code Copilot│    │              │     │              │
│ 自定义应用    │     │              │     │              │
└─────────────┘     └──────────────┘     └──────────────┘
```

- **Host**：用户侧 AI 应用，负责管理多个 MCP Client 实例
- **Client**：与单个 MCP Server 保持 1:1 连接的协议客户端
- **Server**：暴露工具、资源、提示词的服务端

> [!tip] C# 类比
> 这就像 **ADO.NET 的三层架构**：
> - Host = 你的 ASP.NET 应用
> - Client = `SqlConnection`（每个连接对应一个数据源）
> - Server = SQL Server 实例（提供数据和存储过程）

### 协议传输层

MCP 定义了两种标准传输方式：

| 传输方式 | 通信模型 | 适用场景 | 生命周期 |
| :--- | :--- | :--- | :--- |
| **stdio** | 进程内管道 | 本地工具、CLI 应用 | 随进程启停 |
| **Streamable HTTP** | HTTP + SSE | 远程服务、云端部署 | 跨请求持久化 |

> [!note] 协议版本变化
> 2025 年 3 月发布的 MCP 规范版本 `2025-03-26` 用 **Streamable HTTP** 替代了之前的 SSE 传输方式。新方式允许服务端在单个 HTTP 端点上同时处理请求-响应和服务端推送，简化了部署拓扑。旧的 HTTP+SSE 传输方式已标记为 deprecated。

### 消息协议

MCP 基于 **JSON-RPC 2.0** 协议通信，三种消息类型：

```jsonc
// 1. Request（需要对方响应）
{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {...}}

// 2. Response（对 Request 的响应）  
{"jsonrpc": "2.0", "id": 1, "result": {...}}

// 3. Notification（单向通知，无需响应）
{"jsonrpc": "2.0", "method": "notifications/tools/list_changed"}
```

### 三大原语 (Primitives)

MCP Server 可以暴露三类能力：

| 原语 | 控制方 | 描述 | 类比 |
| :--- | :--- | :--- | :--- |
| **Tools** | 模型控制 | 可执行的函数，模型决定何时调用 | SQL Server 的**存储过程** |
| **Resources** | 应用控制 | 只读数据源（文件、DB 记录等） | SQL Server 的**视图 (View)** |
| **Prompts** | 用户控制 | 预定义的提示词模板，用户手动选择 | SQL Server 的**报表模板** |

#### Tools 定义示例

```json
{
  "name": "query_database",
  "description": "对生产数据库执行只读 SQL 查询",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sql": {
        "type": "string",
        "description": "SELECT 语句，禁止 DML/DDL"
      }
    },
    "required": ["sql"]
  },
  "annotations": {
    "readOnlyHint": true,
    "openWorldHint": false
  }
}
```

> [!note] Tool Annotations
> 2025 年 3 月版本新增了 **Tool Annotations** 机制，通过 `readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint` 等元数据标注工具的行为特征。这些标注不影响协议行为，但 Host 可以据此做安全决策（如对 `destructiveHint: true` 的工具自动触发人工审批）。

### 自建 MCP Server 实战（TypeScript 示例）

```typescript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({
  name: "inventory-server",
  version: "1.0.0"
});

// 定义 Tool
server.tool(
  "check_inventory",
  "查询商品库存。传入商品SKU，返回各仓库存量。",
  {
    sku: z.string().describe("商品SKU编码，格式 SKU-XXXXX"),
    warehouse: z.enum(["east", "west", "all"]).optional()
  },
  async ({ sku, warehouse }) => {
    const result = await queryInventoryDB(sku, warehouse ?? "all");
    return {
      content: [{ type: "text", text: JSON.stringify(result) }]
    };
  }
);

// 定义 Resource
server.resource(
  "inventory://daily-report",
  "每日库存汇总报表",
  async () => ({
    contents: [{ uri: "inventory://daily-report", text: await getDailyReport() }]
  })
);

const transport = new StdioServerTransport();
await server.connect(transport);
```

## 安全模型与授权

### OAuth 2.1 集成

2025 年 3 月版本引入了基于 **OAuth 2.1** 的授权框架（针对 HTTP 传输）：

1. Client 发起请求 → Server 返回 `401 Unauthorized`
2. Client 从 Server 的 `/.well-known/oauth-authorization-server` 获取 OAuth 元数据
3. Client 引导用户完成 OAuth 授权流程（PKCE 必选）
4. 后续请求携带 Bearer Token

> [!warning] 安全提醒
> MCP Server 默认没有沙箱隔离。`destructiveHint: true` 的工具（如删除文件、执行 SQL DELETE）必须在 Host 层实现审批机制。参考 [[4.4-Human-in-the-loop交接机制]]。

### 关键安全原则

1. **最小权限**：Server 只暴露必要的工具和资源
2. **用户确认**：敏感操作需要人工审批
3. **数据隐私**：Host 不应将用户数据在未经同意的情况下传给 Server
4. **Tool Annotation 驱动的策略**：基于 annotations 自动分级管控

## MCP vs 传统 Function Calling

| 维度 | 传统 Function Calling | MCP |
| :--- | :--- | :--- |
| 工具发现 | 硬编码在 API 请求中 | 动态发现 (`tools/list`) |
| 工具数量 | 受上下文窗口限制（通常 < 20） | 理论上无限（按需加载） |
| 有状态性 | 无状态 | 有状态会话 |
| 跨应用复用 | 每个应用单独实现 | 一个 Server 服务所有 Host |
| 标准化程度 | 各厂商 API 不同 | 统一开放协议 |
| 生态 | 碎片化 | 统一生态，共享 Server |
