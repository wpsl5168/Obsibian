# Model Context Protocol 规范解析

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。聚焦 MCP 协议的技术规范、架构设计与生态演进。

## 一句话理解 MCP

**MCP 之于 AI Agent，就像 ADO.NET 之于 .NET 应用——一套标准化的数据访问协议。**

在没有 ADO.NET 之前，访问 SQL Server 用一套 API，访问 Oracle 用另一套，访问 MySQL 又是一套。ADO.NET 统一了接口：`IDbConnection`、`IDbCommand`、`IDataReader`，不管底层是什么数据库，上层代码写法一样。

MCP 做的是同一件事：在没有 MCP 之前，接 Claude 用 Anthropic 的 Tool API，接 GPT 用 OpenAI 的 Function Calling，接 Gemini 用 Google 的 Tool 格式。每家 LLM 平台的工具接入方式都不同。MCP 统一了这一切。

Anthropic 在 2024 年 11 月发布 MCP，称之为 **"AI 的 USB-C 接口"**。到 2025 年，OpenAI（2025.3）和 Google（2025.4）相继宣布支持，MCP 正在成为事实上的行业标准。

### MCP 解决的核心问题

传统 Function Calling 的痛点：
1. **M×N 集成问题**：每个 AI 应用 × 每个工具都需要单独适配
2. **上下文碎片化**：工具定义、资源、提示词散落在各处
3. **无状态困境**：每次 API 调用都是独立的，缺乏会话级的上下文管理

MCP 将这些问题统一为标准化的 **Client-Server 架构**。

## 协议架构详解

### 三层角色模型

```
┌─────────────────────────────────────────┐
│                 Host                     │
│  (Claude Desktop / VS Code / IDE)       │
│                                          │
│  ┌──────────┐  ┌──────────┐             │
│  │ MCP      │  │ MCP      │             │
│  │ Client 1 │  │ Client 2 │  ...        │
│  └────┬─────┘  └────┬─────┘             │
└───────┼──────────────┼──────────────────┘
        │              │
   ┌────▼─────┐  ┌────▼─────┐
   │ MCP      │  │ MCP      │
   │ Server A │  │ Server B │
   │ (GitHub) │  │ (数据库)  │
   └──────────┘  └──────────┘
```

- **Host**：用户侧 AI 应用，负责管理多个 MCP Client 实例
- **Client**：与单个 MCP Server 保持 1:1 连接的协议客户端
- **Server**：暴露工具、资源、提示词的服务端

> [!tip] ADO.NET 三层类比
> | 角色 | .NET 类比 | 职责 |
> |---|---|---|
> | Host | ASP.NET 宿主进程 (IIS/Kestrel) | 运行环境，管理生命周期 |
> | Client | ADO.NET 的 `SqlConnection` | 维护与单个 Server 的连接，1:1 关系 |
> | Server | SQL Server 实例 | 暴露存储过程(Tools)、表/视图(Resources)、查询模板(Prompts) |
>
> Host 内部为每个 Server 维护一个 Client 实例——就像你的 ASP.NET 应用为每个数据源维护一个 `SqlConnection`。

### 三大原语 (Primitives)

MCP Server 可以暴露三类能力：

| 原语 | 控制方 | 描述 | SQL Server 类比 |
| :--- | :--- | :--- | :--- |
| **Tools** | 模型控制 | 可执行的函数，模型决定何时调用 | 存储过程 (Stored Procedure) |
| **Resources** | 应用控制 | 只读数据源（文件、DB 记录等） | 视图 (View) |
| **Prompts** | 用户控制 | 预定义的提示词模板，用户手动选择 | 查询模板 (SQL Template) |

#### Tools（工具）= 存储过程

这是 MCP 最核心的原语。每个 Tool 就像一个存储过程——有名称、描述、参数 Schema、返回值。

```json
// MCP Tool 声明，类似存储过程签名
{
  "name": "query_database",
  "description": "对生产数据库执行只读 SQL 查询",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sql": {
        "type": "string",
        "description": "SELECT 语句，禁止 DML/DDL"
      },
      "database": {
        "type": "string",
        "enum": ["production_readonly", "analytics"],
        "description": "目标数据库"
      }
    },
    "required": ["sql", "database"]
  },
  "annotations": {
    "readOnlyHint": true,
    "openWorldHint": false
  }
}
```

```sql
-- SQL Server 类比：这就是一个存储过程签名
CREATE PROCEDURE [dbo].[query_database]
    @sql NVARCHAR(MAX),
    @database NVARCHAR(50)  -- 约束: 'production_readonly' | 'analytics'
AS
```

> [!note] Tool Annotations（2025.3 新增）
> 类似 .NET 的 `[Attribute]` 标注，给工具加元数据。通过 `readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint` 等字段标注工具的行为特征。
>
> ```json
> {
>   "name": "delete_file",
>   "annotations": {
>     "destructiveHint": true,
>     "idempotentHint": false,
>     "readOnlyHint": false,
>     "openWorldHint": true
>   }
> }
> ```
>
> 这些标注不影响协议行为，但 Host 可以据此做安全决策——比如对 `destructiveHint: true` 的工具自动触发人工审批，就像 SQL Server Management Studio 执行 DELETE 前的警告。

#### Resources（资源）= 视图

只读数据暴露。Agent 可以读取但不能修改。

```json
{
  "uri": "file:///project/src/main.py",
  "name": "主程序源码",
  "mimeType": "text/x-python"
}
```

类比：就像给 Agent 开了一个只读的数据库视图权限。

#### Prompts（提示模板）= 查询模板

预定义的 Prompt 模板，用户或 Agent 可以填参数使用。

```json
{
  "name": "code_review",
  "description": "代码审查提示模板",
  "arguments": [
    { "name": "language", "description": "编程语言", "required": true },
    { "name": "code", "description": "待审查代码", "required": true }
  ]
}
```

类比：就像团队共享的 SQL 查询模板，参数化后复用。

### 消息协议：JSON-RPC 2.0

MCP 基于 **JSON-RPC 2.0** 协议通信——对 .NET 开发者应该很熟悉，和 WCF/gRPC 的 RPC 调用模式一样。三种消息类型：

```jsonc
// 1. Request（需要对方响应）
{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {...}}

// 2. Response（对 Request 的响应）  
{"jsonrpc": "2.0", "id": 1, "result": {...}}

// 3. Notification（单向通知，无需响应）
{"jsonrpc": "2.0", "method": "notifications/tools/list_changed"}
```

**完整请求/响应示例：**

```json
// 请求：调用工具（类似 EXEC sp_get_weather @city='北京'）
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "北京" }
  }
}

// 响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "北京：多云转小雨，15-22°C"
      }
    ]
  }
}
```

> [!tip] JSON-RPC 批处理（2025.3 新增）
> 可以一次发送多个请求，减少网络往返——就像 SQL Server 的批量查询：
> ```json
> [
>   {"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_weather","arguments":{"city":"北京"}}},
>   {"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"get_weather","arguments":{"city":"上海"}}}
> ]
> ```

### 连接生命周期

```
Client                          Server
  │                                │
  ├── initialize ─────────────────▶│  (版本协商、能力声明)
  │◀──────────── initialize result─┤  (类似 TLS 握手/连接协商)
  │                                │
  ├── initialized ────────────────▶│  (确认就绪)
  │                                │
  │  ═══ 正常通信阶段 ═══           │
  │                                │
  ├── tools/list ─────────────────▶│  获取工具列表
  │◀──────────── tools list result─┤  (类似 sp_helptext 查看存储过程)
  │                                │
  ├── tools/call ─────────────────▶│  调用工具
  │◀──────────── tool call result──┤  (类似 EXEC stored_procedure)
  │                                │
  ├── ping ───────────────────────▶│  (心跳检测)
  │◀──────────── pong ─────────────┤
  │                                │
  ├── close ──────────────────────▶│  (优雅关闭，类似 SqlConnection.Close)
  └────────────────────────────────┘
```

## 协议传输层

MCP 定义了两种标准传输方式：

| 传输方式 | 通信模型 | 适用场景 | .NET 类比 |
| :--- | :--- | :--- | :--- |
| **stdio** | 进程内管道 | 本地工具、CLI 应用 | `Process.Start()` + `StandardInput/Output` |
| **Streamable HTTP** | HTTP + SSE | 远程服务、云端部署 | SignalR |
| ~~HTTP+SSE~~ | ~~Server-Sent Events~~ | ~~已 deprecated~~ | ~~Long Polling~~ |

> [!note] 协议版本变化
> 2025 年 3 月发布的 MCP 规范版本 `2025-03-26` 用 **Streamable HTTP** 替代了之前的 SSE 传输方式。新方式允许服务端在单个 HTTP 端点上同时处理请求-响应和服务端推送，简化了部署拓扑。Streamable HTTP 就是 MCP 世界的"协议升级"——从早期的 Long Polling 到 SignalR。

### stdio 传输：本地进程通信

Server 作为子进程运行，通过标准输入/输出通信：

```
Host进程
  └── MCP Client
        └── 子进程: MCP Server (stdin/stdout)
```

```csharp
// .NET 类比：Process.Start() 启动子进程通信
var process = new Process();
process.StartInfo.FileName = "mcp-server-sqlite";
process.StartInfo.RedirectStandardInput = true;
process.StartInfo.RedirectStandardOutput = true;
process.Start();

// 发送 JSON-RPC 请求
await process.StandardInput.WriteLineAsync(jsonRpcRequest);
// 读取响应
var response = await process.StandardOutput.ReadLineAsync();
```

### Streamable HTTP：远程传输

支持 OAuth 2.1 认证，适用于远程/云端 MCP Server。

### 传输选择指南

| 场景 | 传输方式 | 类比 |
|---|---|---|
| 本地 IDE 插件 | stdio | 进程间通信 (IPC) |
| 云端服务集成 | Streamable HTTP | REST API / SignalR |
| 已有 SSE 实现 | SSE（deprecated，迁移中） | 旧版 WebSocket polyfill |

## SDK 与开发实战

官方提供 Python 和 TypeScript 两个 SDK。

### TypeScript SDK 示例

```typescript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({
  name: "inventory-server",
  version: "1.0.0"
});

// 定义 Tool
server.tool(
  "check_inventory",
  "查询商品库存。传入商品SKU，返回各仓库存量。",
  {
    sku: z.string().describe("商品SKU编码，格式 SKU-XXXXX"),
    warehouse: z.enum(["east", "west", "all"]).optional()
  },
  async ({ sku, warehouse }) => {
    const result = await queryInventoryDB(sku, warehouse ?? "all");
    return {
      content: [{ type: "text", text: JSON.stringify(result) }]
    };
  }
);

// 定义 Resource
server.resource(
  "inventory://daily-report",
  "每日库存汇总报表",
  async () => ({
    contents: [{ uri: "inventory://daily-report", text: await getDailyReport() }]
  })
);

const transport = new StdioServerTransport();
await server.connect(transport);
```

### Python SDK 示例

```python
from mcp.server import Server
from mcp.types import Tool, TextContent

server = Server("my-tool-server")

@server.list_tools()
async def list_tools():
    return [
        Tool(
            name="calculate",
            description="计算数学表达式",
            inputSchema={
                "type": "object",
                "properties": {
                    "expression": {
                        "type": "string",
                        "description": "数学表达式，如 '2+3*4'"
                    }
                },
                "required": ["expression"]
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "calculate":
        result = eval(arguments["expression"])  # 生产环境请用安全的解析器
        return [TextContent(type="text", text=str(result))]

# 启动：stdio 传输
if __name__ == "__main__":
    import asyncio
    from mcp.server.stdio import stdio_server
    asyncio.run(stdio_server(server))
```

> [!tip] .NET 类比
> 这和写一个 ASP.NET Minimal API 的体验几乎一样——定义路由(`list_tools`)、处理请求(`call_tool`)、启动服务。

## 安全模型与授权

### OAuth 2.1 集成

2025 年 3 月版本引入了基于 **OAuth 2.1** 的授权框架（针对 HTTP 传输）：

1. Client 发起请求 → Server 返回 `401 Unauthorized`
2. Client 从 Server 的 `/.well-known/oauth-authorization-server` 获取 OAuth 元数据
3. Client 引导用户完成 OAuth 授权流程（PKCE 必选）
4. 后续请求携带 Bearer Token

> [!warning] 安全提醒
> MCP Server 默认没有沙箱隔离。`destructiveHint: true` 的工具（如删除文件、执行 SQL DELETE）必须在 Host 层实现审批机制。参考 [[4.4-Human-in-the-loop交接机制]]。

### 关键安全原则

1. **最小权限**：Server 只暴露必要的工具和资源
2. **用户确认**：敏感操作需要人工审批
3. **数据隐私**：Host 不应将用户数据在未经同意的情况下传给 Server
4. **Tool Annotation 驱动的策略**：基于 annotations 自动分级管控

## MCP vs 传统 Function Calling

| 维度 | 传统 Function Calling | MCP |
| :--- | :--- | :--- |
| 工具发现 | 硬编码在 API 请求中 | 动态发现 (`tools/list`) |
| 工具数量 | 受上下文窗口限制（通常 < 20） | 理论上无限（按需加载） |
| 有状态性 | 无状态 | 有状态会话 |
| 跨应用复用 | 每个应用单独实现 | 一个 Server 服务所有 Host |
| 标准化程度 | 各厂商 API 不同 | 统一开放协议 |
| 生态 | 碎片化 | 统一生态，共享 Server |

## 当前缺口与展望

MCP 虽然势头强劲，但仍有明显短板：

| 缺口 | 现状 | 期望 |
|---|---|---|
| 安全认证 | OAuth 2.1 刚加入，实践不足 | 需要成熟的认证最佳实践 |
| Server 发现 | 手动配置，无注册中心 | 需要类似 NuGet/npm 的 Server Registry |
| 权限粒度 | 粗粒度：全部工具或不连 | 需要细粒度的 Tool 级权限控制 |
| 版本管理 | 无版本协商机制 | 需要类似 API 版本控制的方案 |
| 监控审计 | 缺少标准化的日志/审计方案 | 需要类似 Application Insights 的集成 |

> [!tip] .NET 类比
> MCP 现在的阶段类似早期的 NuGet——核心功能可用，生态快速增长，但治理和安全机制还在完善中。
