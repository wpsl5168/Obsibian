## 待老王确认 (P1, 仅报告)

### 1. useEffect deps 包含 callback,父组件重渲会重建整个 LDraw 模型
**位置**: BrickRenderer.js:840 `useEffect(..., [ldrawCode, loaderEligible, loaderEnabled, forceProcedural, onSetupSteps, onPartsExtract])`

**问题**: `onRendered` 这个 callback 已经走 ref 模式 (line 573-574 `onRenderedRef`) 避免重渲,但 `onSetupSteps` 和 `onPartsExtract` 没有走相同保护,仍直接进 deps。若父组件传的是 inline arrow function (没有 useCallback wrap),每次父重渲都会拿到新引用,触发整段 LDraw 重新解析+渲染 (700ms+ 的重活)。

**建议**: 同样改 ref 模式,或在 PR 里要求所有传入的 callback 用 useCallback。

**风险**: P1 (功能性能,涉及对外契约),不自动改。

### 2. 强制 cache-busting 把浏览器/CDN 缓存全废了
**位置**: BrickRenderer.js:324 `const cacheBustedUrl = fetchUrl + (...) + 'cb=' + Date.now()`

**问题**: 每次 HTTP 请求都加 `?cb=<timestamp>` 参数,绕过浏览器 HTTP cache 和 CDN cache,LDraw parts 库 (~万个 .dat 小文件) 全部走网络。虽有 IndexedDB 兜底缓存,但首次访问/cache miss 时每个 part 都跨网络,且这个时间戳让 CDN 完全无效。

**根因猜测**: 历史上某次 HTML 错误页被浏览器缓存导致渲染崩,加 cb 兜底。但已有 line 329-333 的 HTML 检测+ `missingPartUrlCache`,理论上不再需要 cache-bust。

**建议**: 移除 cb 参数,或仅在检测到上一次返回 HTML 时才加。

**风险**: P1 (涉及前端缓存策略,改动可能引入老问题),不自动改。

### 3. `window._brickhubDebugGroup` 始终挂全局,无 debug gate
**位置**: BrickRenderer.js:819 `window._brickhubDebugGroup = groupResult.result`

**问题**: 每次模型加载都把整个 scene graph 挂全局,生产环境也挂。这是一份对 Three.js Group 的强引用,模型切换时旧 Group 没有被显式 `dispose()`,通过 `_brickhubDebugGroup` 永远活着 → 内存泄漏。

**建议**: 包一层 `if (debugMode || process.env.NODE_ENV !== 'production')`,与 line 999 的 `debugMode` 判断对齐。

**风险**: P1 (内存泄漏 + 调试 API 暴露,涉及生产行为变更),不自动改。

### 4. `partsIndexDict` 模块级永久缓存,部署后旧客户端拿不到新 index
**位置**: BrickRenderer.js:118 + 250-260 `if (!partsIndexDict) { ... partsIndexDict = await res.json() }`

**问题**: parts-index.json 在模块加载时拉一次后永远缓存。SPA 长会话场景下 (用户开着 tab 几天不刷新),后端更新了 parts-index 也无法生效。

**建议**: (a) 给 fetch 加 query string `?v=<buildId>` 让浏览器层面感知新版本; (b) 或定期 TTL 刷新 (24h)。

**风险**: P1 (涉及前端缓存策略+部署流程),不自动改。
