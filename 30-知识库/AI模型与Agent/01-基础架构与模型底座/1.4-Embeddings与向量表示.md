# Embeddings 与向量表示

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。

## 核心概念

Embedding（嵌入/向量表示）本质上就是把人类语言"翻译"成计算机能做数学运算的高维浮点数组。如果你熟悉 SQL Server，可以这样理解：**一张表的每一行是一个文本，Embedding 就是给每行算出一个固定长度的 `VARBINARY` 指纹——只不过这个指纹保留了语义信息，语义越接近的文本，指纹越相似**。

核心要点：
- **维度（Dimensions）**：当前主流模型输出 768~3072 维向量。维度越高，表达能力越强，但存储和检索成本也越高——类似于 `NVARCHAR(MAX)` vs `NVARCHAR(256)` 的取舍
- **距离度量（Distance Metrics）**：余弦相似度（Cosine Similarity）是最常用的，本质上算两个向量夹角的余弦值。还有欧氏距离、点积等。对应到 C# 就是 `Vector.Dot()` / `Vector.CosineSimilarity()`
- **Token 限制**：每个 Embedding 模型有最大输入 token 数，超过就截断。类似 `SUBSTRING()` 的硬限制

## 关键机制与原理解析

### 1. Matryoshka Representation Learning（套娃表示学习）

这是 2024-2025 年最重要的 Embedding 技术突破。传统模型输出固定维度，**Matryoshka 训练法让向量的前 N 维就能独立使用**——就像俄罗斯套娃，大娃包着中娃包着小娃，每层都是完整的。

```csharp
// 类比：就像 SQL Server 的聚集索引 + 非聚集索引的关系
// 先用低维（256维）做粗筛，再用全维（3072维）做精排
var coarseVector = fullVector[..256];   // 粗筛：快但略粗糙
var fineVector = fullVector[..3072];    // 精排：慢但精准

// OpenAI text-embedding-3-large 原生支持
var response = await client.EmbeddingsEndpoint
    .CreateEmbeddingAsync("你的文本", dimensions: 256);  // 按需降维
```

**实战价值**：存储成本可降低 90%+，检索速度提升数倍，精度损失极小。对于 .NET 开发者来说，这意味着你可以在 SQL Server 里用 `VARBINARY(512)` 存粗筛向量，在精排时再拉全量。

### 2. 多任务 Embedding（Task-Specific Prefixes）

Google 的 `gemini-embedding-001` 和 BGE 系列模型支持通过 Task Type 前缀来切换嵌入模式：

```csharp
// Google Gemini Embedding 示例
var request = new EmbedContentRequest
{
    Content = "如何在 C# 中实现依赖注入？",
    TaskType = TaskType.RETRIEVAL_QUERY      // 查询模式
    // 其他选项：RETRIEVAL_DOCUMENT, SEMANTIC_SIMILARITY, 
    //          CLASSIFICATION, CLUSTERING, CODE_RETRIEVAL
};

// 文档入库时用 RETRIEVAL_DOCUMENT，搜索时用 RETRIEVAL_QUERY
// 类比：就像 SQL Server 的全文索引，索引时和查询时用不同的分词器
```

### 3. 长上下文 Embedding 的崛起

2025 年的趋势是上下文窗口急剧扩大：
- Cohere embed-v4 支持 **128K token**——整本技术文档一次性向量化
- Voyage-3-large 支持 **32K token**
- 传统的 "分块（Chunking）→ 嵌入 → 检索" 管线正在被 "整文档嵌入 + Late Chunking" 取代

```
传统 RAG 管线：Document → Chunk(512 tokens) → Embed → Vector DB → Search
新范式：      Document → Embed(全文) → Late Interaction → 精准定位段落
```

**Late Chunking（延迟分块）**：先用长上下文模型对整个文档做 Embedding，保留全局语义上下文，最后再切分——类比 SQL Server 的 `COLUMNSTORE INDEX`，先全列压缩再按段读取。

### 4. 多模态 Embedding

2025 年多模态嵌入已经成熟：
- **Cohere embed-v4**：文本和图片统一嵌入到同一向量空间
- **Google Multimodal Embedding**：支持文本、图片、视频片段
- **应用场景**：电商场景下 "用户输入文字搜商品图片"，或 "以图搜图" 都用同一个向量空间

### 5. Binary / Scalar Quantization（二值/标量量化）

向量存太多扛不住？量化来帮忙：

```csharp
// 原始 float32 向量：1536维 × 4字节 = 6KB/条
// int8 量化后：1536维 × 1字节 = 1.5KB/条（省 75%）
// Binary 量化：1536维 / 8 = 192字节/条（省 97%！）

// Cohere embed-v4 原生输出 binary/int8/float32 三种格式
// 类似于 SQL Server 的 ROW_COMPRESSION vs PAGE_COMPRESSION
```

Qdrant、Milvus、Weaviate 等主流向量数据库已全面支持量化存储。

### 6. ColBERT 与 Late Interaction（晚交互检索）

ColBERT（Contextualized Late Interaction over BERT）是 2024-2026 年检索领域的明星架构，代表了从"单向量"到"多向量"的范式转变：

```
传统 Embedding（单向量）：
  文档 → 1 个向量（1536维）→ 余弦相似度

ColBERT（多向量 / Late Interaction）：
  文档 → 每个 token 1 个向量 → 逐 token 最大相似度聚合（MaxSim）
```

```csharp
// 类比：传统 Embedding 像给整张表算一个 HASHBYTES 指纹
// ColBERT 像给每个字段分别建索引，查询时逐字段匹配再汇总

// 伪代码：ColBERT 的 MaxSim 评分
float ColBertScore(float[][] queryTokenVectors, float[][] docTokenVectors)
{
    float totalScore = 0;
    foreach (var qVec in queryTokenVectors)
    {
        // 每个 query token 找到最相似的 doc token
        float maxSim = docTokenVectors.Max(dVec => CosineSimilarity(qVec, dVec));
        totalScore += maxSim;
    }
    return totalScore;
}
```

**优势**：细粒度语义匹配，对长文档和多义词查询效果显著优于单向量。BAAI 的 bge-m3 和 Jina 的 ColBERT v2 都支持此模式。

**代价**：存储成本高（每文档 N 个向量），检索时计算量大。目前 Vespa、Qdrant（实验性）支持 ColBERT 索引。

### 7. Hybrid Search（混合检索）——2025-2026 最佳实践

纯向量搜索并非万能，实际生产系统中 **向量 + 关键词** 的混合检索已成标配：

```
混合检索管线：
  Query → ┬→ 向量检索（语义匹配）→ 候选集 A
          └→ BM25 检索（关键词匹配）→ 候选集 B
              ↓
          RRF / Cross-Encoder 融合排序 → 最终结果
```

```csharp
// 类比 SQL Server：就像同时用全文索引 + LIKE 查询，然后 UNION 结果
// SELECT * FROM Documents WHERE CONTAINS(Content, @keywords)  -- BM25
// UNION
// SELECT * FROM Documents ORDER BY VECTOR_DISTANCE(Embedding, @query)  -- 向量
// 最后用 Cross-Encoder 或 RRF 统一排序
```

主流向量数据库 2025-2026 年的混合检索支持情况：
- **Qdrant**：原生 Hybrid Search（稀疏+稠密向量），支持 Fusion 策略
- **Weaviate**：BM25 + Vector 混合，`alpha` 参数控制权重
- **Azure AI Search**：Semantic Ranker + Vector + Keyword 三路融合
- **pgvector + pg_search**：PostgreSQL 生态中向量与全文索引的组合方案
- **SQL Server 2025**：VECTOR_DISTANCE + FREETEXT 可在同一查询中组合

> [!tip] 老王特别提示

> ```sql
> -- SQL Server 2025 原生向量检索
> CREATE TABLE Documents (
>     Id INT PRIMARY KEY,
>     Content NVARCHAR(MAX),
>     Embedding VECTOR(1536)  -- 新数据类型！
> );
> 
> SELECT TOP 10 Id, Content,
>     VECTOR_DISTANCE('cosine', Embedding, @queryVector) AS Distance
> FROM Documents
> ORDER BY Distance;
> ```

## Semantic Kernel 集成实战

对 .NET 开发者来说，微软的 Semantic Kernel 是使用 Embedding 的首选框架：

```csharp
// Semantic Kernel 中使用 Embedding
using Microsoft.SemanticKernel;
using Microsoft.SemanticKernel.Connectors.OpenAI;

var kernel = Kernel.CreateBuilder()
    .AddOpenAITextEmbeddingGeneration("text-embedding-3-large", apiKey)
    .AddQdrantVectorStore("localhost", 6334)
    .Build();

// 文档入库
var memoryStore = kernel.GetRequiredService<IVectorStore>();
var collection = memoryStore.GetCollection<string, DocumentRecord>("knowledge-base");
await collection.UpsertAsync(new DocumentRecord
{
    Key = "doc-001",
    Content = "C# 依赖注入最佳实践...",
    // Embedding 自动计算
});

// 语义搜索
var searchResults = await collection.VectorizedSearchAsync(
    queryEmbedding, 
    new() { Top = 5, Filter = new EqualToFilterClause("Category", "CSharp") }
);
```
