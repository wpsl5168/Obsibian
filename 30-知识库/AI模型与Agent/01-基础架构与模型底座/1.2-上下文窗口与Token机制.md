# 上下文窗口与 Token 机制

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。搞清楚 Token 和上下文窗口，是理解 LLM 一切行为的底层基础。

## 核心概念

### Token：LLM 的最小计算单元

Token 不等于字符，也不等于单词。它是模型 Tokenizer 切分后的最小语义单元。

> [!tip] .NET 类比
> Token 之于 LLM，就像 `char` 之于 C# 的 `string`——但更准确的类比是 `Span<byte>` 的切片粒度。一个英文单词可能被切成 1-3 个 Token，一个中文字通常是 1-2 个 Token。

**主流 Tokenizer 对比**：

| Tokenizer | 使用方 | 词表大小 | 特点 |
| :--- | :--- | :--- | :--- |
| tiktoken (cl100k_base) | OpenAI GPT-4 | ~100K | BPE 算法，英文高效 |
| tiktoken (o200k_base) | OpenAI GPT-4o/o1 | ~200K | 更大词表，多语言优化 |
| SentencePiece | Google Gemini, LLaMA | 256K (Gemini) | Unigram/BPE，多语言友好 |
| Claude Tokenizer | Anthropic Claude | 未公开 | 基于 BPE，中文效率较好 |

### 上下文窗口（Context Window）

上下文窗口是模型单次推理能"看到"的全部 Token 数量，包括**输入（Prompt）+ 输出（Completion）**。

> [!tip] SQL Server 类比
> 上下文窗口就像 SQL Server 的 **Buffer Pool 大小**。Buffer Pool 能缓存多少数据页，决定了查询能在多大范围内快速检索。上下文窗口能装多少 Token，决定了 LLM 能在多大范围内建立注意力关联。

> [!warning] 上下文长度 ≠ 有效利用长度
> 这是最常见的误区。128K 的窗口不意味着模型能均匀关注到每个位置。研究表明存在"Lost in the Middle"现象——模型对开头和结尾的信息关注度远高于中间部分。就像 SQL Server 的聚集索引扫描，越靠前和靠后的数据页命中率越高。

### Extended Thinking 对上下文的影响

Claude 3.7 Sonnet 和后续模型引入了 **Extended Thinking**（扩展思考），模型会在输出前进行内部推理：

```
总上下文消耗 = 输入 Token + Thinking Token（不可见）+ 输出 Token
```

> [!important] 工程关键点
> 启用 Extended Thinking 时，`max_tokens` 参数定义的是 Thinking + 输出的总预算。比如设置 `max_tokens=16000`，如果模型"想"了 12000 Token，只剩 4000 Token 给实际输出。这就像 SQL Server 的 TempDB 和数据文件共享同一块磁盘——TempDB 膨胀了，数据文件可用空间就少了。

## Token 计费机制

### 输入/输出差异定价

所有主流 API 都采用**输入 Token 和输出 Token 差异定价**：

| 模型 | 输入价格 (每 1M Token) | 输出价格 (每 1M Token) | 输入/输出比 |
| :--- | :--- | :--- | :--- |
| Claude 3.5 Sonnet | $3.00 | $15.00 | 1:5 |
| Claude 4 Opus | $15.00 [待验证] | $75.00 [待验证] | 1:5 |
| GPT-4o | $2.50 | $10.00 | 1:4 |
| GPT-4o mini | $0.15 | $0.60 | 1:4 |
| Gemini 2.5 Pro | $1.25 (≤200K) / $2.50 (>200K) | $10.00 / $15.00 | 动态阶梯 |

> [!tip] 成本优化策略
> 1. **Prompt Caching**：Claude 和 OpenAI 都支持上下文缓存，重复输入部分打折（Claude 缓存读取价格为原价 10%）
> 2. **Batch API**：非实时场景使用批量 API，通常 50% 折扣
> 3. **模型降级**：先用大模型（Opus/GPT-4o）写 Evals，再用小模型（Haiku/4o-mini）跑生产

### Prompt Caching 详解

Anthropic 2024 年推出的 Prompt Caching 是成本优化的杀手锏：

```json
// 用 cache_control 标记需要缓存的内容块
{
  "system": [
    {
      "type": "text",
      "text": "你是一个资深 .NET 架构师...(大段系统提示词)...",
      "cache_control": {"type": "ephemeral"}
    }
  ]
}
```

缓存命中时，输入价格从 $3/1M 降至 $0.30/1M，降低 **90%**。缓存写入有 25% 溢价，但只要复用 2 次以上就能回本。

> [!tip] SQL Server 类比
> Prompt Caching 就像 SQL Server 的 **执行计划缓存（Plan Cache）**。第一次编译存储过程有开销，但后续调用直接复用缓存的执行计划，性能提升数量级。

## Token 化的工程陷阱

### 1. 中文 Token 效率

中文在大多数英文优先的 Tokenizer 中效率较低：
- 英文 "hello" = 1 Token
- 中文 "你好" = 2-3 Token（取决于 Tokenizer）

**工程影响**：同样语义的中文 Prompt 消耗 Token 可能比英文多 50-100%。

### 2. JSON 输出的 Token 浪费

结构化 JSON 输出中，键名和格式字符（`{`, `}`, `"`, `,`）都消耗 Token：

```json
{"name": "张三", "age": 30, "city": "北京"}
// 上面这行大约消耗 20+ Token，其中格式字符占了一半
```

> [!tip] 优化建议
> 在高频调用场景下，考虑用 [[2.3-结构化数据输出]] 中的紧凑格式或直接让模型输出 CSV/TSV 格式，Token 消耗可降低 30-50%。

### 3. System Prompt 的隐性成本

System Prompt 在每次 API 调用时都会被发送，长系统提示词 × 高频调用 = 巨额成本。务必配合 Prompt Caching 使用。
