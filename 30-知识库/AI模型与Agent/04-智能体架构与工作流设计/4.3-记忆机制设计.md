# 记忆机制设计

> [!note] 说明
> 本文档为小贝知识库自动整理和排版。聚焦 AI Agent 的记忆系统架构设计，从理论到工程实践。

## 核心概念

**记忆（Memory）** 是 Agent 区别于一次性 LLM 调用的关键特征。没有记忆的 Agent 就像患了健忘症的员工——每次汇报都要从头解释背景。记忆系统让 Agent 能够跨会话积累经验、持久化关键信息、动态调整行为策略。

> [!tip] SQL Server 类比
> Agent 的记忆层级，精确对应 SQL Server 的存储层级：
> | Agent 记忆 | SQL Server 对应 | 特点 |
> | :--- | :--- | :--- |
> | Context Window（上下文窗口） | Buffer Pool（内存缓冲池） | 速度最快，容量有限 |
> | Short-term Memory（短期记忆） | tempdb | 会话级，用完释放 |
> | Long-term Memory（长期记忆） | 持久化表（用户表） | 跨会话持久化 |
> | Episodic Memory（情景记忆） | 审计日志 (Audit Trail) | 记录"发生过什么" |
> | Semantic Memory（语义记忆） | 知识库表 + 全文索引 | 记录"知道什么" |
> | Procedural Memory（程序性记忆） | 存储过程库 | 记录"怎么做" |

## 记忆类型详解

### 1. 上下文窗口（Context Window）—— 最基础的"记忆"

LLM 的上下文窗口本身就是最基础的记忆形式——所有的 messages 历史都在这个窗口中。

**核心限制**：
- 窗口有上限（GPT-4o: 128K tokens, Claude 3.5 Sonnet: 200K tokens, Gemini 2.5 Pro: 1M tokens）
- Token 越多，推理延迟和成本越高
- 存在"中间丢失"现象（Lost in the Middle）：模型对窗口中间位置的信息关注度较低

### 2. 短期记忆（Short-term / Working Memory）

维护当前会话的对话历史和中间推理状态。核心工程问题是**如何在上下文窗口有限的情况下保留最重要的信息**。

**主要策略**：

| 策略 | 原理 | 优缺点 |
| :--- | :--- | :--- |
| **滑动窗口** | 保留最近 N 轮对话 | 简单但会丢失早期关键信息 |
| **Token 截断** | 当 messages 超过阈值时，丢弃最早的 | 粗暴但有效 |
| **摘要压缩** | 用 LLM 对历史对话生成摘要，替代原始消息 | 保留语义但损失细节 |
| **滑动摘要** | 滑动窗口 + 被滑出的部分自动摘要 | 平衡近期细节和远期概要 |
| **重要性评分** | 对每条消息打重要性分数，低分的优先丢弃 | 精细但增加计算开销 |

```python
# 滑动摘要策略的伪代码
class SlidingWindowWithSummary:
    def __init__(self, window_size=10, max_tokens=4000):
        self.window_size = window_size
        self.summary = ""  # 压缩的历史摘要
        self.recent_messages = []  # 最近的消息（完整保留）
    
    def add_message(self, message):
        self.recent_messages.append(message)
        if len(self.recent_messages) > self.window_size:
            # 把最早的消息压缩进摘要
            oldest = self.recent_messages.pop(0)
            self.summary = llm_summarize(self.summary, oldest)
    
    def get_context(self):
        return [
            {"role": "system", "content": f"历史摘要:\n{self.summary}"},
            *self.recent_messages
        ]
```

### 3. 长期记忆（Long-term Memory）

跨会话持久化的记忆，Agent 需要"记住"用户偏好、历史交互中学到的知识、已完成的任务等。

**实现方案**：

#### 方案 A：向量数据库存储
将记忆编码为 embedding 存入向量库，检索时按语义相似度召回。

```
记忆写入：
  对话/事件 → LLM 提取关键信息 → Embedding → 存入向量库

记忆读取：
  当前上下文 → Embedding → 向量相似度检索 → Top-K 相关记忆 → 注入 prompt
```

#### 方案 B：结构化存储
用关系型数据库或 KV 存储保存结构化记忆：

```sql
-- 用户偏好记忆表（SQL Server 风格）
CREATE TABLE agent_memories (
    memory_id       UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id         NVARCHAR(100) NOT NULL,
    memory_type     NVARCHAR(50) NOT NULL,  -- 'preference' | 'fact' | 'episode'
    content         NVARCHAR(MAX) NOT NULL,
    importance      FLOAT DEFAULT 0.5,       -- 重要性评分 0-1
    last_accessed   DATETIME2 DEFAULT GETUTCDATE(),
    access_count    INT DEFAULT 0,
    created_at      DATETIME2 DEFAULT GETUTCDATE(),
    embedding       VECTOR(1536)              -- 向量列 [Azure SQL]
);

-- 按重要性 × 时效性的衰减检索
SELECT TOP 10 *
FROM agent_memories
WHERE user_id = @userId
ORDER BY importance * EXP(-DATEDIFF(DAY, last_accessed, GETUTCDATE()) * 0.01) DESC;
```

#### 方案 C：混合存储
实践中最常用——**结构化元数据 + 向量语义检索**的组合：
- 结构化字段（用户ID、记忆类型、时间戳）用关系库索引
- 内容字段同时存向量，支持语义检索
- 重要性/新鲜度/访问频率综合评分

### 4. 情景记忆（Episodic Memory）

记录 Agent 的"经历"——过去执行任务的完整轨迹，包括成功和失败。

**核心价值**：
- 相似任务复用经验：遇到类似问题时，检索过去的成功经验
- 避免重蹈覆辙：Reflexion 模式依赖情景记忆存储失败教训
- Few-shot 动态构建：从情景记忆中检索相关案例作为 few-shot examples

```json
// 一条情景记忆
{
  "episode_id": "ep_20260413_001",
  "task": "查询用户最近3个月的订单总额",
  "trajectory": [
    {"thought": "需要先获取用户ID", "action": "get_user_id", "result": "user_123"},
    {"thought": "用ID查询订单", "action": "query_orders", "result": "找到15条订单"},
    {"thought": "计算总额", "action": "calculate_sum", "result": "¥12,580"}
  ],
  "outcome": "success",
  "lessons": "直接用用户名查订单更快，不需要先查ID",
  "created_at": "2026-04-13T10:30:00Z"
}
```

### 5. 语义记忆（Semantic Memory）

存储"事实性知识"——关于世界、用户、业务的静态知识。

- 用户偏好："老王偏好 .NET 技术栈，讨厌 Java"
- 业务规则："VIP 客户退货无需审批"
- 领域知识：从文档中提取的知识点

本质上就是 [[3.3-RAG系统架构与演进|RAG]] 系统，只不过数据源是 Agent 自身在交互中积累的知识。

### 6. 程序性记忆（Procedural Memory）

存储"如何完成任务"的方法论——类似于**存储过程**：

- Agent 在多次执行类似任务后，总结出标准操作流程（SOP）
- 下次遇到同类任务时，直接调用 SOP 而非从头推理
- 可以看作是一种 **Meta-Learning**——学习如何学习

## MemGPT / Letta：虚拟记忆管理

**MemGPT**（后更名为 **Letta**）是 2023 年由 UC Berkeley 团队提出的革命性记忆管理方案，其核心洞察是：

> 把 LLM 的上下文窗口视为"内存"，把外部存储视为"磁盘"，Agent 自己管理内存与磁盘之间的数据交换。

> [!tip] 精确的 OS 类比
> MemGPT 的设计**直接对标操作系统的虚拟内存管理**：
> | 操作系统概念 | MemGPT 对应 |
> | :--- | :--- |
> | 物理内存 (RAM) | LLM Context Window |
> | 虚拟内存 / Swap | 外部存储（向量库/文件） |
> | Page Fault | Agent 发现需要的信息不在上下文中 |
> | Page In / Page Out | Agent 主动调用 `memory_retrieve` / `memory_store` |
> | Memory-Mapped File | RAG 检索的文档块 |

### MemGPT 的内存层级

```
┌─────────────────────────────────┐  ← 始终在上下文中
│  System Prompt (核心指令)         │
├─────────────────────────────────┤
│  Core Memory (核心记忆)           │  ← Agent 可读写的"工作记忆"
│  - Human Block: 用户基本信息      │     类似 SQL Server 的
│  - Persona Block: Agent 人设     │     内存优化表 (In-Memory Table)
├─────────────────────────────────┤
│  Recall Memory (回忆记忆)         │  ← 完整对话历史（外部存储）
│  Agent 可搜索但不常驻上下文        │     类似 SQL Server 的磁盘表
├─────────────────────────────────┤
│  Archival Memory (归档记忆)       │  ← 知识库/文档（向量库）
│  Agent 按需检索                   │     类似 Azure Blob Storage
└─────────────────────────────────┘
```

Agent 通过以下内建工具管理记忆：
- `core_memory_append(key, value)` — 向核心记忆追加信息
- `core_memory_replace(key, old, new)` — 修改核心记忆
- `recall_memory_search(query)` — 搜索对话历史
- `archival_memory_insert(content)` — 存入归档记忆
- `archival_memory_search(query)` — 检索归档记忆

### 2025-2026 年 Letta 进展

Letta（MemGPT 的商业化版本）在 2025 年持续演进：
- **Letta Cloud**：托管的有状态 Agent 服务，提供 REST API
- **Agent State 持久化**：Agent 的完整状态（包括记忆、工具、模型配置）可以保存和恢复
- **Multi-Agent Memory Sharing**：多个 Agent 可以共享 Archival Memory 源
- **MCP 集成**：通过 MCP Server 暴露记忆管理能力 [待验证]

## 2025-2026 年记忆机制新进展

### OpenAI 的 Memory 功能

ChatGPT 的 Memory 功能（2024 年推出，2025 年持续演进）是面向消费者的长期记忆实现：
- 自动从对话中提取用户偏好和事实
- 用户可以查看、编辑、删除记忆
- 记忆以自然语言形式存储，在新对话开始时注入 system prompt

### Claude 的 Memory

Anthropic 在 2025 年为 Claude 引入了类似的记忆功能：
- **Project Knowledge**：项目级别的持久化知识
- **User Preferences**：跨会话的用户偏好记忆 [待验证]

### LangGraph 的 Memory Store

LangGraph 在 2025 年引入了 `MemoryStore` 抽象：
- **Thread-level Memory**：单个会话的 checkpointed 状态（短期记忆）
- **Cross-thread Memory**：跨会话的持久化记忆（长期记忆）
- 底层支持多种存储后端（PostgreSQL、Redis、内存）

### Zep：专用 Agent 记忆平台

Zep 是 2025 年崛起的专用 Agent 记忆基础设施：
- 自动从对话中提取事实和实体关系
- 构建用户知识图谱
- 时序感知的记忆检索（最近的记忆权重更高）
- 提供 REST API，可与任何 Agent 框架集成

## 记忆系统设计模式

### 记忆的 CRUD 生命周期

```
Create (创建)
  ├── 显式创建：Agent 主动调用 memory_store
  └── 隐式创建：系统自动从对话中提取

Read (读取)
  ├── 主动检索：Agent 根据当前任务搜索相关记忆
  └── 被动注入：系统在每轮对话前自动注入相关记忆

Update (更新)
  ├── 覆盖更新：新信息替代旧信息
  └── 追加更新：在已有记忆上补充细节

Delete (删除)
  ├── 显式删除：用户要求遗忘
  ├── 衰减删除：长期未访问的记忆自动淘汰
  └── 合并删除：多条重复记忆合并为一条
```

### 记忆检索的加权评分

综合以下因素对记忆进行排序：

```
最终得分 = w₁ × Relevance(语义相关性)
         + w₂ × Recency(时间新鲜度)
         + w₃ × Importance(重要性)
         + w₄ × Frequency(访问频率)
```

> [!tip] 参数建议
> 初始权重建议 `w₁=0.4, w₂=0.3, w₃=0.2, w₄=0.1`，根据业务场景调整。对客服场景，Recency 权重应提高；对知识库场景，Relevance 权重应提高。
