# BrickHub 2.0 互动拼搭引擎架构选型与技术白皮书 (TDD)

> 相关文档：[[4.5-BrickHub_Architecture_Vision|架构愿景]] · [[4.6-BrickHub_Technical_Research|技术研究]] · [[4.9-BrickHub_Engineering_Principles_and_Lessons|工程教训]]

## 概述

BrickHub 2.0 的核心目标是打造对标 Mecabricks 的**“可互动拖拽、可动态拆解的在线拼搭工厂”**。为实现数万级零件的高性能渲染与丝滑的拼搭交互，本白皮书针对四大核心技术难题进行了深度调研，并给出了明确的架构选型与代码级实现思路。

---

## 核心技术攻坚方案

### 1. 按需加载与缓存架构：极速秒开设计

**痛点：** LDraw 模型包含海量 `.dat` 和 `.ldr` 零件库文件，传统的 HTTP 请求会导致严重的阻塞和网络开销。

**业内标准做法：**
结合 Three.js 的 `LDrawLoader`、外部 CDN 分发与浏览器 `IndexedDB` 离线缓存，实现网络请求的全面拦截与本地加速。

**具体实现思路：**
- **Service Worker / IndexedDB 拦截层**：使用 `localforage` 或直接操作 `IndexedDB`。重写 `LDrawLoader` 的 `FileLoader` 逻辑（或者在网络层通过 Service Worker 拦截 `fetch` 请求）。
- **按需拉取与缓存**：当请求某个零件如 `3001.dat` 时：
  1. 优先查询 `IndexedDB` 是否存在该零件的解析后数据（BufferGeometry 甚至序列化后的对象）或原始文本。
  2. 若未命中，则通过 CDN 并发拉取，解析完成后异步存入 `IndexedDB`。
- **解析优化**：LDraw 文件解析是 CPU 密集型任务，应将 `LDrawLoader` 的解析过程（正则表达式匹配、顶点生成）放入 Web Worker 中执行，避免阻塞主线程，解析后将 ArrayBuffer 转移（Transferable Objects）回主线程。

### 2. “性能与交互的死局”突破：Instancing 与单体交互

**痛点：** 数万个零件如果使用独立的 `Mesh` 会导致严重的 Draw Call 瓶颈。使用 `InstancedMesh` 可以保证 60FPS，但实例渲染极难做单体级别的拖拽和点击高亮。

**业内标准做法：**
**“静态合批，动态抽离” (Static Instancing, Dynamic Extraction)**。

**具体实现思路与结论：**
- **初始状态（静态展示）**：将相同类型和颜色的零件合并入同一个 `InstancedMesh`。
- **选中与高亮（Hover/Select）**：
  - 通过 `Raycaster` 命中 `InstancedMesh`，获取 `instanceId`。
  - **高亮处理**：无需剥离，可通过向 Shader 传递一个选中状态的 uniform 数组，或者更简单地，在命中位置动态生成一个稍微放大且开启背面剔除（Back-face culling）的半透明/发光边框外壳（Shell Mesh）。
- **拖拽与编辑（Drag/Edit）**：
  1. **抽离 (Extraction)**：当鼠标按下开始拖拽时，根据 `instanceId` 获取对应的变换矩阵（`getMatrixAt`）。
  2. **隐藏实例**：将该 `instanceId` 对应的矩阵缩放设为 0（`matrix.makeScale(0, 0, 0)`），更新 `instanceMatrix.needsUpdate = true`，使其在视觉上消失。
  3. **生成独立 Mesh**：在相同位置瞬间实例化一个普通的 `Mesh`（复用相同的 Geometry 和 Material），交由 `TransformControls` 或拖拽逻辑接管。
  4. **合批 (Re-instancing)**：拖拽放下后，获取独立 `Mesh` 的新矩阵，更新回 `InstancedMesh` 的对应 `instanceId` 矩阵中，并销毁临时 `Mesh`。

### 3. 动态拆解与自动吸附 (Snapping)

**痛点：** 乐高特有的网格对齐（Grid Snapping）与凸起/凹槽（Stud & Tube/Hole）捕捉计算复杂；按步骤动态拆解需要严谨的场景图管理。

**业内标准做法：**
空间哈希网格系统（Spatial Hash Grid）+ LDraw 步骤层级树。

**具体实现思路：**
- **LDU (LDraw Unit) 对齐系统**：乐高的基础单位是 LDU (1 LDU ≈ 0.4mm)。砖块的宽高通常是 20 LDU（1 个颗粒间距），高度是 24 LDU。在 Three.js 中建立严格的基于 LDU 的网格坐标系。拖拽时的平移采用舍入到最近 20/24 LDU 倍数的步进系统（Step translation）。
- **连接点捕捉 (Stud/Tube Collision)**：
  - 并非使用物理引擎进行网格碰撞，而是**语义化连接点**。为每种基础零件定义其底部的凹槽包围盒和顶部的凸起坐标列阵。
  - 当拖拽中的零件 A 靠近零件 B 时，计算 A 的底部吸附面与 B 的顶部凸起集合的距离。当距离小于阈值（如 10 LDU）时，触发矩阵自动吸附（Snap），更新临时 Mesh 的位置。
- **步骤树与 Scene Graph 管理**：
  - LDraw 文件原生包含 `0 STEP` 指令。解析时，构建一个嵌套的 `Group` 树：`Model -> StepGroup -> Parts`。
  - **动态拆解播放**：提供一个时间轴控制器。切换 Step 时，通过遍历遍历控制后续 StepGroup 中零件的 `visible` 属性，或赋予材质溶解/淡入淡出的动画（Tween.js）。

### 4. 专业视觉渲染：条件线与 ABS 塑料材质

**痛点：** 乐高模型渲染必须具备特有的硬表面边缘线（Conditional Lines）以及 ABS 塑料特有的光泽和微表面划痕质感。

**业内标准做法：**
结合 Three.js 高级线段渲染器与 `MeshPhysicalMaterial`，配合环境光遮蔽（AO）和基于图像的照明（IBL/HDRI）。

**具体实现思路：**
- **条件线渲染 (Conditional Lines)**：
  - LDraw 格式中包含了类型 5 的条件线段（仅在特定角度下可见的轮廓线）。
  - 使用 `@react-three/drei` 中的 `Edges` 或 Three.js 源码中的 `LineSegmentsGeometry` + `LineMaterial`。通过自定义 Shader，结合法线夹角阈值和摄像机视角计算，动态控制线段的透明度或显隐，消除传统边缘线在曲面上的突兀感。
- **ABS 塑料材质 (Clearcoat)**：
  - 弃用传统的 `MeshStandardMaterial`，全面升级为 `MeshPhysicalMaterial`。
  - **核心参数配置**：
    - `roughness`: 0.1 - 0.2（保持一定的光滑度）。
    - `metalness`: 0.0（纯非金属）。
    - `clearcoat`: 1.0（增加清漆涂层，模拟 ABS 注塑成型的高光）。
    - `clearcoatRoughness`: 0.1（涂层本身的极低粗糙度）。
  - **微表面细节**：引入法线贴图（Normal Map）添加极其微小的注塑纹理或轻微的指纹/划痕瑕疵，提升照片级真实感。
  - **倒角 (Beveling)**：如果不使用极高精度的模型，可在材质中使用法线贴图模拟边缘倒角，或利用 Three.js 的 `EdgeSplitModifier` 配合自定义 Shader 渲染高光边缘。

---
**结论：** 
BrickHub 2.0 的互动引擎将基于上述技术栈构建，实现极速加载、极致性能、精准交互与照片级渲染的完美平衡。

## 五、 站点性能与多人并发压力评估

针对高并发与多人同时操作的场景，本架构设计不仅能够有效避免站点崩溃，更能轻松扛住极高并发。核心支撑点如下：

### 1. 算力下沉（零服务端渲染压力）
WebGL / Three.js 的所有渲染工作 100% 运行在用户的浏览器和本地 GPU 上。服务器不需要为哪怕一块积木计算光影、材质或几何变换。因此，即使有 1 万个用户同时在线拼搭，对服务器的 CPU 渲染压力也是 0。这实现了彻底的算力下沉。

### 2. 流量剥离（零带宽瓶颈）
得益于“外部 CDN 分发零件库 + 浏览器 IndexedDB 缓存”架构，极度消耗资源的“大文件下载”带来的带宽压力被完全剥离。服务器端仅负责吐出极小的初始 HTML/JS 框架页面。核心 3D 资产均走边缘 CDN 节点并缓存在本地，从根本上消除了带宽瓶颈。

### 3. 多人协同拼搭的增量同步（如 Figma 模式）
如果要实现真正的“多人同一个房间同时拖拽拼搭”，服务器只作为“信令中转站”。采用 CRDT 算法（如 Yjs）+ WebSocket，服务器只负责转发极轻量的 JSON 坐标变化数据（例如：“用户A 把零件 3001 移动到了 x,y,z”），数据包在 KB 级别，单台普通 Node.js 服务器就能扛住数千人的高频协同操作。
