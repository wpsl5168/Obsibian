# Safety AI · 决策记录（ADR）

## ADR-001：交付模式 = 私有交付（一客户一套）
- **日期**：2026-05-03
- **决策**：放弃 SaaS 多租户路线，所有客户独立部署
- **理由**：
  - 工地/电力/化工客户对数据敏感度高
  - 私部能避开 ICP 备案、跨境数据等合规问题
  - 单租户实现简单，可快速 v1 上线
- **影响**：必须做"一键安装包"，必须做客户白标，运维成本上升

## ADR-002：工程师端 = APK（不做小程序）
- **日期**：2026-05-03
- **决策**：v1 只交付 APK，H5 作 fallback，**不做微信小程序**
- **理由**：
  - 小程序需 ICP 备案（`brickhub.cc` 在 Azure 海外，无法备案）
  - APK 拍照体验+离线缓存最稳
  - 工地场景手机分发可控
- **影响**：iOS 用户无法用（v1 不支持）；APK 分发靠扫码

## ADR-003：行业策略 = 通用内核 + 行业模板包
- **日期**：2026-05-03
- **决策**：内核一套规则引擎，每个行业一份 YAML 模板包
- **理由**：
  - 单一行业市场太窄
  - 通用规则只能解决 30%，必须有行业深度
  - 模板包可独立维护、独立销售
- **影响**：必须建立行业专家访谈机制；模板包 = 核心资产

## ADR-004：AI = OpenRouter（VLM 走云）
- **日期**：2026-05-03
- **决策**：VLM 全部走 OpenRouter，不自部署模型
- **理由**：
  - 自部署 GPU 成本极高
  - OpenRouter 多模型可路由，灵活
  - 客户成本透明（按调用付费）
- **影响**：客户内网必须能访问 openrouter.ai；后期需预研国产模型本地化

## ADR-005：技术栈 = FastAPI + Next.js + Docker Compose
- **日期**：2026-05-03
- **决策**：与 BrickHub 同栈
- **理由**：复用经验，降低学习成本

## ADR-006：进程守护 = systemd（不用 PM2）
- **日期**：2026-05-03
- **决策**：私部统一 systemd user unit
- **理由**：
  - PM2 daemon 在 brickhub 上多次死掉
  - systemd 是 Linux 原生，最稳
- **影响**：开发 install.sh 时必须生成 systemd unit 模板
