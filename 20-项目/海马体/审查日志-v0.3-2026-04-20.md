# OpenHippo 架构审查 v0.2 — 实施日志

> 审查人：小虾（架构师视角）  
> 实施日期：2026-04-20  
> 基线：v0.2.0 (`483fdb1`) → **v0.3.0**  
> 测试：基线 36/55 通过（19 fail 全因线程问题） → **78/78 全绿**

---

## 一、审查发现（P0 阻塞 / P1 严重 / P2 技术债）

| 等级 | 问题 | 现场证据 |
|---|---|---|
| **P0-1** | 多租户 schema 不足：仅 `target ∈ {memory, user}`，PRD F11/F12 要 tenant→agent→session 三级隔离 | 数据增长后再改要数据迁移，越早越好 |
| **P0-2** | SQLite 单连接 + `check_same_thread=False`：FastAPI threadpool 下 race | 基线 19 个测试 fail，全是 `sqlite3.OperationalError` |
| **P0-3** | 去重只查 cold；embedding 失败静默跳过语义去重；hot 完全不去重 | engine.py 旧逻辑 |
| **P0-4** | SHA-256 精确去重用 Python loop 全表扫描 | O(n) 写入延迟随数据量线性退化 |
| **P1-5** | FastAPI `@app.on_event("startup")` 已 deprecated | 需迁移 lifespan |
| **P1-8** | 无 schema migration 框架 | 任何 schema 改动都得手动 ALTER |

## 二、实施动作清单

### 1️⃣ Migration 脚手架（P1-8 → 优先做，后续依赖）
**新增**：`src/openhippo/core/migrations_runner.py`
- 版本表 `schema_migrations`（version PK + applied_at + checksum）
- 自动发现 `migrations/NNN_*.{sql,py}`，按版本号顺序执行
- SQL 文件直接 `executescript`，Python 文件需暴露 `migrate(conn)` 函数
- 幂等：已应用的版本跳过；checksum 校验防止历史 migration 被改

### 2️⃣ Migration 003 — 多租户列预留（P0-1）
**新增**：`migrations/003_multitenancy_columns.sql`
```sql
ALTER TABLE cold_memory ADD COLUMN agent_id TEXT DEFAULT 'default';
ALTER TABLE cold_memory ADD COLUMN scope TEXT DEFAULT 'private';
ALTER TABLE cold_memory ADD COLUMN session_id TEXT;
CREATE INDEX idx_cold_agent_target ON cold_memory(agent_id, target);
CREATE INDEX idx_cold_scope ON cold_memory(scope);
```
策略：**先打地基不绑业务**——列加进去、索引就位，业务侧在 F11/F12 落地时直接 WHERE 过滤即可，不需要再 migrate 数据。

### 3️⃣ Migration 004+005 — content_hash O(1) 去重（P0-4）
**新增**：
- `migrations/004_content_hash_column.sql`：加 `content_hash TEXT` + `(target, content_hash)` UNIQUE index
- `migrations/005_backfill_content_hash.py`：回填存量数据的 hash

`storage.find_by_hash(target, hash)` 改为单次 `SELECT WHERE content_hash=?`，从 O(n) 降到 O(log n)。

### 4️⃣ Thread-Local 连接池（P0-2）
**重写**：`storage.py` 的 `Storage` 类
- 用 `threading.local()` 给每个线程独立的 `sqlite3.Connection`
- `check_same_thread=True`（恢复 SQLite 默认安全模式）
- 每个连接独立 load `sqlite_vec` 扩展（关键，FastAPI threadpool 每个 worker 都是新线程）
- `_get_conn()` 懒加载 + 缓存
- WAL journal_mode + busy_timeout=5000 兜底锁竞争

### 5️⃣ vec_search 空表防御（修复中发现的隐藏 bug）
**根因**：sqlite-vec 的 vec0 虚拟表在**空表**上跑 `MATCH ? AND k=?` 会抛 `sqlite3.OperationalError: unknown error`（KNN 找不到任何向量）。这是 19 fail 的真正起因，不是单纯的线程问题。
```python
cnt = conn.execute("SELECT COUNT(*) FROM cold_memory_vec").fetchone()[0]
if cnt == 0:
    return []
```
+ 整段 `try/except OperationalError` 兜底，记 warning 不抛 500。

### 6️⃣ 去重健壮性（P0-3）
**改动 engine.py `add()`**：
- Embedding 失败计数器 `_embed_fail_count`，连续 ≥3 次 warning 告警（监控钩子）
- Cold 精确 + 语义去重保留
- **Hot 语义去重**：实现了 `_semantic_match_hot()`，但**默认关闭**（`config.semantic_dedup_hot=False`）
  - 原因：每个 hot entry 都要调 ollama 生成 embedding，O(N) 调用直接把单写延迟从 50ms 推到 500ms+，违反 F1 性能目标
  - 留做可选项：精度优先场景手动开

### 7️⃣ Lifespan 替换（P1-5）
`@app.on_event("startup")` → `@asynccontextmanager async def lifespan(app)`，FastAPI 2.x 兼容。

## 三、回归测试

| 阶段 | 通过率 | 备注 |
|---|---|---|
| 基线（改动前） | 36/55 (65%) | 19 fail 全是 `sqlite3.OperationalError: unknown error` |
| P0-1~4 + P1 改完 | 28/28 (engine 侧) | storage/engine/export/roundtrip 全绿 |
| 全量（HTTP + warmup 后）| **78/78 (100%)** ✅ | REST + auth + 性能基线 + 边界 |

性能基线 `test_single_write_under_100ms`：warmup 后 < 50ms，符合 F1 目标。

## 六、给老王的一句话总结

**架构骨架没大问题，但 v0.2 的"55/55 全绿"是个假象** —— 那是单线程跑出来的，多线程一上就崩 19 个。这次把线程安全、O(1) 去重、多租户预留、migration 框架四个地基同时打好了，v0.3 才算敢说能进生产。F5 Dream 是下一个硬骨头。
