# F5 统一软删除管线设计 v0.1

**作者**: 小虾
**日期**: 2026-04-21
**状态**: 草稿，待架构审核
**关联**: F5-Dream设计-v0.1.md

## 1. 问题陈述

当前 OpenHippo 所有"删除"语义（用户 remove、测试 teardown、dream consolidate）都是**物理 DELETE**：

- 风险高：误删无法恢复（小虾刚刚就差点删坏 FTS 索引）
- 违反 F5 零信任原则：老王明确要求 "never hard delete, only mark dormant"
- 缺乏审查窗口：删完就没了，没机会"睡一晚醒来后悔"
- 测试残渣 39 条说明物理删除路径还会留孤儿（FTS5/vec 同步漏洞）

## 2. 设计目标

**所有删除操作统一收口为"打 dormant 标记"，由 dream 物理清理 job 在隔离审查窗口后执行真正的物理删除。**

### 核心原则

1. **无差别软删除**：用户主动删 / 测试 teardown / dream consolidate / extraction noise，**全部**走同一条软删除路径
2. **可追溯**：每条 dormant 记录必须带 `marked_by`（谁打的）+ `marked_reason`（为啥打）
3. **可恢复**：审查窗口内（默认 7 天）随时可 restore
4. **审查窗口结束后才物理删除**，且物理删除也要走正确的级联路径
5. **召回不返回 dormant**：搜索/timeline/hot 注入都自动过滤 `dream_status='dormant'`

## 3. 数据模型变更

### 3.1 新增 dream_status 状态值

```
'active'        ← 现存，正常活跃
'consolidated'  ← 现存，已被 dream 合并入新条目
'dormant'       ← 新增，待审查删除
```

### 3.2 cold_memory 新增字段（迁移 010_dormant_metadata.sql）

```sql
ALTER TABLE cold_memory ADD COLUMN marked_dormant_at REAL;
ALTER TABLE cold_memory ADD COLUMN marked_by TEXT;        -- 'user'|'test'|'dream-consolidate'|'extraction-noise'|'duplicate-cleanup'
ALTER TABLE cold_memory ADD COLUMN dormant_reason TEXT;   -- 自由文本说明
ALTER TABLE cold_memory ADD COLUMN purge_after REAL;      -- 物理删除截止时间戳
CREATE INDEX idx_cold_dormant ON cold_memory(dream_status, purge_after) WHERE dream_status='dormant';
```

### 3.3 hot_memory / hot_user_memory 同步加字段

热层也需要软删除（用户在对话里说"忘掉这条"时不能立刻物理删）：
```sql
ALTER TABLE hot_memory ADD COLUMN dream_status TEXT DEFAULT 'active';
ALTER TABLE hot_memory ADD COLUMN marked_dormant_at REAL;
ALTER TABLE hot_memory ADD COLUMN marked_by TEXT;
ALTER TABLE hot_memory ADD COLUMN dormant_reason TEXT;
ALTER TABLE hot_memory ADD COLUMN purge_after REAL;
-- 同样加 user 表
```

## 4. API 变更

### 4.1 现有 remove/archive 行为变更（重大变更，需版本号 0.5.0）

| 端点 | 旧行为 | 新行为 |
|------|--------|--------|
| `POST /v1/memories/remove` | 物理 DELETE 行 | UPDATE 设置 dream_status='dormant', marked_by='user' |
| `POST /v1/memories/archive` | hot→cold 物理迁移 | 不变（archive ≠ delete） |
| `DELETE /v1/memories/{id}` | 物理 DELETE | 同上软删除 |

### 4.2 新增端点

```
POST /v1/dormant/mark       — 显式打 dormant 标记（test 套件用，可指定 marked_by）
POST /v1/dormant/restore    — 复用现有 /dream/restore/{id}
GET  /v1/dormant/list       — 列出所有 dormant 条目（带筛选：marked_by/marked_after）
POST /v1/dormant/purge      — 立即物理清除已过 purge_after 的条目（仅 dream cron 调用）
GET  /v1/dormant/preview    — Dry-run：列出本次 purge 会删什么
```

### 4.3 召回过滤

所有 `vec_search/fts_search/get_hot/get_timeline` SQL 必须加 `WHERE dream_status != 'dormant'` 条件。

## 5. Dream 物理清理 Job

### 5.1 触发方式

- **定时**：每日 04:00 UTC cron 执行 `POST /v1/dormant/purge`
- **手动**：架构师审核后可手动触发，必须先调 `/preview`

### 5.2 物理删除的正确路径（吸取教训）

```python
def physical_purge(conn, ids: list[str]):
    """正确的级联删除顺序，绝对不可手动 DELETE FROM cold_memory_fts。"""
    ph = ",".join("?"*len(ids))
    # 1. 先删 vec0 表（无 trigger 联动，必须手动；关联键是 memory_id 不是 rowid）
    conn.execute(f"DELETE FROM cold_memory_vec WHERE memory_id IN ({ph})", ids)
    # 2. 删主表 cold_memory
    #    FTS5 是 content=cold_memory 外部内容模式
    #    cold_memory_ad trigger 会自动同步删除 FTS，禁止手动删 FTS！
    conn.execute(f"DELETE FROM cold_memory WHERE id IN ({ph})", ids)
    # 3. integrity_check 验证
    chk = conn.execute("PRAGMA integrity_check").fetchone()[0]
    assert chk == "ok", f"Purge corrupted DB: {chk}"
```

### 5.3 审计

每次 purge 写入 `dream_actions` 表：
```
action='physical_purge'
details=JSON{ids, marked_by, marked_reason, purged_at, integrity_check}
```

## 6. 审查窗口策略

| marked_by | 默认审查窗口 | 理由 |
|-----------|-------------|------|
| `user` | 7 天 | 用户最易后悔，给最长窗口 |
| `dream-consolidate` | 14 天 | 合并产物可能丢失细节，给更长 |
| `extraction-noise` | 3 天 | 自动识别的噪声，老王可干预 |
| `test` | 1 小时 | 测试残渣明确无价值 |
| `duplicate-cleanup` | 3 天 | 去重判断可能误判 |

可通过环境变量 `HIPPO_DORMANT_WINDOW_<KEY>` 覆盖。

## 7. 历史数据回填

### 7.1 现存 39 条测试残渣处理

**不要立刻物理删**，而是：
```sql
UPDATE cold_memory
SET dream_status='dormant',
    marked_by='test',
    dormant_reason='Historical test residue cleanup',
    marked_dormant_at=unixepoch('now'),
    purge_after=unixepoch('now')+3600
WHERE content LIKE '[T_%]%' OR content LIKE '[T1.%' OR content LIKE '[perf_%]%';
```

1 小时后由首次 dream purge 物理清除（且 dry-run 老王确认）。

### 7.2 现存 12 条 ghost / 4 条 snapshot

- **Snapshot dumps**：保留，这是 hermes 自动备份链路（`on_session_start` hook 写入），可考虑迁移到独立表 `system_snapshots`
- **Ghosts**：标记 `marked_by='legacy-orphan'`，`purge_after=NULL`（永不自动删），等老王人工审

## 10. 风险评估

| 风险 | 严重度 | 缓解 |
|------|--------|------|
| 误把生产条目标记 dormant | 高 | 1. mark API 必须带 reason；2. dry-run 必跑；3. 审查窗口可恢复 |
| 物理 purge 破坏 DB | 高 | 1. 走严格级联顺序；2. purge 前自动备份；3. integrity_check 失败回滚 |
| 召回过滤遗漏 → dormant 泄漏 | 中 | 单元测试覆盖所有 search 路径，新增 dormant 的查询不能命中 |
| dormant 占用空间持续增长 | 低 | metrics 监控，超过阈值告警 |
| API 兼容性破坏（remove 行为变） | 中 | 版本号 0.5.0，CHANGELOG 显式说明 |

## 11. 不在本期范围

- Hot 层 LRU 自动淘汰（独立设计）
- 跨 agent 的 dormant 同步
- 用户级 dormant 配额管理
