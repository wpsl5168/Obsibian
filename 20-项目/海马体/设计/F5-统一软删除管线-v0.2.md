## 1. 问题陈述

OpenHippo 当前所有"删除"语义都走**物理 DELETE**，三处现存物理删点（`grep` 实测）：

| 文件 | 行 | 路径 |
|---|---|---|
| `core/storage.py` | 256 | `hot_remove()` 直接 `DELETE FROM hot_memory` |
| `core/storage.py` | 389 | `cold_delete()` 直接 `DELETE FROM cold_memory` + `vec_delete` |
| `core/dream.py` | 多处 | consolidate 物理删冗余记录 |

**风险**：
- 误删无法恢复（小虾 2026-04-21 差点删坏 FTS 索引，事务回滚救命）
- 违反 F5 零信任铁律：**never hard delete, only mark dormant**
- 缺审查窗口：删完即没，没机会"睡一晚醒来后悔"
- 23 条测试残渣证明物理删路径会留孤儿（FTS5 / vec0 同步漏洞）

## 2. 设计目标

**所有删除语义统一收口为"打 dormant 标记 + dream_actions 审计 + 隔离审查窗口后由 dream purge job 物理清理"。**

### 核心原则

1. **无差别软删除**：用户 remove / API delete / dream consolidate / 测试 teardown，**全部**走同一路径
2. **可追溯**：dream_actions 记录 `action='mark_dormant'` + `details.reason` + `details.actor`
3. **可恢复**：审查窗口内（默认 14 天，可配）走 `/v1/dream/restore/{id}` 复活
4. **审查到期才物理删**：dream purge job 周期性消费 `dormant + last_dream_at < now-14d`
5. **召回过滤 dormant**：`cold_search(include_dormant=False)` 默认值已实现
6. **禁后门**：不开放 immediate hard delete 开关，pattern 删除也必须走软删管线

## 3. 数据模型变更（基于现状盘点）

### 3.1 cold_memory：复用现有字段，只补索引 + CHECK

现状（`007_dream_columns.sql`）：
```sql
ALTER TABLE cold_memory ADD COLUMN dream_status TEXT DEFAULT 'active';
-- 取值: 'active' | 'dormant' | 'consolidated'
ALTER TABLE cold_memory ADD COLUMN last_dream_at TEXT;
CREATE INDEX idx_cold_dream_status ON cold_memory(dream_status, last_dream_at);
```

v0.2 新增 `migrations/011_dormant_constraints.sql`：
```sql
-- 1. 加 CHECK 约束防野值（SQLite 不支持 ADD CONSTRAINT，靠 trigger）
CREATE TRIGGER IF NOT EXISTS cold_memory_dream_status_check
BEFORE INSERT ON cold_memory
WHEN NEW.dream_status NOT IN ('active', 'dormant', 'consolidated')
BEGIN
  SELECT RAISE(ABORT, 'invalid dream_status');
END;

CREATE TRIGGER IF NOT EXISTS cold_memory_dream_status_check_upd
BEFORE UPDATE OF dream_status ON cold_memory
WHEN NEW.dream_status NOT IN ('active', 'dormant', 'consolidated')
BEGIN
  SELECT RAISE(ABORT, 'invalid dream_status');
END;

-- 2. 新增 marked_by / marked_reason 元数据列（审计三元组）
ALTER TABLE cold_memory ADD COLUMN marked_by TEXT;       -- 'user' | 'api' | 'dream:consolidate' | 'test'
ALTER TABLE cold_memory ADD COLUMN marked_reason TEXT;   -- 自由文本

-- 3. 索引：purge job 扫描 dormant 到期记录的热路径
CREATE INDEX IF NOT EXISTS idx_cold_dormant_purge
  ON cold_memory(dream_status, last_dream_at) WHERE dream_status = 'dormant';
```

### 3.2 hot_memory：**不动**

依据：B4。hot 表是窄注入表，加字段破坏 char 容量不变量。
策略：hot 删除 = `hot_remove + cold_add(source='archived_dormant') + mark dormant`，复用现成 `archive()` 函数，零侵入 hot schema。

### 3.3 dream_actions：扩 action 枚举

现状（`008_dream_actions.sql`）：
- 表已存在，含 `action TEXT NOT NULL`
- 无 CHECK 约束，当前实际取值：`consolidate_member` / `consolidate_seed`

v0.2 `migrations/012_dream_action_enum.sql`：
```sql
-- 仅加 CHECK 约束 + 新枚举值，不改表结构
CREATE TRIGGER IF NOT EXISTS dream_actions_enum_check
BEFORE INSERT ON dream_actions
WHEN NEW.action NOT IN (
  'consolidate_member', 'consolidate_seed',
  'mark_dormant', 'restore_dormant', 'purge_dormant'
)
BEGIN
  SELECT RAISE(ABORT, 'invalid dream_action: ' || NEW.action);
END;
```

`details` JSON 约定（`mark_dormant`）：
```json
{"actor": "user|api|test", "reason": "user_remove|api_delete|consolidate|...",
 "source_tier": "hot|cold", "original_id": "<hot_id if from hot>"}
```

### 4.2 storage 层改动（PR-1 核心）

```python
# storage.py 新增私有方法
def _mark_dormant(self, memory_id: str, *, actor: str, reason: str,
                  source_tier: str, original_id: str | None = None) -> dict:
    """统一软删入口。所有删路径必须经过这里。"""
    conn = self._get_conn()
    now = utcnow_iso()
    conn.execute(
        "UPDATE cold_memory SET dream_status='dormant', last_dream_at=?, "
        "marked_by=?, marked_reason=? WHERE id=?",
        (now, actor, reason, memory_id),
    )
    conn.execute(
        "INSERT INTO dream_actions(dream_run_id, action, memory_id, details, created_at) "
        "VALUES (?, 'mark_dormant', ?, ?, ?)",
        (f"manual:{now}", memory_id,
         json.dumps({"actor": actor, "reason": reason,
                     "source_tier": source_tier, "original_id": original_id}), now),
    )
    conn.commit()
    return {"id": memory_id, "status": "dormant"}

# hot_remove 改造：不再直接 DELETE
def hot_remove(self, target, old_text):
    # 原物理删 → 改 archive→cold→mark_dormant
    archived = self.archive(target, old_text)        # hot DELETE + cold INSERT
    if "error" in archived: return archived
    return self._mark_dormant(archived["cold_id"],
        actor="user", reason="hot_remove", source_tier="hot",
        original_id=archived["hot_id"])

# cold_delete 改造
def cold_delete(self, memory_id):
    # 原 DELETE + vec_delete → 改 mark_dormant（保留行 + 保留 vec）
    return self._mark_dormant(memory_id,
        actor="api", reason="cold_delete", source_tier="cold")
```

**关键不变量**：
- mark_dormant **不动 cold_memory_vec**（向量保留，purge 时统一删，避免 dormant→restore 后重新 embed）
- mark_dormant **不动 cold_memory_fts**（外部内容表自动跟随主表，主表行还在，FTS 也在）
- 召回过滤靠 `cold_search(include_dormant=False)` —— 已存在，行为不变

### 4.3 dream purge job（PR-3）

新增 `core/dream.py::purge_overdue_dormant()`：
```python
def purge_overdue_dormant(retention_days: int = 14, batch_size: int = 100):
    """物理清理：dormant 且 last_dream_at < now - retention_days 的记录。
    这是全系统唯一被允许执行 DELETE FROM cold_memory 的函数。"""
    cutoff = (utcnow() - timedelta(days=retention_days)).isoformat()
    rows = conn.execute(
        "SELECT id FROM cold_memory WHERE dream_status='dormant' "
        "AND last_dream_at < ? LIMIT ?", (cutoff, batch_size)).fetchall()
    for (mid,) in rows:
        # 正确级联：先 vec，再主表（FTS 由 cold_memory_ad trigger 自动）
        conn.execute("DELETE FROM cold_memory_vec WHERE memory_id=?", (mid,))
        conn.execute("DELETE FROM cold_memory WHERE id=?", (mid,))
        log_dream_action(action='purge_dormant', memory_id=mid,
                         details={"retention_days": retention_days})
    # integrity_check 兜底
    assert conn.execute("PRAGMA integrity_check").fetchone()[0] == "ok"
```

## 7. 8 个开放问题决策汇总

| # | 问题 | 决策 | 依据 |
|---|---|---|---|
| 1 | 用户 remove 是否开 immediate 开关 | **不开**，统一软删 | F5 铁律。立即删走 dream purge 主动消费 |
| 2 | hot 层 dormant 方案 | **不在 hot 加字段**，archive→cold→mark dormant | B4，hot 窄表不变 |
| 3 | dream_actions 复用 vs 新建 | **复用** dream_actions，扩 3 个 action 枚举 | 审计 trail 统一，restore 端点不动 |
| 4 | PR 拆分 | **3-PR 渐进**，PR-3 须 PR-2 上线 ≥14 天后再 merge | 数据沉淀验证 + 独立回滚 |
| 5 | mark API pattern 直连 | **禁用**，pattern 必须走 remove() 软删管线 | 否则破 F5 |
| 6 | 23 条残渣是否人工 review | **不需要**，走新管线打 dormant，14 天到期自动清 | 验证管线即清残渣，一举两得 |
| 7 | agent_id 隔离范围 | **本期不动**，沿用现有 `__local__`+agent_id 模型 | storage 已完整支持，多租户独立议题 |
| 8 | snapshot 是否单独建表 | **不建表**，靠 `source='snapshot'` 区分；purge 时单独定保留期 | source 字段已存在，残渣 source=NULL 不影响 |

## 9. 风险与兜底

| 风险 | 概率 | 影响 | 兜底 |
|---|---|---|---|
| dormant 累积撑大 cold 表 | 中 | 查询变慢 | `idx_cold_dormant_purge` 部分索引 + purge job 每日跑 |
| restore 后 vec 不一致 | 低 | 召回不准 | mark dormant **不删 vec**，restore 直接可用 |
| purge job 删错 | 低 | 数据丢失 | purge 前 `PRAGMA integrity_check`，DELETE 限批量 100 + 事务 |
| migration 011/012 顺序错 | 低 | 启动失败 | trigger CHECK 是幂等的，CREATE IF NOT EXISTS |
| 老 dream_actions 行无 CHECK | — | 历史数据冲突 | trigger 只对新 INSERT 生效，老数据不动 |
