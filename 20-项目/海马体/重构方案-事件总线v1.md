# 海马体重构方案 v1.0 — 事件总线架构

> 决策人：老王 | 起草：小虾 | 状态：待审批后实施
> 触发原因：2026-04-21 发现 Hermes Gateway 重启 22h 后 OpenHippo 0次 hook 调用，90条飞书消息全丢
> 根因：当前 plugin 架构 monkey-patch 宿主 + 业务逻辑外漏 + 命运绑死 hermes 内部事件总线

---

## 一、问题陈述

### 1.1 症状
- Gateway 启动 22 小时，0 次 OpenHippo hook 触发
- 今日 90 条飞书消息、全部 Telegram 对话**完全丢失**
- 历史 77 条 `OpenHippo injected` 日志全部来自 CLI session（`[YYYYMMDD_xxx]`），无一来自 gateway 路径

### 1.2 第一性原理诊断

> **当前架构把"记忆系统的命运"绑在了"宿主进程的内部事件总线"上。**
> 宿主一个 bug，记忆系统就停摆——违反关注点分离和故障隔离。

| 当前 plugin 模块 | 行数占比 | 性质 | 应该归谁 |
|---|---|---|---|
| HTTP 调用 + WAL + 重试 | 30% | 通用基础设施 | 通用 SDK |
| `_should_extract` 规则提取 | 10% | 业务逻辑 | **海马体服务端** |
| MEMORY.md/USER.md 快照 | 15% | Hermes 私有 | **下沉到事件 schema** |
| `_install_memory_tool_shim()` monkey-patch | 10% | 🔴 入侵宿主 | **删除** |
| 4 个 Hook 回调 | 30% | 适配器 | ✅ 保留但极度精简 |
| 其他工具函数 | 5% | — | — |

**整体评分**：通用性 0/10、零入侵 3/10、简洁性 5/10。

### 1.3 必须解决的根本矛盾
- 海马体定位：**通用记忆数据库即服务**，对标 Mem0 计划商业化
- 现实：海马体**只能跑在 Hermes 上**，且 Hermes 一坏就坏
- 矛盾：要么妥协通用性，要么彻底解耦

---

## 二、目标架构

### 2.1 总览

```
┌──────────────────────────────────────────────────────────────┐
│  任意 Agent 宿主 (Hermes / Claude Code / Codex / N8N / Dify)  │
│  ─────────                                                    │
│  仅做一件事：把对话/工具事件 fire-and-forget 推到 webhook       │
│  适配层 < 100 行，纯 IO，不含业务逻辑                            │
└────────────────────────┬─────────────────────────────────────┘
                         │ POST /v1/events  (CloudEvents 1.0)
                         │ {type, source, agent_id, session_id, data}
                         ▼
┌──────────────────────────────────────────────────────────────┐
│  OpenHippo (海马体) — 完全独立服务，可单机/可容器/可云            │
│  ┌──────────────┬─────────────┬──────────────┬─────────────┐ │
│  │ Event Bus    │ Memory      │ Dream Loop   │ Search      │ │
│  │ (asyncio     │ Engine      │ (existing)   │ API         │ │
│  │  in-proc)    │ (existing)  │              │ (existing)  │ │
│  └──────────────┴─────────────┴──────────────┴─────────────┘ │
│  - 自己决定哪些事件提取记忆（规则 / LLM / 可插拔）                │
│  - 自己处理重试 / WAL / 去重                                    │
│  - 自己暴露 metrics + 健康指标                                  │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 关键原则

| # | 原则 | 落地动作 |
|---|---|---|
| 1 | **协议标准化** | 用 CloudEvents 1.0 定义事件 schema |
| 2 | **薄适配器** | 每个宿主只写 ~50 行：捕获事件 → HTTP POST |
| 3 | **业务下沉** | 规则提取、快照、WAL、重试 全部回到服务端 |
| 4 | **零入侵** | 适配器只**读**宿主事件，从不 monkey-patch |
| 5 | **故障隔离** | 海马体宕机/网络断 → 适配器丢这条事件，agent 继续工作 |
| 6 | **可观测性** | `/metrics` 暴露 `events_received` / `extract_rate` / `last_event_at` |
| 7 | **可重放** | 服务端提供 `POST /v1/events/replay` 用于回灌 |

## 三、CloudEvents Schema 设计

### 3.1 通用信封（CloudEvents 1.0 标准）

```json
{
  "specversion": "1.0",
  "id": "evt_01HZX...",                    // 全局唯一
  "source": "/hermes/gateway",              // 谁产生的
  "type": "ai.openhippo.message.exchange",  // 事件类型
  "time": "2026-04-21T06:52:00Z",
  "datacontenttype": "application/json",
  "subject": "agent:main:feishu:dm:oc_xxx", // 业务主键(session)
  "agent_id": "hermes-default",             // 多租户key
  "data": { /* 类型特定 payload */ }
}
```

### 3.2 事件类型枚举

| type | 触发时机 | 服务端动作 |
|---|---|---|
| `ai.openhippo.session.start` | 新会话开始 | 触发 snapshot，注册 session |
| `ai.openhippo.session.end` | 会话终止 | flush 提取队列，归档 |
| `ai.openhippo.message.user` | 用户消息到达 | 入提取队列 + 触发 search 返回相关记忆 |
| `ai.openhippo.message.assistant` | LLM 回复完成 | 入提取队列（可异步） |
| `ai.openhippo.tool.call` | tool 调用完成 | memory 操作镜像；其他 tool 仅记录 |
| `ai.openhippo.memory.snapshot` | 宿主主动推送 hot memory 全量 | 内容寻址去重后入冷存储 |

### 3.3 事件 payload 示例

**message.user**：
```json
{
  "type": "ai.openhippo.message.user",
  "subject": "agent:main:feishu:dm:oc_xxx",
  "data": {
    "content": "继续",
    "user_id": "ou_9c360...",
    "platform": "feishu",
    "model": "claude-opus-4.7"
  }
}
```

**memory.snapshot**（替代当前 plugin 内的硬编码 MEMORY.md/USER.md 读取）：
```json
{
  "type": "ai.openhippo.memory.snapshot",
  "subject": "hermes-default",
  "data": {
    "scope": "agent",          // agent | user
    "format": "markdown_sections",
    "content": "...",          // MEMORY.md 全文
    "section_separator": "\n§\n"
  }
}
```

## 四、HTTP API 设计

### 4.1 写入路径

| Endpoint | 用途 | 同步性 |
|---|---|---|
| `POST /v1/events` | **核心** — 接收单个事件 | fire-and-forget，返回 202 + event_id |
| `POST /v1/events/batch` | 批量推送（适配器侧失败重传） | 同上 |
| `POST /v1/events/replay` | 回灌历史事件（带 dedup） | 同步，返回 ingested/skipped 计数 |

### 4.2 读取路径

| Endpoint | 用途 |
|---|---|
| `POST /v1/recall` | **新接口** — 一站式: 输入 user_message → 返回相关记忆（封装 search + ranking） |
| `GET /v1/events?since=...` | 审计：查事件流 |
| `GET /v1/metrics` | Prometheus 格式指标 |

### 4.3 兼容性

- 保留现有 `/v1/cold/memories` / `/v1/memories/search` / `/v1/dream/*`，**不破坏 v0.3 用户**
- 新事件接口为增量；旧 plugin 用户无感知

## 五、SDK 设计（hippo-sdk-py）

### 5.1 包结构（独立 pip 包）

```
hippo-sdk-py/
├── pyproject.toml
├── hippo_sdk/
│   ├── __init__.py
│   ├── client.py        # HippoClient — sync + async
│   ├── events.py        # 事件构造器
│   ├── adapters/
│   │   ├── hermes.py    # Hermes 适配器（plugin 入口）
│   │   ├── claude_code.py  # 预留
│   │   └── webhook.py   # 通用 webhook 适配器（N8N/Dify 用）
│   └── retry.py         # WAL + 指数退避（从 plugin 抽出来）
└── tests/
```

### 5.2 SDK 公共 API

```python
from hippo_sdk import HippoClient, Event

client = HippoClient(
    base_url="http://127.0.0.1:8200",
    agent_id="hermes-default",
    token="...",                       # 可选 Bearer
    timeout=0.1,                       # fire-and-forget 默认 100ms
    wal_dir="~/.hippo/wal",            # 失败时写本地 WAL
)

# 单条事件（异步触发，不阻塞）
client.emit(Event.message_user(
    subject="agent:main:feishu:dm:oc_xxx",
    content="继续",
    user_id="ou_xxx",
    platform="feishu",
))

# 一站式 recall（同步阻塞，<2s）
ctx = client.recall(
    subject="agent:main:feishu:dm:oc_xxx",
    user_message="继续",
    limit=5,
)
# ctx.context_text → 直接拼到 user message 里
```

### 5.3 Hermes 适配器（最终形态，~60 行）

```python
# ~/.hermes/plugins/openhippo_adapter/__init__.py
"""Hermes ↔ OpenHippo 薄适配器。零业务逻辑，只做事件透传。"""
from hippo_sdk import HippoClient, Event

_client = HippoClient.from_env()  # 读 HIPPO_URL / HIPPO_TOKEN

def register(ctx):
    ctx.register_hook("on_session_start", _on_session_start)
    ctx.register_hook("pre_llm_call",     _on_pre_llm_call)
    ctx.register_hook("post_llm_call",    _on_post_llm_call)
    ctx.register_hook("post_tool_call",   _on_post_tool_call)

def _on_session_start(session_id, model="", platform="", **kw):
    _client.emit(Event.session_start(
        subject=session_id, model=model, platform=platform))
    # 把 hot memory 一并推送（一次性快照）
    for scope, fname in [("agent", "MEMORY.md"), ("user", "USER.md")]:
        path = Path.home() / ".hermes" / "memories" / fname
        if path.exists():
            _client.emit(Event.memory_snapshot(
                subject=_client.agent_id, scope=scope,
                content=path.read_text(encoding="utf-8")))

def _on_pre_llm_call(session_id, user_message, **kw):
    # 同步 recall（<2s 阻塞）
    ctx = _client.recall(subject=session_id, user_message=user_message)
    # 异步 emit 事件
    _client.emit(Event.message_user(
        subject=session_id, content=user_message,
        user_id=kw.get("sender_id"), platform=kw.get("platform")))
    return {"context": ctx.context_text} if ctx.context_text else None

def _on_post_llm_call(session_id, user_message, response_text="", **kw):
    _client.emit(Event.message_assistant(
        subject=session_id, user_message=user_message,
        response=response_text, model=kw.get("model")))

def _on_post_tool_call(tool_name, args, result, session_id="", **kw):
    _client.emit(Event.tool_call(
        subject=session_id, tool_name=tool_name,
        args=args, result=result))
```

**对比当前 483 行**：60 行，无 monkey-patch，无 WAL，无 HTTP 重试，无规则提取——全部下沉。

## 六、服务端业务下沉清单

### 6.1 规则提取（原 plugin `_should_extract`）

```
~/.hippocampus/extractors/
├── default.yaml          # 默认规则（关键词 / 长度 / 否定词）
└── llm_extractor.py      # 可选 LLM 提取器（用 Ollama 本地小模型）
```

服务端在 `EventBus.consume(message.assistant)` 时按 pipeline 跑提取器，**用户可配置/可禁用/可换 LLM 提取器**。

### 6.2 快照（原 plugin `on_session_start` 内 MEMORY.md/USER.md 读取）

服务端收到 `memory.snapshot` 事件后：
- 内容寻址去重（content_hash UNIQUE）
- 自动按 `\n§\n` 拆条目入冷存储
- 适配器**不需要知道**文件格式细节

### 6.3 WAL / 重试

`HippoClient` 内置：
- 优先 fire-and-forget HTTP（100ms timeout）
- 失败写 `~/.hippo/wal/*.jsonl`
- 后台线程定期重放（指数退避）

适配器零感知。

## 七、Milestone 排期

| M | 工作 | 工时 | 验收 |
|---|---|---|---|
| **M1** | OpenHippo 服务端：`POST /v1/events` + `EventBus` + 6 类事件处理 | 1 天 | curl 推事件 → DB 出现记录 |
| **M2** | 抽出 `hippo-sdk-py` pip 包（client.py + events.py + retry.py） | 0.5 天 | `pip install -e` 后能 emit 事件 |
| **M3** | 写新 Hermes 适配器（60 行）+ 灰度并行运行（旧 plugin 暂留） | 0.5 天 | gateway 重启后 hook 100% 触发，metrics 可见 |
| **M4** | 服务端规则提取 + 快照下沉 | 0.5 天 | 旧 plugin 业务逻辑 100% 等价迁移 |
| **M5** | 回灌今天丢失的 90 条飞书消息（用 `/v1/events/replay`） | 0.5 天 | DB 中可搜索到当天对话 |
| **M6** | 删除旧 plugin + Hermes 侧 hook 调用点对账 + 文档 | 0.5 天 | `~/.hermes/plugins/openhippo/` 移除 |

**总计：3.5 天**（与之前估算一致）

### 灰度策略
- M3 完成后：**新旧 plugin 并行 7 天**
- 用 metrics 对账：`new_adapter.events_count == old_plugin.hook_invocations_count`
- 全绿后再 M6 删除旧 plugin

## 八、验收红线

| 红线 | 验证方法 |
|---|---|
| 海马体宕机时 Hermes 对话**0 影响** | systemd stop hippo + 跑 5 条对话 + 重启 + 验证 WAL 回放 |
| Hermes gateway 重启后 hook 100% 触发 | 重启 + 发 1 条消息 + 看 `/v1/metrics` 计数 +1 |
| 适配器代码 < 100 行（含注释） | `wc -l` |
| 服务端**不再依赖**任何 Hermes 特定路径/模块 | `grep -r "hermes\|MEMORY.md" src/openhippo/` 应返 0 |
| Claude Code 适配器可在 1 天内复刻 | 写 1 个 Claude Code adapter PoC |

## 九、风险与回滚

| 风险 | 缓解 |
|---|---|
| 服务端 EventBus 性能不足 | 用 asyncio.Queue + worker 池，先单进程，后续可换 NATS |
| recall 同步调用 >2s 阻塞 LLM | 设 800ms 硬超时，超时返空，不阻塞 |
| 灰度期间双写产生重复记忆 | content_hash UNIQUE 去重已就位 |
| 旧 plugin 已删但发现回归 | git revert + restore plugin（保留 7 天 backup tag） |
