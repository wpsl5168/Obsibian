结论

技术上有路径，但不应设计成“给聊天Agent交易密码，让它自由买卖”。推荐起步架构是：AI研究与草案 → 你逐单审核 → 独立风控 → 券商许可的交易接口 → 回报对账。AI不持有券商凭据、不拥有绕过风控的接口；实际委托由你控制的券商端或独立执行服务提交。

中信的普通交易条款明确涉及条件单、网格交易、算法单，说明原生智能委托能力确实存在；你的账户支持哪些类型、是否云端运行、触发与失效条件，仍须在客户端和营业部确认，不能从隐私条款推导完整产品合同。[7]

中信CATS网站确认其为中信自研的量化交易平台，覆盖数据、策略、算法与风控；这不证明普通个人账户已具备CATS/API权限。[4]

迅投官方文档确认MiniQMT的XtQuant交易模块支持报单、撤单、查询资产/持仓/委托/成交及主推回报；这是供应商能力，不等于中信已经向你的账户开放。[1]

三种接入路径

A. 券商原生条件单：最快、系统边界最小

  • 方式：你在中信官方终端创建规则；我协助分析规则的适用性、检查参数和复盘，券商端按产品约定监控触发。[7]
  • 适合：明确价格/时间/数量条件，且不需要复杂跨标的逻辑的场景。能否表达回撤、网格、组合条件，以你实际终端功能为准。
  • 优点（架构判断）：少一个自建下单服务，减少本地停机、网络和凭据暴露环节。
  • 限制：不能自动把“基本面恶化”等自然语言转换成可靠规则；触发不等于成交。云端还是本地执行、盘后是否有效、断线是否继续、报价类型与失效日期，都要核产品说明。
  • 定位：最快的低复杂度起点，不是完整的AI交易平台。

B. 券商认可的API/量化终端：长期推荐，但先确认准入

  • 方式：优先询问现有中信账户可提供什么：CATS及其许可接口，或营业部实际支持的QMT/MiniQMT等。不要因为QMT社区热门就先选定，再迁就券商。[4]
  • 能力：以MiniQMT为例，可以形成持仓—订单—成交闭环；官方要求先启动MiniQMT客户端，不能把Python库当作脱离券商终端、凭一个普通API Key就能远程下单的公网REST服务。[1][8]
  • 部署：交易节点按券商正式支持的OS、SDK与终端版本选择；若交付Windows终端，就单独设Windows执行节点，现有Linux上的Hermes只做研究与协调。没有核实具体发行包前，不宣称Linux绝对不可用或已能直接运行。
  • 优点（架构判断）：可审计、可查询真实可用份额和资金，可处理撤单、部分成交及失败；适合长期工程化。
  • 代价：接口权限、终端运维、行情授权、交易报告、费用和故障恢复均需落实。个人是否可开、资金/交易量门槛、费用，不采信网络传言，由中信书面确认。
  • 推荐形态：先只读和模拟，再人审；不要从开放式LLM判断直接跳到无人值守实盘。

C. RPA/界面自动化：可研究交互，不作为无人值守实盘方案

  • 方式：识别桌面或手机界面，填入订单并点击。这里只讨论通用技术，不尝试操作账户，也不逆向私有交易协议。
  • 风险（工程判断）：弹窗、验证码、登录过期、窗口缩放、App升级、OCR错位、网络卡顿都可能改变动作含义；看见“提交成功”也无法可靠区分已报、部分成交与全部成交。
  • 结论：可以用于模拟界面测试；不建议作为实盘无人值守下单通道。读不到官方成交回报时，不能靠截图猜订单是否成交，更不能重复点击。

推荐链路：把研究、授权、执行分成不同权限域

  • 研究层（Hermes）：读取获准行情、财报和真实账户的只读投影；输出结构化草案及证据，不直接访问交易凭据。
  • 订单草案层：明确账户别名、证券代码、方向、数量、限价/订单类型、有效期、策略版本、依据时间戳与唯一草案ID。草案不是订单，不因一句模糊“好的”自动提交。
  • 人审层：在经过身份验证的页面检查完整内容；确认必须绑定具体草案的不可变内容，单次有效、可过期。代码、方向、数量或价格变更后必须重新确认。微信只做通知入口，不把普通聊天文本视为签名授权。
  • 独立风控层：重新查询券商可用资金/可用份额、当时有效报价与证券交易参数；检查白名单、单笔金额、日累计金额、仓位限制、杠杆禁用、交易时段和价格偏离。限额由你设定，LLM无权修改。
  • 执行层：仅由你控制、且符合券商协议的独立节点调用认可接口。节点不暴露到公网；如需跨机器，使用受限网络、强认证和最小权限。
  • 对账层：根据券商委托、成交、撤单回报更新事实账本，收到成交后再更新持仓投影；每日与券商账户核对。把委托成功误当成交，是必须防止的错误。

建议的订单状态模型：草案 → 待审核 → 已审核 → 提交中 → 已报 → 部分成交 → 全部成交／部分成交后撤单／拒绝；通信超时进入“状态待核”，而非“下单失败再试一次”。

真正难的不是报单，而是故障时不犯错

  • 超时不重发：API超时可能是券商已经收到、但回报未到。先按券商支持的标识查单。若缺服务端幂等能力，不能承诺严格exactly-once；不确定时冻结该意图，等待对账或人工处理。
  • 重复与并发：每个账户单写入者；本地持久化订单意图、回报与去重标识；断线重连后先拉委托和成交再恢复。两个Agent不能同时抢同一账户。
  • 市场规则：读取证券级交易参数，不统一假设所有品种都是100股、同一个涨跌幅、或都支持当日回转；处理可卖份额、最小申报单位、停牌、集合竞价、节假日和撤单限制。上线前逐一按券商及交易所确认。
  • 公司行动：ETF拆分、除权分红、代码及份额变化必须对账；研究中588200曾发生拆分，旧价格线不能直接套到新份额口径。详关联持仓研究。
  • 过期数据：资讯或行情断流时禁止产生新委托；用于研究的缓存降级策略不能直接用于交易。交易前使用券商认可的有效行情，不把当前5分钟公开行情巡检当作执行行情。
  • 熔断：断线、回报积压、连续拒单、对账不平、限额超标或人工急停时停发新单；是否撤销未成交委托另设明确模式。急停不等于不加判断地市价清仓。
  • 安全：交易密码、证书和会话留在受控执行节点，不进入聊天、提示词、Git或报告。第三方文章、网页和模型输出均是不可信输入，无权调整白名单、账户或风控。
  • 策略与系统分开验收：程序稳定不代表策略赚钱；多个模型意见一致也不构成风险控制。历史回测、模拟成交、真实成交必须分账，不能相互冒充。

合规前置：个人、低频、人审都不能想当然豁免

上交所现行细则将通过程序自动生成或者下达交易指令等纳入定义，明确包含个人投资者；会员客户首次开展前，应向接受委托的券商报告，经券商核查确认后方可进行。报告涉及策略、执行方式、申报速率、软件开发主体等，主要策略或软件信息变化还可能需要变更报告。[6]

因此不能宣传“不是高频就无需报告”或“人工点确认就一定不属于程序化”。具体工作流、账户、交易所与软件的适用性，由中信按最新规则确认；自动执行、提供给他人使用或代客管理资金的合规问题应分别评估。本轮已读取上交所正文；深交所规则页面连接失败，未将上交所文件冒充沪深全部规则。

对中信只需先问清这些

  • 我的普通个人A股账户能开通哪些官方程序化平台？CATS、QMT/MiniQMT或其他许可接口，具体是哪种版本？
  • 是否开放资产、可用持仓、委托、成交、撤单及回报？个人准入、资金/交易量门槛和全部费用是什么？
  • 是否有仿真账户或测试环境？行情订阅和交易权限是否分开？
  • 是否允许自编Python策略、外部策略进程、远程执行节点或云主机？支持的OS、认证和网络部署约束是什么？
  • 首次程序化交易报告、策略变更报告如何办理？人审草案到接口执行的具体流程怎样认定？
  • 故障后如何按客户端标识查单、是否支持幂等、回报重放、成交历史和对账？

落地顺序与验收

  • 阶段一：准入＋只读。取得正式文档与权限确认；真实资产、可用资金和份额与券商界面逐项一致。尚不连接报单功能。
  • 阶段二：影子运行。真实数据生成草案但不提交；记录当时可成交条件、拒绝原因、过期、异常恢复，不把模拟结果称作实盘业绩。
  • 阶段三：故障测试。覆盖重复草案、超时但已受理、部分成交后断线、撤单失败、行情过期、公司行动、重启和人工急停。每种都须有预期状态和真实测试日志。
  • 阶段四：由你在获准交易端开展小额、人审验证。明确预算和范围，逐笔核对券商订单号、成交量、成交价及最终资产，不凭HTTP成功或日志“已发送”验收。
  • 阶段五：是否采用受约束的规则自动化，另行决定。仅适用于你批准并合规落地的确定性规则；开放式模型研究仍停留在建议层，不能自行扩大权限或资金范围。

下一步不是购买服务器或写下单脚本，而是取得中信对账户可用平台与接入条件的正式答复。在此之前，可以设计协议、搭建不接真实账户的模拟执行服务，但不能声称已具备自动交易能力。
